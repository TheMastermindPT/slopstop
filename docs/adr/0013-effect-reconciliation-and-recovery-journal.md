# ADR 0013: Effect Reconciliation And Recovery Journal

- Status: Accepted
- Date: 2026-08-26
- Decision owners: Pedro Mesquita

## Context

ADRs 0007 through 0009 require every effectful Model attempt, Tool invocation, Process job, Run-workspace operation, Artifact removal, and Integration apply to be attributable and recoverable without replaying uncertain work. ADR 0008 assigns dispatch, Run workspaces, Process jobs, leases, and checkpoints to Execution while assigning Recovery Journal records, effect reconciliation, and safety proof to Evidence. ADR 0010 then defines typed Effect and Recovery Evidence families with append-only observations, evaluations, decisions, and atomic current evaluations.

Those decisions leave the implementation contract incomplete. A restart still needs one stable effect identity, an immutable declaration, exact write-ahead facts, class-specific observers, evidence-sufficiency rules, retry and cancellation behavior, shared-resource coordination, direct recovery queries, and a clear distinction between recovery, compensation, abandonment, and Integration. The accepted solution for issue 59 keeps one human-readable Effect Dossier but explicitly prevents it from becoming another ledger or state authority.

## Decisions

### Authority And Effect Identity

- Give every effect attempt one opaque Project-scoped `EffectId`. The Application coordinator owns the Effect identity/declaration mechanism, while the selected subject owner retains its operation lifecycle and attributed owner observations: Execution for `run-worker`, the Artifact or external Storage-operation owner for `project-operation`, and Integration for `integration`. Evidence alone owns Effect observations, evaluations, decisions, and decided current authority. An Effect is not a status aggregate and has no mutable lifecycle column.
- Create one immutable declaration before dispatch. Keep only fields common to every Effect on the identity root: Project, Effect subject kind, final authorized operation and argument Artifact/hash, Command ID and fingerprint, effect ordinal, and declaration schema/canonicalization/hash. Persist the admitting receipt/order/fence, subject, authority, scope, coordination, idempotency, cancellation, observer, and proof requirements in exact relational children.
- Permit one admitted command to declare several independently reconcilable effects by assigning a non-negative `effect_ordinal`. Make `(project_id, command_id, effect_ordinal)` unique. Effects that cannot be retried, compensated, or reconciled independently belong in one declaration; independently recoverable remote calls or mutations require separate Effect identities.
- Keep the immutable declaration structural and exact. A changed target, scope, resource key, final argument hash, Capability, policy epoch, approval, budget, idempotency key, cancellation behavior, or proof requirement creates a new command and Effect identity. No adapter may widen the declaration after intent is durable.
- Let the deterministic Application coordinator invoke owner-specific commands and the single canonical Writer transaction. Logical table ownership does not grant another process a writer or allow Execution to decide Evidence truth.
- Keep ADR 0010's `effect_current_evaluations` row as the only current Effect outcome. Do not add `EffectOutcomeHead`, effect status, recovered flag, terminal flag, successful flag, or another current pointer in Execution, the Recovery Journal, a reconciler, or a projection.

### Closed Effect Subjects

Use exactly this top-level `EffectSubjectKind` discriminated union. No generic owner, nullable universal Run, free-text operation, or fourth variant is permitted:

| Subject kind | Required fields | Explicitly absent |
| --- | --- | --- |
| `run-worker` | Exact `RunId`, one closed target arm, one workspace-binding arm, and one same-Run Evidence scope: Run-workspace or Task-workspace for `run-workspace`, and Run-workspace authority scope for `no-workspace` | Project-operation and Integration identities |
| `project-operation` | Exact `ProjectOperationKind`, exact owner-operation identity, one `project-operation` Evidence scope, and operation-specific before state | Run, Waypoint parent, Worker, Delegation task, and Run-workspace identities |
| `integration` | Exact `IntegrationAttemptId`, `CandidateDeltaId` and version, Candidate Evidence scope/fingerprint, `IntegrationTargetId`, target Repository resource, and target fingerprint | Run, Waypoint parent, Worker, Delegation task, and Run-workspace identities |

- For `run-worker`, use exactly one target arm: `run` requires `RunId` plus one versioned Run-operation identity and kind; `waypoint-parent` requires the same Run's `ParentId` and the exact Sealed invocation, Tool invocation, or other admitted owner request; `worker` requires the same Run's `WorkerId`, `DelegationTaskId`, accepted Delegation-plan revision, and exact admitted owner request. Composite foreign keys prove same Project and Run.
- Give every `run-worker` subject exactly one workspace-binding arm. `run-workspace` requires the same Run's `RunWorkspaceId`, `RunWorkspaceResourceKey`, exact Run-workspace or Task-workspace Evidence scope, and accepted before fingerprint. `no-workspace` is permitted only when the final authorized operation declares no repository input or mutation and uses the closed reason `provider-boundary`, `repository-independent-process`, `external-service`, or `credential-access`. It requires the same Run's Run-workspace Evidence scope solely as the partition key used by Effect and Run Recovery current authority, but stores no direct Run-workspace identity, resource, Task-workspace scope, or Workspace-fingerprint dependency and cannot authorize repository observation or mutation.
- For `project-operation`, use exactly one closed operation arm. `artifact-removal` requires the exact `ArtifactId`, Artifact Evidence scope, expected `ArtifactStateVersionId`, accepted removal decision, Artifact-store identity, and owner operation identity. `storage-operation` requires the exact ADR 0005 `StorageOperationId`, `StorageId`, operation kind, external operation-journal identity, and source/target `StorageGenerationId` values required by that operation. It never invents a Run workspace.
- Make `storage-operation` a nested closed union rather than a row of nullable generation fields. `backup` and `export` require the exact source generation and output Project snapshot identity and prohibit a target generation. `migration` requires source and staged target generations. `restore` requires the pre-operation current generation, exact restore Project snapshot, and staged target generation. `import` requires the exact Project-export snapshot/source lineage and staged destination generation and prohibits a local source generation. `runtime-reset` requires source generation, quarantine identity, and staged target generation. `delete` requires one delete-subject row, one external deletion tombstone, and one-or-more generation-member rows and prohibits a target-generation column on the delete subject. Each arm also references its matching ADR 0005 operation kind and owned step set.
- For `project-operation`, create one `project-operation` Evidence scope bound one-to-one to the Effect and operation arm. Artifact removal also references the existing Artifact Evidence scope as an input dependency; it does not reuse that scope as the Effect subject. ADR 0006 Storage-operation records remain outside every Storage generation they can alter, and this subject arm does not move their lifecycle authority into Execution or Evidence.
- For `integration`, bind the subject to the Integration-owned attempt and exact Candidate/target authority. Its target Repository resource is not an ADR 0008 Run workspace. Integration keeps apply lifecycle authority while the common Effect contract records its physical side effect and Evidence outcome.

### Declared Effect Classes And Resource Keys

ADR 0013 is the single owner of the closed v1 `DeclaredEffectSet` class and `EffectResourceKeyKind` vocabularies. Other ADRs and `CONTEXT.md` may reference these exact tokens but must not redefine, copy, narrow, or extend their lists.

Use exactly this closed `DeclaredEffectSet` class vocabulary:

| Effect class | Exact declared scope | Minimum typed resource keys |
| --- | --- | --- |
| `workspace-files` | Repository-relative file roots or exact files that may be created, changed, renamed, or removed in one exact declared repository target | Run-workspace resource for `run-worker` or Integration-target Repository resource for `integration`, plus normalized repository-relative path scope |
| `git-index` | One exact declared target worktree index and the paths or entries that may change | Repository binding, Git common directory, worktree administration identity, and index identity |
| `git-refs` | Exact fully qualified refs and permitted old/new object expectations in one declared Run-workspace or Integration target | Repository binding, Git common directory, and one key per fully qualified ref |
| `git-worktree-admin` | One exact worktree create, lock, unlock, repair, or remove target selected by the subject arm | Repository binding, Git common directory, and worktree administration identity |
| `local-artifacts` | Exact Artifact identities or bounded local stores that may receive, change, or remove bytes | One `local-artifact:<ArtifactId>` key per Artifact plus its `local-artifact-store:<ArtifactStoreId>` key and owning Evidence scope |
| `project-storage` | One exact ADR 0005 Storage operation over logical registry, generation, Project snapshot, import/export, backup, or deletion-tombstone resources | `storage-registry:<StorageId>`, `project-storage-operation:<StorageOperationId>`, and every operation-specific key required below |
| `process-execution` | One bounded executable invocation, process tree, environment-name policy, descendants policy, and terminal-proof contract | Process-job identity, Run-workspace resource when applicable, and every declared shared cache or process-global resource |
| `external-service` | Exact service, account or credential context, region or endpoint class, operation, remote resource, cost scope, and request/idempotency identity when supported | Service, account context, operation, and remote resource or request scope |
| `credential-access` | Exact operating-system credential reference and permitted operation, never the credential value | Credential-reference identity and consuming Capability |

- A Capability declares the possible classes and key shapes. The final authorized action declares the exact subset and concrete scopes. Unknown, unclassified, wildcard remote, pathless file, bare Git, implicit process, or hidden credential behavior fails closed before intent.
- Represent each shared resource with a typed `EffectResourceKey`, not a path or display name. Use exactly these closed key kinds: `run-workspace-resource`, `integration-target-resource`, `workspace-path-scope`, `git-common-directory`, `git-index`, `git-ref`, `git-worktree-admin`, `local-artifact`, `local-artifact-store`, `storage-registry`, `project-storage-operation`, `storage-generation`, `project-snapshot`, `project-backup`, `project-export`, `project-import-source`, `storage-deletion-tombstone`, `shared-cache`, `process-tree`, `external-service-resource`, and `credential-reference`.
- Encode Artifact keys exactly as `local-artifact:<ArtifactId>` and store keys exactly as `local-artifact-store:<ArtifactStoreId>`. An individual Artifact create, mutation, move, or removal requires both keys. A store key alone fails closed because it cannot identify which Artifact identity is being changed.
- Encode Storage keys exactly as `storage-registry:<StorageId>`, `project-storage-operation:<StorageOperationId>`, `storage-generation:<StorageGenerationId>`, `project-snapshot:<ProjectSnapshotId>`, `project-backup:<ProjectSnapshotId>`, `project-export:<ProjectSnapshotId>`, `project-import-source:<ProjectSnapshotId>`, and `storage-deletion-tombstone:<DeletionTombstoneId>`. They identify logical records and packages only. `storage_locations` owns machine-local paths; a path is never a declaration scope, resource key, equality key, or coordination identity.
- Permit `project-storage` only for a `project-operation` subject's `storage-operation` arm. Every such Effect requires its `storage-registry` and `project-storage-operation` keys. `backup` additionally requires its source `storage-generation`, `project-snapshot`, and `project-backup` keys; `export` requires source `storage-generation`, `project-snapshot`, and `project-export` keys; `migration` requires source and target `storage-generation` plus every pre-migration `project-snapshot` and `project-backup` key; `restore` requires current and target `storage-generation`, consumed `project-snapshot`, and its `project-backup` or `project-export` subtype key; `import` requires destination `storage-generation`, consumed `project-snapshot`, `project-export`, and `project-import-source` keys; `runtime-reset` requires source and target `storage-generation` keys; `delete` requires one `storage-generation` key for every generation member, the `storage-deletion-tombstone` key, and keys for every in-scope internal Project snapshot, backup, or export. Missing or extra operation-incompatible kinds reject intent.
- Store an exact access kind `observe`, `mutate`, `invoke`, or `consume` with each resource key. `observe` may run concurrently only against the same accepted fingerprint. `mutate` is exclusive. `invoke` or `consume` is incompatible by default unless the Capability policy proves independent subresources and separate idempotency, budget, and rate-limit authority.
- Derive workspace and Git keys from Repository binding, Git common directory, worktree administration identity, the subject's Run-workspace or Integration-target Repository resource, and stable relative scope. A machine-local path may be retained as redacted installation-local observation data but is never the portable identity or sole coordination key.
- Separate worktrees isolate working files and indexes but may still share the Git common directory, refs, hooks, object store, configured remote, credential, service account, cache, package store, daemon, or rate limit. Every such dependency receives its own key. A missing key is undeclared scope, not evidence that the resources are independent.
- Permit parallel effects only when their subject-specific Evidence scopes are distinct where required and all intersecting resource-key accesses are compatible. An unresolved, missing, broken, truncated, scope-violating, or uncertain Effect closes new conflicting dispatch only for its resource keys and owning scope; unrelated Workers, Project operations, Integration attempts, and resources remain eligible.

### Recovery Journal Facts

Evidence owns one `RecoveryJournalId` per Effect and append-only facts under the same `EffectId`. Use exactly this closed `RecoveryJournalFactKind` vocabulary:

| Fact kind | Meaning and required reference |
| --- | --- |
| `intent` | The immutable Effect declaration and admitting project command receipt or external Storage-operation request record are durable; no start is implied. |
| `started` | Start authorization is durable and the Effect identity is permanently consumed; no boundary crossing or real-world effect is implied. |
| `dispatch-observed` | An exact subject-owner boundary or launch observation exists; it reports only what that owner observed. |
| `terminal-observed` | An exact owner-attempt terminal transport, adapter, Process-job, Integration-attempt, or operation observation exists; semantic and effect success remain undecided. |
| `fingerprint-observed` | An exact `before`, `after`, or `recovery` fingerprint or Artifact-state observation is linked for a declared scope. |
| `cancellation-requested` | A typed cancellation command closed applicable new dispatch and requested bounded cancellation. |
| `cancellation-observed` | An exact acknowledgement, confirmed disappearance, refusal, timeout, late result, or continuity-loss observation exists. |
| `reconciliation-observed` | One typed Effect observation was recorded against the exact declaration and its coordinator or observer producer. |

- Facts are historical claims with exact producer, source identity, command receipt when applicable, observed time, ordinal, schema version, and record digest. Project-database partitions also store canonical recorded Project sequence. The external Storage-operation partition instead stores its application operation-journal ordinal and may retain an observed Project sequence only as supporting input; it never invents Project order while `slopstop.db` is unavailable. Facts never carry an Effect verdict or move a current evaluation by themselves.
- Require exactly one `intent` and at most one `started` fact per Effect. `intent` is ordinal zero. `started` requires the exact declaration hash and no prior cancellation, terminal closure, or abandonment that prohibits start. Facts after `started` use strictly increasing ordinals; distinct sources may append more than one terminal, fingerprint, cancellation, or reconciliation observation.
- The Application coordinator supplies immutable intent, and the exact subject owner supplies dispatch, cancellation, terminal, and Process-job or operation observations as applicable. Evidence validates their identity and appends Journal facts that reference those records rather than copying or reinterpreting owner state. A typed reconciler supplies only an observation proposal; the Evidence writer validates and records it.
- A Journal parse, foreign-key, sequence, digest, declaration-hash, source-identity, or required-child failure is `EFFECT_BROKEN`; for `run-worker` it also produces the applicable `RECOVERY_BROKEN` authority, while other subject owners retain their own broken state. A missing required fact or source is `EFFECT_MISSING` plus the subject owner's applicable missing or blocked outcome. Neither case is an empty Journal, no effect, or clean recovery.

### Current Effect Outcome

ADR 0010 owns the exact closed Effect-family verdict vocabulary. This decision adds operational consequences without introducing a second vocabulary:

| ADR 0010 verdict | Dispatch and recovery consequence |
| --- | --- |
| `EFFECT_NOT_STARTED` | Conclusive sequencing and observer Evidence proves no declared real-world effect boundary was crossed; a durable Journal `started` fact may still have consumed the identity, so a later attempt uses a new Effect identity. |
| `EFFECT_STARTED_UNSETTLED` | `started` is durable and no conclusive terminal real-world outcome exists; checkpoints and conflicting dispatch are blocked. |
| `EFFECT_COMPLETED_AS_DECLARED` | Every declared class and scope is conclusively complete with no undeclared effect; replay is prohibited. |
| `EFFECT_FAILED_NO_EFFECT` | A terminal non-success, including confirmed cancellation, has complete before/after proof that no declared or undeclared effect occurred; a new attempt may be authorized. |
| `EFFECT_PARTIAL` | Some declared effect occurred without the complete declared result; retry is prohibited and explicit remediation or compensation is required. |
| `EFFECT_SCOPE_VIOLATION` | A conclusive undeclared attempt or effect occurred; dispatch closes and remediation is required even if the requested result also completed. |
| `EFFECT_MISSING` | A required Journal fact, owner observation, fingerprint, remote record, or Artifact is unavailable; absence cannot prove no effect. |
| `EFFECT_TRUNCATED` | A bound prevented complete observation of declared or undeclared effects; retry and safety proof are blocked. |
| `EFFECT_UNCERTAIN` | The effect started and complete available Evidence cannot establish one real-world terminal outcome; it is retained and never replayed automatically. |
| `EFFECT_REJECTED` | The proposed observation or reconciliation is unusable under identity, scope, trust, or policy; it grants no retry or safety authority. |
| `EFFECT_BROKEN` | Journal, source, integrity, adapter observation, or evaluator execution is inconsistent or failed; it is a broken gate, never no effect. |

- A cancellation request, Process-job `cancelled` state, provider cancellation acknowledgement, rollback request, abandonment, or accepted risk is not an Effect outcome. Evidence evaluates what happened in the real world and selects only the ADR 0010 verdict justified by complete typed observations.
- Apply structural broken, missing, and truncation checks before favorable outcomes. Apply conclusive scope violation before completion. An in-progress durable start remains `EFFECT_STARTED_UNSETTLED`; when an ended attempt still lacks unique proof, use `EFFECT_UNCERTAIN`. `EFFECT_NOT_STARTED`, `EFFECT_COMPLETED_AS_DECLARED`, and `EFFECT_FAILED_NO_EFFECT` require positive conclusive proof, never silence or absence from a log.
- `StartEffect` appends and flushes only the `started` Journal fact and consumes the identity. Before any physical boundary, `RecordEffectObservation` appends an `effect_sequence_observations` row with role `started-before-boundary` and its `reconciliation-observed` fact. Neither command writes an evaluation, decision, or current pointer.
- `DecideEffectReconciliation` is a separate command. Before the first physical crossing, it must accept an evaluation of that exact sequence observation as current `EFFECT_STARTED_UNSETTLED`. Later observations and terminal reconciliation use the same two-command observation-then-decision protocol. Every accepted decision appends the evaluation and decision and atomically compare-and-sets `effect_current_evaluations`; a rejected proposal advances only `latest_*` unless the same decision transaction proves and accepts a required non-favorable replacement for an inapplicable prior current evaluation.
- A durable `started` fact or an Effect observation without a corresponding decision is a direct unresolved-input blocker. The current row may still reference an older evaluation or may not exist yet, but no physical boundary crossing, checkpoint, retry, completion, cleanup, Artifact consumption, or Integration gate may interpret that pointer as clean while the required pre-boundary decision is absent. The accepted pre-boundary `EFFECT_STARTED_UNSETTLED` decision permits only the exact admitted first crossing after its owner-specific pre-boundary record is durable; it blocks retry, duplicate dispatch, and every conflicting resource dispatch.

### Append-Before-Execute And Crash Windows

Use this exact order for every effectful boundary:

1. Apply canonical command idempotency and validate the final authorized arguments, exact subject arm, declaration, approval, policy, Capability, budget, subject-specific scope and before state, applicable lease/read claim, resource keys, and observer availability.
2. In one owner-partition-fenced transaction, create the immutable Effect and its declaration children, create its Recovery Journal, append `intent`, and link the admitting project command receipt or external Storage-operation request record. Commit and durably flush before any start or external preparation that can itself cause an effect.
3. In a second owner-partition-fenced transaction, append `started` and permanently consume the Effect identity. Commit and durably flush. Do not write an Effect observation, evaluation, decision, current pointer, owner-specific boundary record, or physical resource in this transaction. A Tool invocation, queued Process job, Storage operation, or Integration attempt allocated before Effect intent remains inert and cannot count as that boundary record.
4. Through `RecordEffectObservation`, append and flush one `started-before-boundary` sequence observation proving the exact durable `intent` and `started` records, declaration hash, owner-partition order, and that no owner-specific boundary record or physical boundary record yet exists.
5. Through a separate `DecideEffectReconciliation` transaction, evaluate only that exact observation, append an accepting decision, and atomically advance Effect current authority to `EFFECT_STARTED_UNSETTLED`. No physical resource has been touched at this point.
6. Create and flush the owner-specific pre-boundary record required by its ADR. Create the Model attempt before provider crossing; consume the authorized Tool-invocation identity through its effect-start observation before its adapter or process boundary; move the already queued Process job through its durable `starting` transition before spawn; append and flush the ADR 0010 `ARTIFACT_REMOVAL_STARTED` observation before byte deletion; append the exact Storage-operation step before Storage mutation; and append the Integration attempt's apply-start record before physical apply. Each record references the accepted pre-boundary Effect decision and version. Preallocated owner identities remain identity only and grant no crossing authority.
7. For `artifact-removal` only, run `DecideArtifactStateEvaluation` after the `ARTIFACT_REMOVAL_STARTED` observation. In one fenced transaction, append and accept the exact Artifact-state decision, create the removal-started state version, and atomically advance `artifact_state_current_evaluations`. Commit and verify that transaction before byte deletion. No other owner record or Effect decision substitutes for this Artifact-owned gate.
8. Only now cross the adapter, operating-system, repository, filesystem, credential, Storage, or remote boundary. Artifact removal may cross only when both current `EFFECT_STARTED_UNSETTLED` and current `ARTIFACT_REMOVAL_STARTED` reference the exact same admitted removal. Append Execution dispatch observations and their `dispatch-observed` facts when obtained. An observation written after the boundary cannot be treated as the proof that made crossing safe.
9. Append every owner terminal, cancellation, fingerprint, Artifact, Storage, remote, and typed reconciler observation through `RecordEffectObservation`. That command writes the common Evidence entry, one typed observation, its dependencies and Artifacts, and Journal `reconciliation-observed`, then flushes. It writes no evaluation or current authority. Never infer missing facts from process exit, adapter return, or a newer workspace state.
10. In a separate later `DecideEffectReconciliation` transaction, append the terminal Effect evaluation and decision, typed dependencies, and the atomic `effect_current_evaluations` advance when accepted. Append an applicable Run Recovery evaluation/decision and Safety proof only for a `run-worker` subject; Project operation and Integration owners consume the Effect decision through their own typed state commands.
11. Only then may the exact subject owner consume accepted terminal authority to release a lease, complete a checkpoint, remove one Run recovery condition, authorize another attempt, advance Artifact or Storage operation state, or advance Integration.

Crash recovery applies these rules:

| Last durable state | Required interpretation |
| --- | --- |
| No `intent` | No Effect was admitted. Any observed real-world change is unattributed and requires a new broken or external-change observation; no default Effect is fabricated. |
| `intent` without `started` | The declared Effect did not enter the start protocol. Startup may accept `EFFECT_NOT_STARTED` after Journal integrity and the absence of a contradictory owner record are proved. No Effect replay occurs. |
| `started` without its `started-before-boundary` observation | The Effect identity remains consumed, but the ordering contract proves that no owner-specific boundary record or physical boundary may lawfully exist. Append the missing sequence observation only after direct owner-partition checks prove that absence; otherwise append a broken or contradictory observation. No physical replay occurs. |
| Pre-boundary observation without its accepted decision | The exact observation is directly queryable and blocks boundary crossing. Run `DecideEffectReconciliation`; never create the owner-specific boundary record or touch a physical resource first. |
| Accepted `EFFECT_STARTED_UNSETTLED` without the required pre-boundary owner record | The Effect is current, consumed, and known not yet to have touched a physical resource. Recovery may create the one admitted owner-specific boundary record and continue the original first crossing only when subject authority, resources, policy, and observer contract are still current; otherwise retain the unsettled blocker. This is continuation, never retry. |
| Artifact `ARTIFACT_REMOVAL_STARTED` observation without its accepted decision/current advance | The Artifact observation is durable but grants no deletion authority. Preserve the prior current Artifact pointer, expose the undecided observation directly, block byte use and deletion, and run `DecideArtifactStateEvaluation`. |
| Accepted current `ARTIFACT_REMOVAL_STARTED` without byte-dispatch evidence | The exact Artifact removal is durably in progress, but no bytes were touched under the required order. Continue only that admitted delete while both Effect and Artifact current authority still match; never create a retry or report removal complete. |
| Pre-boundary owner record without dispatch or terminal proof | Reconcile from owner-specific facts. A Model attempt with a durable local abort may be proven not started; a Process job whose spawn may have occurred or a remote call whose boundary may have been crossed remains unsettled or uncertain. |
| Dispatch observation without terminal proof | Observe the identified process or remote request, request cancellation when authorized, and keep the Effect unsettled or uncertain. Never launch it again. |
| Terminal owner observation without every required after fingerprint or remote fact | Preserve partial, missing, truncated, broken, or uncertain outcome according to the exact missing proof. Process exit or adapter return is insufficient. |
| Complete facts without an accepted current evaluation | Keep the observations visible and unresolved, then run `DecideEffectReconciliation` to append the evaluation/decision and atomically advance Effect current authority. Add Run Recovery authority only for a `run-worker` subject. Do not replay the effect to recreate a missing decision. |
| Observation without a decision | Preserve the old current pointer or no current row, expose the undecided observation directly, and block every favorable consumer until a later decision accepts or rejects it. Never infer the observation's verdict. |
| Accepted current evaluations without an Execution checkpoint or transition | Reconstruct the missing owner action from the exact accepted Evidence through its typed idempotent command. Do not repeat the real-world effect. |

### Typed Reconcilers And Evidence Sufficiency

- Implement typed reconcilers as harness adapters. Each receives one immutable declaration, exact current owner observations, approved observer Capability, bounded query limits, and required credentials through references. It emits one versioned attributed observation with exact source identities, completeness, omissions, truncation, times, and Artifact links. It cannot write the Journal, select a verdict, authorize retry, move a Run, release a lease, or apply Integration.
- Keep reconcilers repeatable but not automatically repeat-dispatched. A remote query, credential resolution, process launch, Git command, or filesystem scan that is itself effectful uses its own Effect identity and Journal. A proven read-only local observation may use the Evidence producer-attempt contract without a second Effect.

| Declared class | Required observer behavior and sufficient proof |
| --- | --- |
| `workspace-files` | Compare the accepted before fingerprint with a fresh complete fingerprint for the exact subject repository target and declared path manifest. That target is a Run workspace for `run-worker` or the Integration target for `integration`. Completion requires every expected file result and no out-of-scope path; no-effect requires exact relevant equality and complete untracked enumeration. Missing paths without deletion proof, unreadable files, symlink ambiguity, or bounded enumeration cannot prove clean. |
| `git-index` | Observe the exact subject-target worktree index identity, staged entries, modes, object IDs, and declared paths against before state. Working-tree equality does not prove index equality. |
| `git-refs` | Read each exact fully qualified ref and expected old/new object through Git for the declared Run-workspace or Integration target, plus remote evidence when the declared effect includes a push. A local ref update cannot prove a remote ref update, and reflog absence cannot prove no update. |
| `git-worktree-admin` | Use `git worktree list --porcelain`, exact Git common directory, subject-target administration identity, lock state, and target existence. Directory presence or absence alone is insufficient. |
| `local-artifacts` | Consume ADR 0010 Artifact-state observations and exact Artifact identity, size, digest, provenance, and store reachability. Equal bytes do not merge Artifact identities; missing, unavailable, removed, corrupt, or state-broken bytes remain their exact non-clean state. |
| `project-storage` | Consume the external ADR 0005 operation journal, exact registry revision, operation revision, generation manifests and lineage, Project snapshot identity/manifests/checksums, active-generation observation, import/export/backup identity, delete generation membership, and deletion tombstone. Completion requires conclusive proof for every declared resource key and operation step. A path, missing generation member, missing tombstone, incomplete package, or unavailable manifest cannot prove completion or no effect. |
| `process-execution` | Consume the exact Process-job identity, durable start identity, process-tree observations, terminal state, confirmed disappearance, output/truncation artifacts, and cancellation observations. Process exit establishes only the process observation declared for this class; it cannot prove file, Git, remote, credential, test, or semantic success. |
| `external-service` | Query the authoritative remote request or resource by the exact provider request identity or idempotency key and account/region scope. A provider terminal response, state read, receipt, usage, or cost record may prove its own fact. Transport disconnect, absent local logs, generic retry behavior, or a different account cannot prove no effect. If the service exposes no conclusive observer, retain uncertainty. |
| `credential-access` | Observe only the exact operating-system credential-reference operation and its success, refusal, or proven non-start. Never persist a value. Credential access proves neither provider invocation nor remote outcome; those require their own declared class and observations. |

- `EFFECT_COMPLETED_AS_DECLARED` requires complete trustworthy observations for every declared class and scope, every required terminal and after fact, exact declaration and owner identity, no contradictory observation, no undeclared effect, and no missing, broken, truncated, stale, or uncertain dependency.
- `EFFECT_FAILED_NO_EFFECT` requires a terminal non-success or confirmed cancellation plus conclusive proof that none of the declared classes crossed its real-world boundary and no undeclared effect occurred. If a process started, a credential was read, a ref moved, a file changed, an Artifact was removed, or a remote request was accepted, the composite Effect is not no-effect even when its ultimate purpose failed.
- `EFFECT_PARTIAL` requires a complete enough observation to prove at least one declared effect and the absence of the complete declared result. Incomplete observation that cannot bound what happened remains uncertain, missing, truncated, or broken instead of partial by guess.
- `EFFECT_SCOPE_VIOLATION` requires conclusive observation of an attempted or completed undeclared class, target, path, ref, resource, account, credential, process descendant, or shared resource. It remains a violation even when all declared outcomes also completed.

### Historical Artifact Registration

- Register historical logs, Git reflog exports, provider receipts, remote audit exports, process output, manifests, and recovered files through ADR 0010's `imported-source` Artifact path. Preserve source kind `historical`, logical source, revision or request identity, stable relative identifier, source time, original producer when known, declared digest, importer command, importer trust basis, and current Artifact state.
- Historical source time never changes Journal order or canonical recorded time. Importing an old record does not append a backdated `intent`, `started`, dispatch, terminal, or fingerprint fact as if SlopStop observed it then. Reconciliation appends a current `reconciliation-observed` fact that references the historical Artifact.
- A historical Artifact may establish an outcome only when its identity, integrity, trust, account or Repository scope, and content bind conclusively to the exact Effect declaration. A detached screenshot, free-text explanation, same digest, absent log line, or unverified export remains supporting or unusable Evidence and cannot manufacture completion or no-effect.

### Idempotency, Retry, Cancellation, Compensation, And Abandonment

- Apply canonical ADR 0006 command idempotency before every `slopstop.db` Effect command and Storage-operation request/step idempotency before every external-partition command. An exact duplicate returns the original receipt or operation record, Effect, Journal, owner attempt, observations, and current versions without appending or dispatching. A reused Command ID or Storage-operation request identity with different content creates `IDEMPOTENCY_CONFLICT` and no Effect write.
- Durable `started` permanently consumes the `EffectId`. Never relaunch it, even when later Evidence proves `EFFECT_NOT_STARTED` or `EFFECT_FAILED_NO_EFFECT`. A new real-world attempt uses a new Command ID and fingerprint, owner-attempt identity, Effect identity and ordinal, Journal, before fingerprint, lease proof, budget decision, approval where required, and idempotency key.
- Allow `AuthorizeEffectRetry` only from an exact accepted current Effect evaluation whose version is still current plus the matching subject owner's safe retry authority. A `run-worker` subject requires current Run Recovery authority; `project-operation` requires the exact current Artifact or Storage-operation state; `integration` requires the exact Integration attempt and applicability state. `EFFECT_NOT_STARTED` or `EFFECT_FAILED_NO_EFFECT` may authorize a new attempt only when that subject-specific authority also proves no pending effect. A historical partial, scope-violating, or uncertain outcome requires a later completed compensation or normalizing Effect, fresh final observations, and subject-specific safety proof that no pending or late effect can remain. `EFFECT_COMPLETED_AS_DECLARED` prohibits retry because work already completed. Missing, truncated, rejected, or broken Evidence can never authorize retry.
- A transport resend remains inside the original Effect only when the service contract and observation prove the same remote request identity or idempotency key and that the provider will return or continue the same operation. Store that as another dispatch observation, not a retry Effect. Never claim exactly once and never infer this permission from an SDK's default retry setting.
- `RequestEffectCancellation` closes new applicable dispatch before contacting the process or service and appends `cancellation-requested`. Bounded cancellation may produce acknowledgement, refusal, timeout, late result, or confirmed disappearance observations. Only confirmed process-tree disappearance permits a Process job's `cancelled` state; neither acknowledgement nor local disconnect proves the real-world Effect stopped.
- Evaluate cancellation by real-world outcome. Pre-start cancellation may become `EFFECT_NOT_STARTED`; confirmed no-effect after start may become `EFFECT_FAILED_NO_EFFECT`; completed work remains `EFFECT_COMPLETED_AS_DECLARED`; incomplete known work is `EFFECT_PARTIAL`; inconclusive work is `EFFECT_UNCERTAIN` or another exact non-clean verdict.
- Treat rollback or compensation as a new immutable Effect linked by `compensates`. It follows the full declaration, approval, Journal, observer, outcome, and retry contract. The original Effect remains completed, partial, violating, or uncertain according to its own Evidence. Successful compensation does not rewrite it to no-effect, but a later Recovery evaluation may use the complete chain and fresh current-state proof to establish that no unresolved risk remains.
- `AbandonEffectRecovery` is an explicit canonical user decision to stop automatic observation or compensation for one Effect and retain its exact current outcome. It closes further conflicting dispatch for the exact subject owner and retains its affected workspace, Artifact, Storage, Candidate, and resource records as applicable. It cannot create a Safety proof, release a resource blocked by possible mutation, authorize retry, mark cleanup safe, make a Candidate acceptable, authorize Integration, or change Effect current authority or any subject-owner current authority.
- ADR 0014 Finding risk acceptance and any separate operational risk acknowledgement remain separate typed decisions with actor, reason, scope, policy, and expiry when applicable. They may explain an explicit abandonment or later user choice, but they cannot write Effect or Recovery Evidence, convert unknown to success, satisfy an unrelated Completion obligation, or manufacture `RECOVERY_RECONCILED_*`.

### Checkpoints, Blocked Operations, And Restart

- A Safe checkpoint or Worker stop checkpoint requires every Effect in its exact scope either to have current `EFFECT_NOT_STARTED`, `EFFECT_COMPLETED_AS_DECLARED`, or `EFFECT_FAILED_NO_EFFECT`, or to be bounded by an exact chain of completed compensation or normalization Effects and an accepted Recovery safety proof. In both cases it requires complete final fingerprints, no pending or late effect, and no active owner attempt. Rejected reconciliation, missing/truncated/broken input, unbounded partial or scope violation, and unresolved uncertainty remain unsafe even when no process is running.
- While an Effect is started-unsettled, partial without completed remediation, scope-violating, missing, truncated, uncertain, rejected, or broken, prohibit conflicting resource dispatch, lease release, Safe checkpoint, pause confirmation, Worker stop confirmation, stopped-Worker retry or replacement, Run completion, Candidate acceptance for the affected scope, Integration applicability or apply, discard that claims safety, and cleanup. Preserve unrelated scopes and compatible resource keys.
- On harness startup, before Turn Machines, Process-job dispatch, stopped-Worker replacement, Integration apply, or Action availability, query every admitted nonterminal Effect and unresolved current outcome. Reconcile Journal integrity, owner identity, Process-job continuity, Git and filesystem state, Artifact state, remote request identities, cancellation observations, and required fingerprints. Append exact interrupted, missing, broken, or uncertain observations rather than defaulting to no effect.
- Preserve an identified still-running process under its Process-job owner, observe or cancel it under policy, and keep its Effect unsettled. Mark continuity-lost Process jobs `interrupted`; that status is input to the process reconciler and never the Effect verdict.
- After Evidence advances Effect current authority and any applicable subject-owner authority, only the exact owner command may consume them. For `run-worker`, ADR 0007 `ApplyRunRecoveryReconciliation` removes one Run recovery condition and recomputes every blocker; it never assumes that a reconciled Effect means the Run should become `running`. Artifact, Storage, and Integration commands consume their own typed state instead of a fabricated Run Recovery row.

### Integration Boundary And Effect Dossier

- Keep Candidate user authorization, Integration applicability, Integration attempt lifecycle, and physical apply outside the Effect family. Evidence decides applicability under ADR 0010; Integration alone decides and records apply lifecycle. Neither a favorable Effect outcome nor the Effect Dossier applies a Candidate.
- Before physical apply, the Integration command declares one or more Effects with exact Candidate, Candidate fingerprint, target, target fingerprint, Git/file/resource keys, command fingerprint, and preallocated inert Integration-attempt identity. For each Effect, the Application coordinator flushes intent and `started`, records and separately accepts pre-boundary `EFFECT_STARTED_UNSETTLED`, then appends the Integration attempt's apply-start record with that decision/version before physical apply. Integration emits attributed observations; Evidence reconciles the effects; a later Integration command consumes those exact terminal current evaluations to advance Integration state.
- Never merge unrelated remote, process, credential, local-artifact, or Integration effects during Candidate fan-in. Candidate construction combines only explicitly selected repository deltas and keeps every effect dependency exact.
- Define the Effect Dossier as a query/view over immutable `effects`, subject and declaration children, owner observations, Recovery Journal facts, Evidence observations/evaluations/decisions, current Effect evaluation, applicable Run Recovery evaluation, applicable Artifact/Storage/Integration owner state, Artifacts, retry/compensation/abandonment links, and relevant Process jobs. It has no write command, table-owned status, current pointer, accepted flag, or independent cache authority.
- A replaceable Dossier cache is permitted only when keyed by exact source versions and discarded on mismatch. Missing or broken source data renders the Dossier incomplete or broken with the exact diagnostic; it never omits the gap or synthesizes a clean story.

No boundary crossing follows a failed or unverified intent/start flush; Artifact byte deletion also remains prohibited after a failed, rejected, stale, or unverified `DecideArtifactStateEvaluation` transaction.

### Keys And Constraints

- Key each partition's `effects` by `(project_id, effect_id)`. Store only `EffectSubjectKind`, command identity/fingerprint, non-negative effect ordinal, declaration schema and canonicalization versions, declaration hash algorithm/value, and final authorized operation/argument Artifact/hash. Make `(project_id, command_id, effect_ordinal)` unique across the selected partition without making declaration hashes unique. Do not store command receipt/order/fence, Run identity, owner-operation identity, workspace, Evidence scope, before fingerprint, policy, Capability, approval, budget, lease/claim, idempotency, cancellation, observer, terminal proof, or start Project sequence on this root.
- Require one admission-authority child. `effect_project_command_authorities` is valid only in `slopstop.db` and references the exact canonical command receipt, creation Project sequence, and Writer generation. `effect_storage_operation_authorities` is valid only for a Storage-operation subject in `application.db` and references the exact `StorageOperationId`, immutable request fingerprint, external operation-journal `requested` record and ordinal, and application operation revision used for compare-and-set. Neither child has the other's fields.
- Require exactly one top-level subject child matching `EffectSubjectKind`. A `run-worker` subject requires exactly one target child and one workspace-binding child. A `project-operation` subject requires exactly one `artifact-removal` or `storage-operation` child matching `ProjectOperationKind`. An `integration` subject has its own one-to-one child. Checks plus same-database composite foreign keys prove Project, Run where applicable, owner operation, subject scope, and target identity; prohibited-arm columns do not exist.
- Require `effect_run_targets`, `effect_waypoint_parent_targets`, and `effect_worker_targets` to carry only the exact owner fields listed in the closed-subject contract. The available pre-boundary owner request is immutable at intent; a later Model attempt, Tool invocation, Process job, or process-start identity links through the corresponding observation without changing the subject.
- Bind every `effect_run_worker_subjects` row to one Evidence scope belonging to the same Run. A `run-workspace` binding accepts the exact Run-workspace or Task-workspace scope and fingerprint selected by that binding. An `effect_no_workspace_bindings` row instead requires the Run-workspace scope used by `(project_id, run_id, run_workspace_evidence_scope_id)` Recovery authority, prohibits an Evidence-scope fingerprint and repository resource, and records only its closed no-workspace reason. This scope partitions current authority; it is not evidence that the operation read or changed repository state.
- Bind `effect_project_operation_subjects` one-to-one to a `project-operation` Evidence scope. The Artifact-removal child references the exact Artifact, Artifact Evidence scope, expected Artifact-state version, accepted retention decision, and Artifact store. The Storage-operation root references the exact ADR 0005 operation, Storage identity, operation kind, and external journal and requires exactly one matching backup, export, migration, restore, import, runtime-reset, or delete child with only the fields listed in the closed nested union. Bind `effect_integration_subjects` to the exact Integration attempt, Candidate identity/version/scope/fingerprint, Integration target, Repository resource, and target fingerprint.
- Make `effect_storage_delete_subjects` one-to-one with its `effect_storage_operation_subjects` parent. Store the exact deletion-tombstone identity and no source-generation set, target-generation, path, or nullable generation columns on that row. Key `effect_storage_delete_generation_members` by `(project_id, effect_id, member_position)`, make `(project_id, effect_id, storage_generation_id)` unique, and use composite foreign keys to prove that every member belongs to the same Storage and delete operation. The intent transaction rejects zero members, and opening integrity checks report a persisted zero-member delete as broken. Exactly one applies to the delete subject arm; one-or-more applies to its generation members.
- Do not create cross-database foreign keys or pretend that one SQLite transaction covers both databases. The Storage-operation partition records exact manifest, Storage, generation, database-lineage, schema-head, and operation-step identities from `application.db`; before start, the coordinator validates matching `storage_identity` and Project waterline from `slopstop.db` when readable. After a crash or destructive step, the external operation journal remains the recoverable authority even when the Project database is absent. A later Project-database observation is appended as Evidence, never backfilled as an atomic cross-database write.
- Key declaration classes and scopes by Effect plus non-negative position. Require at least one class, at least one scope for every class, unique class-and-scope canonical encodings, and exact agreement with the final authorized `DeclaredEffectSet`. Every Storage-operation Effect has exactly one `project-storage` class row and matching `effect_storage_declaration_scopes` child that references its exact `StorageOperationId`; no other subject may use that class or child. Key resource rows by Effect and position, store one closed key/access kind, and reject duplicates after canonical normalization.
- Give every Storage resource row exactly one matching typed child selected by its key kind. The registry, operation, generation, snapshot, backup, export, import-source, and deletion-tombstone children reference their exact logical `application.db` identities through same-Storage composite foreign keys and reconstruct exactly the canonical key encodings owned above. Operation-arm checks require the exact key combination specified by the `project-storage` declaration and reject missing, duplicate, extra, or incompatible rows. These children contain no `storage_locations` identity, path, URI, drive name, or other machine-local locator.
- Bind every declared scope needing state authority to one exact `effect_before_fingerprint_requirements` row. Run-workspace and Task-workspace scopes reference their accepted `EvidenceScopeFingerprintId`; Artifact removal additionally references its expected `ArtifactStateVersionId`; Integration references Candidate and target fingerprints; Storage operations reference the generation manifests required by their operation arm. A declaration cannot hide a before fingerprint in JSON or infer it at dispatch.
- Require one `effect_authority_bindings` row with exact policy owner/version and Capability/version. Require approval and budget children when the selected subject, class, or policy says they apply, and prohibit them otherwise. Their absence is a declared canonical value, not a nullable ambiguous payload.
- Require one coordination root with exactly one `mutation-lease`, `read-claim`, or `none` child. Lease and claim children reference the exact ADR 0008 authority and matching Run-workspace resource; `none` carries no lease or claim field and is rejected for a declared mutation that requires one.
- Require one remote-idempotency root with exactly one `provider-key` or `none` child. The provider child references the exact external-service resource and stores the provider idempotency key fingerprint or stable remote request key, never a secret. `none` is rejected when the adapter's declared retry contract requires remote lookup or continuation.
- Require one cancellation root and exactly one closed child. `unsupported` records only its stable reason and prohibits a request Capability. `request-only` records the exact cancellation Capability/version, request shape, and bound but grants no acknowledgement or disappearance proof. `request-and-observe` additionally records the exact acknowledgement/continuity observer version and required terminal observation roles. No arm may claim that cancellation itself proves the Effect outcome.
- Require one observer requirement per declared class/scope and every required terminal-proof role as relational rows. Their versions, time/size bounds, source authority, and required positive or negative proof participate in the declaration hash. Cancellation support, observer scope, or terminal sufficiency cannot be widened by an adapter after intent.
- Make Effect identity, all subject, admission-authority, and declaration children, and the `intent` Journal fact insert-only. No update or delete may change an admitted declaration. A correction or retry creates another Effect linked to the earlier one.
- Key `recovery_journals` by `(project_id, recovery_journal_id)` and make `(project_id, effect_id)` unique. Key records by `(project_id, recovery_journal_id, fact_ordinal)` and make each `(project_id, recovery_journal_record_id)` unique. Store the closed fact kind on the root and require exactly one matching typed fact child.
- Use partial unique indexes for one `intent` and one `started` fact per Effect. A composite foreign key from every fact child proves same Project, Journal, Effect, record kind, declaration hash, and source owner. Dispatch, terminal, fingerprint, cancellation-observation, and reconciliation facts require `started`; cancellation request may follow `intent` without start and then permanently prohibits start.
- Require the first post-`started` Journal record to be the `reconciliation-observed` fact for the unique `started-before-boundary` sequence observation. Require the first accepted Effect decision and current version after `started` to evaluate only that observation as `EFFECT_STARTED_UNSETTLED`. Every owner-specific pre-boundary record and every dispatch fact references that accepted decision/version and has a strictly later owner-partition order. For `artifact-removal`, the `ARTIFACT_REMOVAL_STARTED` observation is that owner record, and byte dispatch additionally references the later accepted Artifact-state decision/version and matching `artifact_state_current_evaluations` row. The coordinator rejects boundary crossing when any required row or reference is absent, stale, rejected, or broken.
- Make source observation identity unique within its adapter/version namespace so delivery retries return the original fact instead of duplicating history. Record the partition's Project sequence or Storage operation-journal ordinal plus the record ordinal separately from source-observed time.
- Key `effect_observations` by `(project_id, effect_observation_id)` with one unique Evidence entry and exact Effect, declaration hash, Evidence scope, observer identity/version, completeness, and source set. Require exactly one typed observation child. Non-sequence observations reference an exact producer attempt; deterministic sequence observations instead reference the exact coordinator command receipt or external Storage-operation observation record. An `effect_sequence_observations` child references exact Journal intent/start facts and role-applicable owner-boundary records and uses the closed fact roles `intent-not-started`, `started-before-boundary`, `boundary-continuity`, or `owner-terminal-sequence`; `started-before-boundary` prohibits an owner-boundary reference and proves its absence by owner-partition order. Sequence observations report sequencing only and carry no Effect verdict. Every other typed child must match one declared effect class. Multi-class reconciliation uses several observations and one evaluation rather than an untyped combined payload.
- Require each Effect reconciliation evaluation to reference a non-empty ordered set of exact Effect-observation Evidence entries through `evidence_entry_dependencies`. A decision decides only its exact evaluation. The pending-observation query therefore anti-joins observations through evaluation dependencies to decisions; an unused observation remains an explicit blocker until a later evaluation is accepted or rejected against it.
- Enforce class-specific references: workspace and Git observations use the exact Run workspace or Integration target selected by the subject, its resource, Evidence scope, and requested/current fingerprints; local Artifact observations use an exact Artifact-state version; `project-storage` observations use the exact Storage operation, external journal ordinal, registry revision, relevant generation manifests, delete-generation membership, Project snapshot/package identities, operation steps, and tombstone selected by the declaration; process observations use one Process job and process-start identity; external observations use exact service/account/region/request or resource identity; credential observations use a credential reference and never a value.
- Key `effect_current_evaluations` exactly as ADR 0010 requires by `(project_id, evidence_scope_id, effect_id)`. Composite foreign keys prove that current evaluation, accepted decision, Effect, declaration hash, scope, fingerprints, evaluator version/hash, Project, and verdict agree. Current advancement and its newly accepted decision remain one transaction.
- Key attempt links by `(project_id, source_effect_id, link_kind, target_effect_id)` with closed kinds `retry-of` and `compensates`. The source must have an earlier order in the same owner partition than the target: Project sequence in `slopstop.db` or Storage operation-journal ordinal in `application.db`. Reject cross-partition links, self-links, duplicate targets, and cycles. A retry target references exactly one `effect_retry_authorizations` row and a compensation target references its approving project command or Storage-operation action.
- Key retry authorization by `(project_id, effect_retry_authorization_id)`, make the new Effect unique, and reference exact source Effect current-evaluation version, accepted Effect decision, expected declaration hash, fresh project command receipt or Storage-operation continuation record, before fingerprint, policy, Capability, budget, and coordination authority. Require a matching subject-specific retry-authority child: Run Recovery current evaluation and decision for `run-worker`, exact Artifact or Storage operation state for `project-operation`, or exact Integration attempt/applicability state for `integration`. The transaction rechecks every selected current pointer.
- Key abandonment by Effect and its exact project command receipt or Storage-operation action record. Store actor, reason, scope, policy, retained blockers, and time. Add no foreign key from abandonment to current Effect or Recovery decision that could imply acceptance or change current authority.
- Keep machine-local paths, raw environment values, credential values, source text, prompts, model output, and provider-private secrets outside these rows and transmitted diagnostics. Use bounded Artifacts and redacted installation-local observations where exact diagnosis requires content.

- Index Effect subject children by Run, Worker or Waypoint parent, Project-operation kind and owner identity, Integration attempt, Run workspace when present, Evidence scope, admitting receipt/request record, declaration class, and partition creation order. Index `started` Journal facts by Project sequence in `slopstop.db` or operation-journal ordinal in the external Storage partition. Index resource keys by `(project_id, resource_kind, canonical_resource_key, access_kind, effect_id)` and join them to both pending Journal/observation blockers and current Effect verdict for conflict admission.
- Index Journal facts by Effect and ordinal, kind and owner-partition order, source owner identity, Process job, Model attempt, Tool invocation, Artifact/Storage operation, Integration attempt, fingerprint, Artifact, remote request identity, provider idempotency key, and cancellation request. Keep partial indexes for `intent`, `started`, and unresolved terminal-proof roles.
- Index typed Effect observations by Effect and descending owner-partition order, observer identity/version, producer attempt or coordinator source, Run-workspace fingerprint, Process job, Artifact/Storage state, Git ref, remote request/idempotency identity, and credential reference. Index current Effect rows by verdict and `current_evaluation_entry_id` in addition to their exact primary key.
- Index retry, compensation, and abandonment records in both source-to-target and target-to-source directions. Index Safety proofs by Effect, Run, Run workspace, and checkpoint consumer.

Startup and recovery must support these direct indexed queries without replaying generic events or selecting the latest timestamp:

| Recovery query | Direct predicate and use |
| --- | --- |

Artifact removal inserts a separate accepted `ARTIFACT_REMOVAL_STARTED` decision/current transaction between its observation and byte deletion. Terminal observation and later terminal decision/current transactions follow the physical boundary, then the subject-owner transition. | Blocked operations | Unresolved Effects block conflicting dispatch, lease release, checkpoints, stop/retry/replacement, completion, affected Candidate/Integration actions, discard safety, and cleanup while preserving unrelated scopes. |

## Consequences

- One stable identity and declaration let Process jobs, provider attempts, files, Git, Artifacts, credentials, remote systems, and Integration attempts tell one attributable story without sharing state authority.
- Write-ahead intent and start plus permanently consumed identities prefer visible uncertainty over duplicate effects. This may require user recovery when no observer can prove a remote result.
- Typed resource keys preserve useful parallelism while preventing separate worktrees from pretending shared Git, cache, credential, or service resources are isolated.
- Typed observers remain small and replaceable because Evidence owns evaluation and current truth. New effect classes require an explicit declaration class, resource-key shape, observation schema, sufficiency rule, and migration rather than a generic plugin verdict.
- Compensation and abandonment remain honest. The system can stop or remediate work without rewriting history or treating accepted risk as successful recovery.
- Concrete tables and direct anti-join queries add schema volume, but they make crash windows, unresolved effects, retry authority, and broken recovery directly queryable without event replay.
