# ADR 0009: Provider-Neutral Agent Runtime And Turn Contracts

- Status: Accepted
- Date: 2026-08-26
- Decision owners: Pedro Mesquita

## Context

ADR 0007 makes Execution the owner of Run and Worker transitions and leaves exact AgentRuntime invocation and result schemas to a later decision. ADR 0008 makes the deterministic Application coordinator the sole process and committed-action authority, while keeping model and tool invocation records outside Process-job state. The remaining boundary must let one Waypoint parent and several bounded Workers use a deterministic test runtime, a selected provider, and optionally Mastra without allowing provider sessions, callbacks, retries, or storage to become a second execution authority.

The runtime must also preserve exact prompt and Invocation context record provenance, role-specific visible tools, typed retrieval, budget and model policy, Run pause and cancellation, Worker stop, recovery after interruption, and attributed output and usage. Parallel Workers cannot share an opaque provider loop because each Worker has its own task, policy, workspace inputs, budget, and durable lifecycle, while the Waypoint parent alone owns logical fan-out and fan-in.

## Decisions

### Authority And Runtime Boundary

- Define the project-owned `AgentRuntime` as an Execution port implemented in the harness. Execution passes it one policy-admitted immutable Sealed Invocation, and provider or optional runtime adapters emit normalized attributed observations. Execution owns the durable invocation and observation records; adapters expose no session or state objects to kernel, protocol, desktop, or canonical state.
- Use an Execution-owned internal `Turn Machine` to sequence Waypoint parent and Worker Sealed Invocations, admitted provider-dispatch Model attempts, Tool invocations, Control requests, and continuation decisions. It is an in-memory mechanism reconstructed from durable records, not a new aggregate, status family, event authority, or persistence owner.
- Keep the Worker aggregate as the durable state authority for each Worker attempt under ADR 0007. Only validated Execution commands may move Worker lifecycle. Waypoint parent availability remains derived as ADR 0007 requires; neither a Turn Machine state nor an adapter callback may replace it.
- Keep the deterministic Application coordinator as scheduling, policy, budget, command-settlement, and dispatch authority. A provider, optional runtime, or tool adapter owns no execution state or canonical authority. Its normalized attributed observations report boundary facts or proposals until Execution validates and records them.
- Permit Mastra as the first optional runtime adapter only behind this port and only with its first exercised behavior. Mastra threads, sessions, workflow state, callbacks, retries, and `mastra.db` remain adapter-private and disposable from the perspective of canonical execution truth.

### Turn Sequencing

- Give the Waypoint parent and every Worker attempt an independent, non-negative sequence of admitted provider-dispatch Model attempts. A prepared Sealed Invocation carries the expected next sequence without consuming it. Only a command- and policy-admitted provider dispatch allocates that sequence to a durable Model attempt, uniquely within the exact Waypoint parent or Worker identity.
- Let one Turn Machine drive only one Waypoint parent or Worker sequence. It may inspect durable Run, Worker, policy, budget, Invocation context record, Evidence, Control-request, Tool invocation, Process-job, and recovery records, but it cannot persist a competing current-turn row or infer authority from adapter memory.
- Follow the provider-neutral cycle: establish current authority, compile the exact prompt and Invocation context record, prepare and seal the candidate invocation, settle its dispatch command, and stop without a Model attempt when command or policy admission rejects it. For an admitted dispatch, persist and flush Recovery Journal intent and `started`, create and flush one Model attempt referencing the exact admitted seal, and only then cross the adapter boundary. Record normalized attributed observations and usage, validate any output or tool proposal, and decide whether another candidate may be prepared.
- Treat tool execution, canonical commands, and model invocation as separate steps. A model tool call is a proposal between Model attempts; the Turn Machine cannot execute it directly or treat it as a successful Worker result.

### Sealed Invocation

- Identify every immutable candidate with a `SealedInvocationId`. Execution may prepare and reject a Sealed Invocation during command or policy admission before any provider dispatch or Model attempt exists. Every admitted provider-dispatch Model attempt references exactly one admitted Sealed Invocation, while a Sealed Invocation references zero or one Model attempt. Seal a versioned canonical encoding and content hash; any changed input requires a new candidate.
- Represent the target as a discriminated union. A Waypoint parent invocation pins `RunId`, `ParentId`, and its coordination purpose. A Worker invocation pins `RunId`, `WorkerId`, the exact `DelegationTaskId`, and the task's accepted Delegation-plan revision. An absent task on a Waypoint parent candidate is explicit and can never be mistaken for a Worker invocation.
- Pin these exact identity and authority inputs: Project, Run, target, per-target turn sequence, Action version, Behavior Contract, Test Contract, Completion Contract expectations, Delegation-plan revision, Run policy epoch, applicable approvals and Control requests, Capability versions, and causation records.
- Pin these exact workspace and result inputs: Run workspace, physical-resource identity when applicable, accepted Workspace fingerprint waterline, Evidence and prior Worker-result references, and immutable artifact hashes. Use an explicit `no-workspace-input` variant where no workspace observation is authorized. Never use a machine-local path as portable identity.
- Pin these exact prompt and context inputs: prompt compiler and role-instruction versions, prompt hash, one immutable `InvocationContextRecordId`, its deterministic output hash, and exact artifact hashes referenced by that record. The Sealed Invocation does not copy or redefine the Invocation context record.
- Pin these exact tool and model inputs: role-specific visible-tool identities, versions and schema hashes, tool and effect policy, concrete provider and model, model settings, provider-adapter version, optional runtime-adapter version, and the exact versioned adapter capability report used to prove representability.
- Pin these exact budget inputs without choosing numeric defaults in this decision: budget scope and policy version, approved ceilings, reservation or allowance for this attempt, consumed and pending usage waterlines, and limit units for model output, model usage, tool calls, elapsed time, and cost where the selected provider can account for them.
- Pin the expected normalized result schema, completion expectations, output bounds, and control boundary. Store large prompt and provider-input details as immutable local artifacts referenced by the Sealed Invocation; store output details as separate attributed result artifacts. Keep identities, sizes, hashes, media types, and provenance without duplicating Invocation context record authority.

### Invocation Context And Resume Reconstruction

- Make Execution the sole owner of immutable Invocation context records for Waypoint-parent and Worker provider candidates. A Conversation Context record remains Conversation-owned, links to an exact response through `responseMessageId`, and may link to provider attribution for inspection; it is never reused as an Invocation context record or provider input contract.
- Give every Invocation context record an opaque `InvocationContextRecordId`, exact Project, Run, target union, expected Model-attempt sequence, Delegation task when applicable, policy epoch, prompt compiler and role-instruction versions, provider/model profile, tokenizer identity/version, creation command receipt, canonical encoding version, and deterministic output hash. A changed source decision, order, transformation, token count, delivery mode, or artifact creates a new record.
- Persist ordered source entries for every included and excluded prompt source. Each entry records source kind and stable identity, source artifact and hash, inclusion state, stable inclusion or exclusion reason, trust classification, allowed scope, exact token contribution under the pinned tokenizer, normalized provider delivery mode, order, and every transformation reference. Excluded entries record zero delivered tokens while preserving the measured candidate contribution separately.
- Use project-owned normalized provider delivery modes such as instruction, user-content, tool-definition, tool-result, and provider-cache reference. The provider adapter may translate their wire representation only through its pinned capability report; it cannot change source content, order, inclusion, role, scope, or semantics invisibly.
- Persist typed retrieval by exact Tool invocation, request/result schema versions, authority and source scope, ordered returned identities, Workspace fingerprints, trust and freshness classifications, omissions, truncation, and result artifact hash. Missing, stale, unauthorized, truncated, empty, failed, and broken remain distinct.
- Persist the recent-turn slice by exact Waypoint-parent or Worker sequence range, message, Model-attempt, Tool-invocation, result-artifact identities and hashes, inclusion decisions, and token contributions. It is bounded input data, not an unbounded provider thread, and parallel Workers never share a turn cursor or opaque session memory.
- Persist each lossy compaction with exact ordered input identities and hashes, exclusions, compiler or model identity, transformation version, output artifact and hash, trust effect, and token contribution before and after compaction. Compaction never rewrites prior messages, attempts, invocations, or source records and never inherits source trust automatically.
- Treat deterministic local compaction as a versioned local transformation with no Model attempt. Treat any model-based compaction as a normal provider operation: prepare a specialized Invocation context record with purpose `context-compaction` over the exact uncompacted source artifacts, then admit a Sealed Invocation through the normal Command ID, policy, Capability, budget, Recovery Journal, pre-boundary Model-attempt, observation, usage, and recovery contracts. The compaction output is an attributed untrusted artifact that only a later Invocation context record may include after validation; it is never inserted into the context record that invoked it.
- Prohibit recursive or unreported model compaction. A `context-compaction` invocation cannot request another compaction, call a provider through a transformation helper, inherit hidden runtime memory, or bypass normal provider conformance. Failure, unavailability, timeout, cancellation, and uncertainty remain ordinary attributed outcomes and never degrade to empty compacted context.
- Persist every remaining transformation as an ordered immutable step with source, reason, version, input and output artifacts/hashes, and trust/scope effect. Compute the Invocation context record's deterministic output hash over the canonical encoding of all ordered source decisions, delivery modes, transformations, retrievals, recent-turn slices, compactions, final artifacts, and compiler/tokenizer versions.
- Compile prompts inside Execution from this exact bounded Invocation context record. Provider or runtime default prompts, memory injection, implicit tools, hidden system instructions, and unrecorded provider cache content are prohibited.
- Expose an inspectable approval and diagnostic projection containing the final compiled prompt identity/hash, ordered inclusion and exclusion decisions with reasons, token contributions, provider delivery modes, transformation chain, and exact artifact links. A user correction creates a new Invocation context record and Sealed Invocation; it never edits an accepted record.
- Reconstruct resumed context from the Resume capsule and durable SlopStop-owned Sealed Invocation, Invocation context record, Model attempt, Tool invocation, Process-job, Evidence, budget, and recovery records. Adapter session storage may accelerate reconstruction but can never determine what happened or what may run next.
- Block or require recovery when a required Invocation context record, source reason, token contribution, delivery mode, artifact, hash, Tool result, usage waterline, or terminal observation is unavailable or inconsistent. Never substitute a Conversation Context record, fresh provider memory, or an empty thread for missing durable invocation inputs.

### Role-Specific Visible Tools

- Build the visible-tool portfolio for each Sealed Invocation from the exact target role, accepted Delegation plan, policy epoch, Capability versions, approvals, workspace mode, and adapter capability report. The Waypoint parent receives only coordination-safe tools; a Worker receives only the tools needed for its exact task. No adapter-owned built-in tool is visible implicitly.
- Present tools through project-owned provider-neutral schemas with stable identities, versions, argument and result schemas, effect classification, approval requirement, and output bounds. Provider vocabulary and wire formats remain inside the provider adapter.
- Require the adapter capability report to prove that the exact provider and model can represent every visible schema and result contract before dispatch admission. Unsupported or lossy representation is a command or policy rejection of the Sealed Invocation and creates no Model attempt.
- Expand a role's visible-tool portfolio only in a later Sealed Invocation under an exact approved plan or policy epoch and a versioned capability report. A running invocation is never amended in place.

### Tool Invocation And Typed Retrieval

- Allocate one durable `ToolInvocationId` when Execution normalizes one complete model-visible tool proposal. Bind it to Project, Run, exact Waypoint parent or Worker, originating Model attempt and Sealed Invocation, provider tool-call identity when available, exact tool and Capability versions, schema hashes, immutable proposed-argument artifact and hash, policy epoch, workspace and fingerprint waterline, budget, and causation.
- Treat every proposed tool name and argument as untrusted model output. Before any rewrite, run and persist one immutable proposed-argument validation against the exact proposed artifact and hash. It records tool visibility and target role, Capability and input-schema versions and verdicts, proposed effect classification, declared scope, risk class, required approval and matching approval identity or absence, policy verdict, workspace and Evidence freshness, budget admission, Control-request state, ordered failure codes, and complete accepted or rejected result.
- Permit rewriting only after that proposed validation is accepted, and only through explicit project-owned extension, policy, or user-approved rewriting. Persist one ordered rewrite record for each step with rewrite source and stable reason, authorizing rule or actor, input artifact/hash, output artifact/hash, original and resulting target/scope, original and resulting effect classification, original and resulting risk classification, and whether fresh approval is required. A rejected proposed validation ends authorization and cannot be rewritten into acceptance.
- Whether arguments remain unchanged or are rewritten, normalize the selected output into one immutable final authorized argument artifact and hash, then persist a new final-argument validation that reruns the complete proposed validation contract: visibility, role, Capability, schema, effect classification, declared scope, risk class, required approval, policy, workspace and Evidence freshness, budget, and Control-request state. A material expansion of target, command, permission, network, configuration, dependency, Git behavior, credential access, cost, or side effect requires fresh approval against the final argument hash; an equal-or-lower-risk rewrite may proceed without fresh approval only when the existing approval explicitly permits that final scope.
- Bind the dispatch Command ID and command fingerprint, `DeclaredEffectSet`, Recovery Journal intent, provider idempotency key, and any Process-job invocation to the final authorized argument artifact and hash, never the proposed artifact. Preserve both artifacts even when no rewrite occurred.
- Prohibit provider, runtime-adapter, provider-adapter, tool-adapter, SDK, or Process-job code from semantically rewriting final authorized arguments. Only recorded transport encoding is allowed. A wire request whose decoded semantic arguments do not hash to the final authorized artifact is `TOOL_ARGUMENT_INTEGRITY_MISMATCH`, does not start or continue the effect, closes that Tool invocation, and requires recovery if dispatch may already have crossed the boundary.
- Derive Tool-invocation lifecycle from its durable proposal, command settlement, and ordered Execution-owned observations rather than a new domain aggregate. Use `proposed -> policy-rejected | authorized -> started -> terminal-observed | interrupted`; `policy-rejected` is a terminal command outcome, while `terminal-observed` and `interrupted` are terminal transport outcomes. A rejected proposal never starts an effect.
- Keep terminal transport observation distinct from schema-valid result, semantic success, and reconciled effect success. An adapter return, process exit, or zero exit code cannot complete a Worker, accept Evidence, prove an effect, or authorize another turn by itself.
- Use a discriminated tool contract with `typed-retrieval` and `effect-request` variants. One invocation cannot change variant after proposal, and no tool may hide an effect behind a retrieval declaration.
- Keep `typed-retrieval` read-only. Bind its request to exact authority scope, source kinds, trust policy, Invocation context purpose, Workspace fingerprint, result schema, result limit, and budget; it may return only ordered typed references, freshness and trust classifications, omissions, truncation, and immutable result artifacts. If an implementation can mutate state, launch a process, access credentials, call an external service, or incur external cost, it is an `effect-request`, not typed retrieval.
- Keep each typed-retrieval result unusable after its Workspace fingerprint, trust, or source authority becomes stale. `completed`, `empty`, `truncated`, `stale`, `unauthorized`, `failed`, and `broken` observations remain distinct. Empty is valid only from a completed authorized query, never from failure or missing input.
- Route every authorized `effect-request` through the deterministic Application coordinator and ADR 0008's Capability, Process-job where applicable, mutation-lease, Declared-effect, Recovery-Journal, and reconciliation contracts. The adapter and Turn Machine never execute an effect as a side channel.
- Reference an accepted Tool result in the next Invocation context record by exact `ToolInvocationId`, terminal and semantic classifications, result artifact and hash, Workspace fingerprint, effect-reconciliation result when applicable, and omissions. A later Sealed Invocation receives that Invocation context record; provider or runtime session memory cannot inject an unrecorded Tool result.

### Provider And Optional Runtime Adapters

- Make the provider adapter a translation boundary from one admitted Sealed Invocation to one concrete provider request and from provider events to normalized attributed observations. An observation is an immutable provider-neutral report bound to the exact invocation, adapter version, source event identity, sequence, time, and payload hash. Execution validates and persists it; the adapter owns no durable observation state.
- Permit an optional runtime adapter to implement provider calling, streaming, or local observability, but require the same Sealed Invocation and normalized attributed-observation contract as the direct provider path and deterministic test path.
- Prohibit unreported model calls, hidden agent loops, autonomous retries, provider or model fallback, hidden fan-out, and hidden fan-in. Each admitted provider-dispatch attempt has one durable Model attempt and one Sealed Invocation before adapter-boundary crossing. A transport replay remains the same request only when an adapter can prove the same provider request identity or idempotency contract; otherwise a validated continuation creates a new attempt.
- Reject before dispatch through the dispatch command and policy settlement when the versioned capability report cannot represent the exact prompt, tool, model, output, budget, or control contract. That rejection is not an adapter observation and creates no Model attempt. Never remove tools, weaken schemas, change models, widen budgets, or discard context to make an adapter call succeed.
- Keep provider request identities and adapter-private payloads as attributed metadata only. They help reconciliation and diagnosis but cannot identify canonical Run, Worker, task, Invocation context, Workspace, or policy state.

### Attributed Output And Usage

- Use a closed versioned provider-outcome vocabulary after adapter-boundary crossing that includes `provider-accepted`, `provider-rejected`, `provider-failed`, `provider-unavailable`, `model-unavailable`, `provider-timeout`, `cancellation-acknowledged`, `cancellation-confirmed`, `provider-interrupted`, and `provider-terminal`, plus bounded stream, tool-proposal, output, refusal, content-filter, and malformed-output observations. `provider-rejected` is generic provider rejection and `provider-failed` is generic provider failure. `provider-unavailable` means the selected provider endpoint, account, region, or service cannot accept the request; `model-unavailable` means the exact selected model cannot be resolved or used at the recorded resolution source. The two availability kinds are distinct from rejection and failure.
- Treat a provider-side `provider-unavailable` or `model-unavailable` observation as `provider-invocation-observed`, then submit only the matching `RecordWorkerProviderUnavailable`, `RecordWorkerModelUnavailable`, `RecordWaypointParentProviderUnavailable`, or `RecordWaypointParentModelUnavailable` command for the exact target. Generic rejection or failure follows normal attempt failure and retry/recovery policy and cannot enter model recovery without a new explicit closed availability observation. Availability discovered before adapter crossing remains a command or policy rejection and creates no Model attempt or adapter observation.
- Record provider request identity when available, usage, terminal outcome, and every normalized observation append-only against the exact Model attempt. Command and policy admission or rejection remain separate command settlements and create no Model attempt. Stream progress remains provisional and cannot move Worker state.
- Store model text, structured output, proposed tool calls, refusal detail, finish reason, provider error, and bounded raw provider evidence as immutable attributed artifacts. Preserve exact Sealed Invocation, Model attempt, provider, model, adapter versions, times, and hashes on every output reference.
- Record usage as attributed observations with the provider-reported input, output, cached, reasoning, tool, time, or cost units that are actually available. Preserve provider units and normalization version. `reported`, `partial`, `unsupported`, `missing`, and `uncertain` usage are distinct; absent provider data is never reported as zero.
- Derive provider-neutral loop-health observations from an exact bounded Waypoint parent or Worker sequence window and its input hashes. Version the evaluator and distinguish progress, repeated or no-progress behavior, malformed-output pressure, budget pressure, provider instability, and unknown input. Loop health may propose a block, stop, retry, or human decision but can never move Worker state directly.
- Let validated budget accounting consume usage observations, but never let the adapter debit, extend, or reset canonical budgets directly. Late output or usage remains attached to its original Model attempt and cannot silently authorize another turn or complete a Worker.
- Give every Model attempt one current boundary classification derived from append-only observations: `proven-not-started` requires durable proof that the adapter boundary was not crossed or that no request reached the provider; `provider-invocation-observed` requires a provider request identity, response, generic rejection, generic failure, usage, or equivalent provider-side evidence; `invocation-uncertain` means the boundary may have been crossed but neither invocation nor absence is proven. These classifications do not report semantic success. Never replay `provider-invocation-observed` or `invocation-uncertain` automatically or degrade either to a clean provider failure.

### Model And Tool Effect Identity And Recovery

- Treat every admitted provider dispatch as an `external-service` and budget effect. Before it starts, bind the admitted Sealed Invocation and dispatch command to the exact Capability version, policy epoch, `CommandId`, command fingerprint, Declared effect set, budget authority and reservation, and required `RecoveryJournalEntryId`. After `started` is durable, create and flush the Model attempt with those same references immediately before adapter-boundary crossing. Include credential access or any additional effect class explicitly; an empty or omitted effect declaration is invalid for a real provider call.
- Bind every authorized effectful Tool invocation to the same exact recovery identity: Capability version, policy epoch, Command ID, command fingerprint, Declared effect set, Recovery Journal entry, required mutation lease, before fingerprint, timeout, output policy, budget, and provider idempotency key when supported. A proven read-only typed retrieval is not an effect; it records an explicit `no-effect` classification and has no Recovery Journal reference. Any external call, cost, credential access, process, or mutation makes the invocation effectful.
- Apply canonical command idempotency before any model or Tool effect. An exact command retry returns the original settlement and existing identities. Reusing a Command ID with different content is `IDEMPOTENCY_CONFLICT`; it never dispatches a provider, adapter, tool, or process.
- Persist and flush the Recovery Journal intent before dispatch, persist and flush `started`, then create and flush the Model attempt or consume the Tool-invocation identity permanently, and only then cross the adapter or process boundary. The pre-boundary Model-attempt record is required because a crash after a possible adapter crossing may otherwise leave provider evidence, late output, usage, cost, and uncertainty without the exact seal, target, command, and recovery identity that owned the request. Never relaunch an identity whose effect reached `started` and never rely on an adapter's retry policy as proof of idempotency.
- Use provider or service idempotency keys where available without claiming exactly-once behavior. A transport retry belongs to the existing identity only when the remote system proves the same request identity and result; otherwise retry requires conclusive recovery plus a new Sealed Invocation or Tool invocation, Command ID, command fingerprint, Recovery Journal entry, budget decision, and before fingerprint where applicable.
- Reconcile crash windows conservatively. Policy or command rejection and intent without `started` have no Model attempt. Durable `started` without a Model attempt proves that the adapter boundary was not crossed under this sequence and settles the Journal effect as not started. A Model attempt followed by a recorded local abort before adapter crossing is `proven-not-started`; an attempt with provider-side evidence is `provider-invocation-observed`; an attempt that may have crossed without conclusive provider or absence evidence is `invocation-uncertain`. A known provider request without outcome must be observed or cancelled; a terminal transport result without complete output, usage, Tool result, effect observation, or after fingerprint remains uncertain; complete Journal and external evidence may reconstruct the missing terminal observation without replay.
- On startup, reconcile every nonterminal Model attempt, Tool invocation, provider request, effect record, and Journal entry before the Turn Machine admits more work. Preserve `proven-not-started`, `provider-invocation-observed`, `invocation-uncertain`, semantic failure, and reconciled effect success as separate classifications. Only validated Execution commands may use those classifications to move Worker state.

### Run Control, Worker Stop, And Model Recovery

- Define a portable provider turn boundary only when zero Model attempts and zero Tool invocations are in flight. Every admitted provider and Tool operation must have durable terminal or reconciled observations, output/result references, usage waterline, and Recovery-Journal classification. `invocation-uncertain` is no longer in flight but still disqualifies a Safe checkpoint until Evidence resolves it. These boundaries are provider- and runtime-neutral because SlopStop records reconstruct them rather than an adapter thread.
- Keep Run pause and cancellation under ADR 0007 and ADR 0008. A Run pause request closes all applicable Run dispatch immediately and reaches `paused` only after a Safe checkpoint proves zero in-flight Model attempts and Tool invocations, no active mutating Process job, and no uncertain effect. Run cancellation may request bounded in-flight cancellation and remains `cancel-requested` or `recovery-required` while any outcome is uncertain. This decision adds no Run `stopped` state.
- Make Worker stop a separate Worker-targeted Control request and lifecycle. `RequestWorkerStop` closes only that Worker's new Model, Tool, and Process-job dispatch immediately and stores an immutable warning-time effect snapshot. `ConfirmWorkerStopped` reaches terminal `stopped` only after ADR 0007's Worker stop checkpoint proves zero in-flight Model attempts and Tool invocations, no active owned work, no uncertain effect, accepted final Workspace fingerprint, and settled budget usage. Its final Evidence-backed classifications may refine warning-time uncertainty and do not have to equal the snapshot.
- Keep a stop-requested Worker and its task slot when uncertainty remains. Do not convert uncertainty to stopped, release the slot, create a retry or replacement, or interrupt unrelated Workers. If the Run enters `recovery-required`, `ApplyRunRecoveryReconciliation` must accept exact Evidence, remove only the resolved recovery condition, and recompute the complete next state and every blocker. Stopped-Worker Retry or Model change remains unavailable until the Run has left `recovery-required` and the recomputed state admits Worker dispatch.
- Emit a typed availability warning only from `provider-unavailable` or `model-unavailable` for the affected Waypoint parent or Worker. Preserve role, concrete provider/model, resolution source, reason, latest checkpoint, warning-time completed effects, warning-time uncertain effects, and available Retry, Model change, and Cancel actions. Cancel submits the existing `RequestRunCancellation` intent as a Run-targeted Control request. It never creates a Worker cancellation transition; changing or removing one task uses a Change request and approved replanning.
- For a stopped availability-affected Worker, explicit same-model Retry invokes `RetryStoppedWorkerModel`, revalidates the same approved concrete provider/model, requires a recovered and currently dispatchable Run, and creates a new Worker linked by `retry_of_worker_id` with the same Delegation task, fresh Invocation context record, and provider-recompiled Sealed Invocation. It never resumes the stopped Worker or reuses its provider request.
- Use the closed Model-change lifecycle `pending-approval -> approved -> applied`, `pending-approval -> rejected`, or pending/approved to `superseded`. `/model` and the graphical picker both invoke `SubmitModelChange`; `ApproveModelChange` or `RejectModelChange` records the attributed decision; approval creates an immutable approved Run profile revision and new policy epoch that are not current until apply. `SupersedeModelChange` closes stale or replaced intent. No lifecycle step calls a provider or selects a fallback.
- For a healthy Waypoint parent, `ApplyWaypointParentModelChange` requires the approved request and a portable boundary, then atomically activates its profile revision and policy epoch for future parent invocations and marks the request `applied`. Subsequently dispatched Workers without explicit overrides inherit the parent's then-current model at dispatch. Existing Workers, historical invocations, and explicit Worker model overrides remain unchanged.
- For a stopped Worker, only `ReplaceStoppedWorkerModel` may apply an approved Worker-targeted request. It requires the released slot, a recovered and dispatchable Run, and the request's approved profile revision and policy epoch, then creates a new Worker linked by `replaces_worker_id`, fresh Invocation context record, and provider-recompiled Sealed Invocation while marking the request `applied`. It never mutates or resumes the stopped Worker.
- When the Waypoint parent emits `provider-unavailable` or `model-unavailable`, invoke the matching ADR 0007 command, add only its matching availability condition, close Waypoint-parent and new-Worker dispatch, and keep or move the Run `blocked` with `PROVIDER_UNAVAILABLE`; do not stop, pause, cancel, or fail the Run automatically. Active Workers follow the policy fixed at that blocking sequence to finish their current bounded task or reach the next safe boundary, and their results queue durably without interpretation.
- `RecoverWaypointParentModel` consumes a successful same-model availability probe or an applied Waypoint-parent Model-change request and removes only the exact provider- or model-unavailable condition that evidence proves resolved. Any external availability probe is a normal attributed Capability effect with Command ID, Recovery Journal, result, and usage or cost, never an unreported model call. Recovery then recomputes every other blocker, recovery condition, pending control, profile and policy input. The Run remains `blocked` if any blocker remains and reaches `running` only when dispatch is otherwise legal; queued results drain only after dispatch reopens. Automatic fallback remains prohibited.
- Apply every provider, model, settings, prompt, Invocation context, tool, runtime, or budget change only to a new Sealed Invocation after the required approved revision or Run policy epoch. Never mutate an in-flight or historical invocation.
- Recover without replaying uncertain work. Reconcile an interrupted provider or Tool request from its Command ID and fingerprint, Recovery Journal, durable started observation, remote request identity where available, adapter evidence, output or result artifacts, usage, effect observations, Workspace fingerprints, and budget waterline. If certainty cannot be restored, preserve uncertainty and require an explicit validated continuation with new identities.
- Allow a different conforming provider or runtime adapter only at a proven portable boundary and under a newly sealed exact contract. Adapter replacement cannot reinterpret old results, inherit hidden session state, or bypass a pending Control request.

### Parallel Worker Coordination

- Give every parallel Worker its own Turn Machine instance, turn sequence, Sealed Invocations, Model attempts, context slices, visible tools, budget waterline, and adapter observations. Parallel execution never creates one shared runtime-owned agent loop.
- Keep logical Task-DAG fan-out, fan-in, and result synthesis with the Waypoint parent. Keep dependency readiness, concurrency and budget admission, dispatch, retry, and cancellation with the deterministic Application coordinator under approved Execution policy. No Worker, provider, model, or optional runtime may create, join, retry, cancel, or accept another Worker.
- Feed Worker results back to the Waypoint parent only as attributed, validated result, Evidence, Tool invocation, and artifact references in a later Waypoint-parent Invocation context record and Sealed Invocation. When the Waypoint parent is unavailable, retain those exact references in its durable result queue. The Waypoint parent's later interpretation remains a proposal until the owning command and Evidence boundaries accept it.
- Continue to apply Worker slots, Run-workspace resource coordination, mutation leases, and Process-job limits independently of model parallelism. Separate Turn Machines do not authorize concurrent mutation or bypass the approved Delegation plan.

### Physical Records

Execution completes ADR 0007's `model_attempts` family and adds these related owner records to `slopstop.db` under ADR 0006's Project-scoped identity, immutable-history, migration, and indexing rules:

| Invocation input | `sealed_invocations`, `sealed_invocation_visible_tools`, `sealed_invocation_budget_limits`, `sealed_invocation_artifacts` |

- Keep exact Project, Run, Waypoint parent or Worker, Delegation task, plan revision, policy epoch, ADR 0008 `run_workspaces` identity, Invocation context record and purpose, provider, model, adapter, budget, Capability, Command ID and fingerprint, Declared effect set, Recovery Journal, and contract references relational. AgentRuntime records never use ADR 0006 application `workspaces` as Run-workspace identity. Use versioned immutable JSON only for variable provider settings and provider-private details permitted by ADR 0006; do not index that JSON.
- Give each Model attempt exactly one admitted Sealed Invocation reference and enforce at most one Model attempt per Sealed Invocation. A policy- or command-rejected Sealed Invocation has no Model attempt and links to its command rejection settlement. Create and flush the Model attempt only after durable Recovery Journal `started` and before the adapter boundary. Make the admitted-dispatch sequence unique per Waypoint parent or Worker, store the seal encoding version and hash, and reject dispatch when recomputation does not match.
- Keep Model attempt and Tool invocation observations, outputs, results, and usage append-only and ordered. Derive Tool invocation lifecycle from those observations; add no generic current Tool status or second state authority. Large or streamed content remains in bounded local artifacts with immutable hashes and explicit truncation; no source, prompt, model output, secret, environment value, or full path enters Sentry.
- Reference one immutable Invocation context record from each Sealed Invocation and enforce that one record can be attached to at most one Sealed Invocation. Do not copy its source rows or use `conversation_context_records` or `responseMessageId` for Execution context composition. A Conversation Context record may reference provider attribution for inspection but remains a separate Conversation-owned response record.
- For `context-compaction`, make `invocation_context_compactions` reference the specialized input Invocation context record, Sealed Invocation, Model attempt when model-based, Command ID, Recovery Journal entry when model-based, usage, and output artifact. The output artifact may be referenced only by a later Invocation context record, preventing recursive ownership.
- Add no Turn-Machine, provider-session, runtime-thread, or framework-retry authority table. Adapter-private runtime persistence remains in `mastra.db`; SlopStop-owned records may retain attributed opaque adapter references without depending on them.

### Conformance And Portfolio Expansion

- Require every direct provider, deterministic test, and optional runtime adapter to pass one shared contract suite for seal verification; policy rejection without a Model attempt; pre-boundary Model-attempt persistence; all three boundary classifications; normalized-observation ownership; target isolation; Invocation context fidelity and deterministic hashing; source inclusion and exclusion reasons; token contributions; delivery modes; visible-tool fidelity; persisted proposed and final Tool-argument validation; Tool invocation lifecycle; typed retrieval separation; model-based `context-compaction` through the normal invocation path; completed output; tool-call proposal; refusal; malformed or partial output; same-model stopped-Worker retry; generic provider rejection; generic provider failure; `provider-unavailable`; `model-unavailable`; timeout; cancellation; effect recovery; Run cancellation; Worker stop; late output; interruption; explicit Worker model replacement; blocked Waypoint-parent recovery with unrelated blockers preserved; unsupported capabilities; usage absence; loop-health input fidelity; idempotency conflict; and restart reconstruction.
- Keep deterministic AgentRuntime and fake-tool outcomes as CI correctness gates. Before a selected provider/model or runtime feature expands the production tool portfolio, separately prove the exact pinned real-provider path with structured output; the proposed tool schema; argument rejection; persisted pre- and post-rewrite validation; typed retrieval; effect dispatch; terminal-versus-semantic result separation; refusal; same-model stopped-Worker retry; generic provider rejection; generic provider failure; `provider-unavailable`; `model-unavailable`; timeout; cancellation; effect recovery; usage reporting behavior; all three Model-attempt boundary classifications; recovery identity; and no secret or hidden fallback.

- Leave numeric turn, token, cost, timeout, retention, output, and concurrency defaults to measured Evidence and later policy decisions. This ADR fixes the exact inputs and authority boundaries, not their eventual default values.

## Consequences

- Deterministic, direct-provider, and Mastra-backed paths can be behaviorally compared at one project-owned boundary without importing framework sessions or provider concepts into canonical state.
- Exact Sealed Invocations, pre-boundary Model attempts, and Execution-owned attributed records make prompts, Invocation context records, Tool argument validations and rewrites, models, budgets, Run-workspace inputs, usage, and recovery inspectable, at the cost of more immutable records and artifact management.
- Portable turn boundaries allow Run pause and cancellation, Worker stop and replacement, Waypoint-parent model recovery, adapter replacement, and restart without trusting opaque provider memory, while preserving uncertainty when in-flight work cannot be reconciled.
- Independent Worker turn sequences preserve non-nesting attribution and safe parallelism; deterministic Waypoint parent fan-out and fan-in remain explicit rather than becoming hidden runtime behavior.
- Adapters lose some convenient autonomous loop, retry, memory, and fallback features. That restriction is intentional because convenience cannot outrank Worker authority, budget accounting, recovery, or failure visibility.
