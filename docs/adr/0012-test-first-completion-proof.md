# ADR 0012: Test-First Completion Proof

- Status: Accepted
- Date: 2026-08-26
- Decision owners: Pedro Mesquita

## Context

The accepted product requires test-first preferred as the default discipline for work SlopStop supervises in external Projects, exact baseline, Red, Green, review, Finding, and exception proof, and a stored Completion contract before a Run may complete. Ticket `#57` asks for the clause-level records and acceptance rules that make those claims inspectable without turning one product-domain discipline into a mandatory global pipeline. `AGENTS.md` separately governs development of SlopStop itself and continues to require strict red-green for every SlopStop behavior change; no product-domain Run exception weakens that repository rule.

ADR 0007 lets Execution complete a Run only from current Evidence completion authority. ADR 0010 already owns typed `test`, `completion`, `finding`, `finding-recheck`, `effect`, and `candidate-review` Evidence families, immutable history, exact current evaluations, explicit reruns, and reverse invalidation. This decision specializes those existing families. It does not create another ledger, another current-completion state, or a generic predicate language.

## Decisions

### Authority And Contract Ownership

- Keep Behavior, Test, and Completion contracts as separate canonical revisioned aggregates under the Application coordinator. A model or Worker may propose content, but only an accepted typed command creates a canonical revision.
- Make the Behavior contract the Waypoint-owned statement of observable intent. Each clause has a stable identity within one Behavior contract, an observable outcome, applicable public seam, limits and failure behavior where relevant, and a classification as behavior-changing or non-behavior work. A material change to intent creates a new Behavior-contract revision.
- Make the Test contract the canonical verification design for one exact Behavior-contract revision. It owns stable Test-check identities, exact approved command specifications, Capability versions, scope, expected semantics, clause coverage, proof phase, required artifacts and limits. A Test contract never owns a test result.
- Make the Completion contract the Waypoint-owned acceptance design for exact Behavior- and Test-contract revisions. It selects fixed contract-specific rule versions and declares every required proof obligation, exact Completion-subject class, Finding policy, effect policy, and risk-based review requirement. Human Completion acceptance is mandatory and cannot be disabled by a contract. A Completion contract never owns Evidence or Run state.
- Pin every Run policy epoch to exact accepted Behavior-, Test-, and Completion-contract revisions, one `RunDisciplineDecisionId`, and one Delegation-plan revision. Each later Run change classification pins the already-current epoch whose mutation phase it authorizes; the epoch does not own that classification. A later contract, profile, plan, discipline policy, or other policy revision does not change an active Run silently; an approved amendment creates the required new immutable records and epoch while historical references remain intact.
- Keep responsibilities separate. Canonical contracts define what must be proved; Execution enforces dispatch and mutation gates; Evidence observes and evaluates proof; the Application coordinator alone settles Run completion; Integration alone applies a Candidate.

### Clause And Obligation Model

- Use stable `BehaviorClauseId`, `TestCheckId`, and `CompletionObligationId` values. Reusing a stable child identity in a later revision means the semantic subject remains the same; a materially different subject gets a new identity and an explicit supersession link.
- Map each automated Test check to one or more exact Behavior clauses or to one exact non-behavior obligation. A check cannot claim wildcard coverage, and a contract cannot infer coverage from a filename, test name, command success, or code anchor alone.
- Use the closed v1 Completion-obligation kinds `test-first-behavior`, `tests-required-behavior`, `approved-alternative-proof`, `non-behavior-check`, `candidate-review`, `finding-disposition`, and `effect-reconciliation`. Each kind has a compiled evaluator implementation and fixed typed inputs; there is no expression tree, user-authored Boolean formula, scriptable predicate, or untyped rule payload.
- Require every Behavior clause in the pinned revision to appear in at least one Completion obligation. Require every Completion obligation to reference only clauses and checks from the exact pinned contract revisions. Duplicate clause-to-obligation rows are invalid.
- Treat clause coverage as proof only when the selected rule's typed Evidence requirements are satisfied. A row that merely links a clause to a test is traceability, not Completion Evidence.

### Development Discipline And Applicability

- Give every product-defined discipline a stable `DevelopmentDisciplinePolicyId` and every immutable semantics revision a `DevelopmentDisciplinePolicyVersionId`, version, content fingerprint, and exact obligation-replacement permissions. Use the accepted mode vocabulary `strict-tdd`, `test-first-preferred`, `tests-required`, and `exploration`; the mode name alone is not authority.
- Make the project-owned Development-discipline Policy component under the Application coordinator the sole writer of policy identities and immutable versions. The Application default decision and optional Project-profile override select policy versions, Execution enforces the decision referenced by the applicable Run policy epoch, and Evidence consumes that exact decision-version-epoch pair as typed dependencies. Models, Workers, contracts, and profiles cannot define or rewrite policy semantics.
- Let one append-only Application Development-discipline default decision supply the current fallback independently of the mutable Application profile. Let an accepted Project-profile revision contain zero or one Development-discipline override; absence inherits the current Application default and a later profile revision may add, replace, or remove the override.
- During initial Run preparation and every approved amendment, resolve the accepted Project-profile revision first: use its exact override when present, otherwise use the exact current Application default decision. Append an immutable ordered `RunDisciplineDecisionId` whenever the accepted plan, source arm, selected policy version, content fingerprint, or replacement permissions differ from the decision used by the prior applicable epoch. An unrelated new epoch may reference the prior decision. Never update or enforce uniqueness by Run.
- Make the applicable `run_policy_epochs` row the current authority pointer to the resolved Run discipline decision. Pin that exact decision-version-epoch pair into every applicable Sealed Invocation, Test-first Proof Chain, Completion evaluation, and Completion authorization. Prior epochs, decisions, invocations, Evidence, and authorizations retain their original pair.
- Use `RegisterDevelopmentDisciplinePolicyVersion` for packaged project-owned policy implementations and `SetApplicationDevelopmentDisciplineDefault` for the installation-local fallback. A Project override is accepted or removed only as the checked child of a new accepted Project-profile revision, not by an independent override command. `ApproveRunPreparation` and `ApproveRunAmendment` deterministically resolve discipline and atomically append any required Run decision plus a policy epoch that references it; `RecordRunDisciplineDecision` is not an independent current-pointer command.
- `SetApplicationDevelopmentDisciplineDefault` carries one `ApplicationCommandId`, normalized command fingerprint, expected current-selection version, exact policy identity/version/content fingerprint, and actor. An applied command atomically settles that command, appends the ordered Application decision, and compare-and-sets the singleton current selection. An exact retry returns the original settled outcome without appending; reuse with different content returns `IDEMPOTENCY_CONFLICT`; a stale expected version settles as rejected and changes no decision or selection. Project-profile and Run settlements use ADR 0006 canonical Command IDs, receipts, expected versions, Project sequence, and Writer fencing.
- `strict-tdd` requires baseline, distinct expected Red, Green, and final applicable Green for every behavior clause expressible at an approved automated public seam. `test-first-preferred` applies the same proof when the seam is meaningful. `tests-required` requires a registered baseline and final applicable Green but does not claim Red. `exploration` may complete only an eligible non-repository output and cannot authorize production behavior.
- Select independent review from the accepted risk recipe and exact Completion-contract obligation, not from discipline mode alone. Low-risk policy may allow one phase-constrained Worker to author tests, implement, refactor, and run deterministic final checks. When the risk recipe or Completion contract requires independent review, the production-mutating Worker cannot supply that review.
- Represent a proposed discipline exception and its immutable user decision separately. The exception pins one Run, Run discipline decision, policy epoch, plan revision, exact Completion obligations and Behavior clauses, missing seam, testability impact, proposed replacement obligations, alternative-proof rule, and expiry. The selected policy version must explicitly permit every proposed replacement. The exception row has no mutable status or supersession field.
- Use exception proposal-decision actions only `accept`, `reject`, and `request-changes`. Only `ApproveDisciplineException` with an exact user `accept` decision can make replacements applicable; `RejectDisciplineException` and `RequestDisciplineExceptionChanges` grant no proof authority.
- After exception approval, rejection, or supersession can change the effective obligations of a current Run, submit the attributed Execution command `ReevaluateRunDiscipline` with the expected Run version and condition identity, current epoch-decision pair, exact exception decision when applicable, and applicability-input fingerprint. It removes only a discipline condition proved resolved, closes dispatch when a new live condition appears, and reruns every blocker and pending-control check. It may select `ready` or `blocked` but never `running`, and it creates no plan, profile, discipline decision, exception, or epoch.
- `SupersedeDisciplineException` writes a separate append-only supersession record. It stores the exact predecessor exception, closed successor arm `replacement` or `none`, nullable successor exception required only for `replacement`, actor, required reason, command receipt, expected applicability-input fingerprint, and Project sequence. `replacement` links another immutable proposal and does not accept it implicitly; `none` explicitly terminates the predecessor with no successor. Neither arm mutates either exception or writes an exception proposal decision.
- Derive current exception applicability for one exact Run obligation by joining the immutable exception to its exact `accept` decision, anti-joining a supersession whose predecessor is that exception, and proving the requested Run policy epoch and discipline decision, plan, contract, policy permissions, obligation, expiry, and alternative-proof inputs remain exact. The query returns the accepted decision and one canonical applicability-input fingerprint. It never treats the successor link, greatest Project sequence, or an earlier acceptance as current authority.
- A Discipline exception is an exact replacement of one or more default proof obligations, not a blanket waiver. It may replace Red, Green, or both only when the selected policy version names those obligations as replaceable and the accepted exception supplies every fixed alternative obligation. It never waives Candidate construction for repository mutation, contract coverage, required risk-based review, Finding disposition, effect reconciliation, freshness, or mandatory human Completion acceptance.
- The effective obligation path is closed: current Application default, replaced by the exact accepted Project-profile override when present, resolved into the decision selected by the applicable Run policy epoch, then altered only by exact approved Run exceptions permitted by that decision's policy version. No profile, plan, Worker, model, or latest-row query adds another inheritance arm.
- Red is non-applicable only for an exact non-behavior obligation, a `tests-required` clause, or an accepted permitted replacement of Red. Green is non-applicable only for an exact non-behavior obligation or an accepted permitted replacement of Green. Difficult test setup, missing time, Worker preference, an existing failure, or a failed test run does not change applicability.
- Coordinate policy identity, Capability, limit, and profile references through ADR 0011's shared project-owned preparation and amendment boundary. This ADR extends each approved Run policy epoch with the exact resolved discipline decision and proof-authority inputs without creating a second preparation path.

### Typed Test-First Proof Chain

- Define the Test-first Proof Chain as a typed view over exact ADR 0010 Evidence evaluations and canonical contract decisions. It is not an Evidence family, mutable checklist, or second ledger.
- Bind one chain to Project, Run, Behavior-contract revision and clause, Test-contract revision and check, Completion-contract revision and obligation, exact Completion subject, Run discipline decision and policy version, Run policy epoch, authorized change classification, and final Candidate or permitted typed non-repository subject fingerprint.
- Use the closed proof roles `baseline`, `red`, `green`, `final-green`, `unchanged-rerun`, `independent-review`, and `approved-exception`. Each role points to the exact family evaluation Evidence entry and accepted decision that gives it meaning. The role itself has no verdict. One evaluation may fill both `green` and `final-green` only under the unchanged-input rule below.
- Baseline proof is an accepted Test evaluation that was current for the relevant pre-change fingerprint and approved command specification when recorded. It records the complete selected-test set and every existing failure before the new Red-producing test mutation. It becomes historical causal proof when the scope advances; Completion references its immutable accepted evaluation rather than pretending that the baseline fingerprint is still current.
- Red proof requires an accepted `TEST_EXPECTED_RED` evaluation that was current for the exact Test check at a fingerprint descended from the registered baseline. The evaluator must prove that the approved test executed, the failure is distinct from registered baseline failures, and the exact expected failure is attributable to the missing Behavior clause. Red likewise becomes historical causal proof after Green. `TEST_FAILED`, timeout, cancellation, ambiguity, truncation, broken invocation, an empty selected-test set, or a pre-existing failure is not Red.
- Red-before-production is an Execution gate. For a behavior under a test-first rule, the first production-code mutation command must reference the current accepted Red evaluation or the exact approved exception. The Red fingerprint may contain the declared test-only change but no production change implementing that Behavior clause.
- Green proof requires current accepted `TEST_PASSED` for the same Test-check identity, command specification, expected semantics, and Behavior clause as Red, at an exact descendant fingerprint containing the authorized implementation. A changed test, expected result, command, Capability, evaluator, or rule starts a new proof chain; it cannot reuse the earlier Red.
- `final-green` is the current applicable `TEST_PASSED` evaluation on the final Completion scope. Green and final Green may reference the same evaluation only when no relevant input changed after Green. Refactoring, remediation, composition, or another relevant change invalidates the earlier Green until the exact final scope is evaluated.
- `independent-review` is applicable only when the accepted risk recipe and Completion-contract revision require it. It references current accepted Candidate-review and Finding Evidence for an exact final Candidate. The reviewer may be the original validator or another qualified validator, but cannot be the Worker whose production mutation is under review. A permitted typed non-repository subject uses an attributed `completion_observations` review payload only when its Completion contract requires review; low-risk policy may omit that obligation without weakening the discipline's Red and Green requirements.
- `approved-exception` references the immutable exception, exact accept decision, current applicability-input fingerprint, and every current accepted alternative Evidence evaluation required by its selected fixed rule. The exception record or a successor link alone is not proof.

### Baseline Failures And Empty Results

- Register each pre-existing failure under one stable baseline-failure identity containing the Test check, normalized semantic failure signature, baseline scope fingerprint, evaluator and rule versions, and exact artifacts. It remains separate from the new expected Red.
- Permit an unchanged unrelated baseline failure to remain non-blocking only when the Test contract names it explicitly, the Completion rule classifies that exact failure as non-blocking, and a final evaluation proves the same normalized failure set, no worsening, no overlap with the changed Behavior clause or affected scope, and no changed dependency. Any changed signature, count, ownership, scope, rule, or relevance makes the allowance stale and blocks Completion pending a new contract decision.
- An allowed baseline failure never satisfies Red, Green, final Green, review, or a Behavior clause. It only proves that one exact registered pre-existing failure did not change and is outside this Completion contract's blocking scope.
- Treat an empty selected-test set, zero discovered checks where the contract requires checks, missing semantic result, or missing required artifact as `COMPLETION_BLOCKED_MISSING_EVIDENCE` or the exact Test-family non-favorable verdict. Silent command output is acceptable only when other complete trusted result data proves the exact required tests executed and their semantics; process exit zero alone is insufficient.

### Reruns And Idempotency

- Apply ADR 0006 command idempotency and ADR 0010 rerun identity before all proof-chain behavior. An exact duplicate Command ID and fingerprint returns its original receipt and appends nothing. A reused Command ID with changed content is `IDEMPOTENCY_CONFLICT` and dispatches nothing.
- Prohibit automatic rerun when the complete ADR 0010 evaluation key is unchanged, regardless of whether the current result passed, failed, was expected Red, was rejected, or was broken. Repeated execution is not a way to manufacture confidence or spend remaining budget.
- Permit an unchanged-key rerun only through ADR 0010's explicit request, accepted reason, new Command ID, separate producer-attempt start, and terminal observation. Use the closed Test-proof reasons `human-request`, `nondeterminism-investigation`, `producer-recovery`, and `independent-reproduction`. Policy selects who may approve each reason.
- A relevant changed fingerprint, contract revision, command specification, Capability, evaluator implementation, rule version, Artifact state, trust basis, or Finding creates a changed evaluation key. The resulting execution is a new applicable evaluation, not an unchanged rerun.
- An accepted rerun request that never starts, a started producer without a terminal result, and a completed rerun remain physically distinct under ADR 0010. None is inferred as pass, Red, no change, or no effect.

### Test Author And Remediation Routing

- Make `test-author` a Delegation role, not an authority owner or status. A Test Author receives exact clauses, current contracts, baseline Evidence, scope, permissions, and proof obligations. It may mutate only approved test and test-support scope and cannot implement the production behavior it must first expose.
- Permit one low-risk Worker to act in application-enforced test-author then implementer phases when the accepted risk rule and Completion contract allow it. Close production mutation during its test-author phase, settle Red, then open only the approved implementation phase. Standard or high-risk policy separates Test Author, implementation Worker, or validator only where the accepted risk recipe names those roles; discipline mode alone does not add them.
- When an in-scope blocking Finding lacks a suitable regression test and test-first policy applies, route first to a Test Author. Production remediation remains closed until the new or amended Test contract and required Red are current.
- A fix submission does not close a Finding. Current accepted `RECHECK_RESOLVED` followed by the exact Finding decision is required for `FINDING_CLOSED_VERIFIED`; accepted risk must identify actor, policy, scope, residual risk, and expiry. Out-of-scope Findings remain real and may propose a derived Waypoint, but cannot silently expand or satisfy the current contract.

### Change Classification And Fixed Tests

- Require one immutable `RunChangeClassificationId` before every repository mutation phase. Use the closed kinds `behavior-implementation`, `production-only-remediation`, `test-changing-remediation`, and `non-behavior`. The classification is a canonical authorization input, not an Evidence verdict, Worker assertion, Candidate verdict, or substitute for effect scope.
- Bind each classification proposal to the exact Run, Worker or planned role, Delegation task, plan revision, Run discipline decision, policy epoch, Behavior-, Test-, and Completion-contract revisions, Behavior clauses, Findings when applicable, declared mutation scope, expected starting fingerprint, risk recipe, and proposed fixed Test set or test-changing scope.
- Persist an immutable authorizing decision with action `accept`, `reject`, or `request-changes`, actor, command receipt, complete proposal fingerprint, expected versions, and rationale. Only an exact `accept` decision opens the declared mutation phase. A changed proposal, scope, contract, policy, risk, Finding, Worker, task, or starting fingerprint requires a new classification and decision.
- Use proposal commands `ProposeRunChangeClassification`, `AcceptRunChangeClassification`, `RejectRunChangeClassification`, and `RequestRunChangeClassificationChanges`. `SupersedeRunChangeClassification` instead appends one supersession record with exact predecessor, closed successor arm `replacement` or `none`, nullable successor classification required only for `replacement`, actor, required reason, command receipt, expected applicability-input fingerprint, and Project sequence. A successor remains an independently decided proposal; absence explicitly ends applicability without fallback. The command mutates no classification and adds no authorization-decision action.
- Apply ADR 0006 command idempotency before every classification or supersession settlement; exact retries return their original receipt and append nothing, while conflicting reuse is `IDEMPOTENCY_CONFLICT`.
- For `behavior-implementation`, require the applicable Red gate or accepted obligation replacement before production mutation. For `production-only-remediation`, require one immutable `FixedTestSetId` containing every fixed Test-check identity, Test-contract revision, command specification and hash, expected semantics, test and support Artifact identities/hashes, evaluator/rule versions, and baseline or Red dependencies.
- A production-only remediation Worker may change only its declared production scope. Any change to a fixed Test check, test/support Artifact, command, expected semantics, coverage mapping, evaluator/rule input, or fixed-set member is an effect-scope violation, invalidates the classification and dependent proof, and cannot be accepted as production-only.
- For `test-changing-remediation`, name the exact test gap or incorrect check, permitted test and support scope, affected clauses and Findings, and the Test Author phase. A changed command, semantics, coverage, or check content requires a new Test-contract revision and makes dependent Red, Green, Completion Evidence, fixed Test sets, and earlier acceptance stale. If test-first remains applicable, the amended check must earn a new expected Red before production remediation.
- For `non-behavior`, require an exact declaration that no Behavior clause changes and name the output and repository scope. Re-evaluate the final Candidate against production, runtime, API, schema, dependency, configuration, packaging, security, generated-code, and user-observable surfaces. Any detected behavior impact invalidates the classification and blocks Completion until a behavior-capable classification and proof chain are accepted.
- Derive current classification applicability by directly joining the immutable proposal to its exact `accept` decision, anti-joining any supersession whose predecessor is that classification, and proving that Run, Worker or role, task, plan, epoch-decision pair, contracts, Findings, risk, scope, starting fingerprint, and Fixed Test set still equal the command's current inputs. Reference that exact accepted decision, applicability-input fingerprint, and Fixed Test set from every mutation command, Worker result, Candidate construction evaluation, Completion observation, Completion evaluation, user Completion-acceptance request, and Completion authorization. No latest-row lookup, mutable status, successor link alone, or historical acceptance grants current authority.

### Parallel Worker And Final Candidate Proof

- Let each Worker prove only its exact Task-workspace result, sealed input, Worker identity, Delegation task, contract inputs, and scope fingerprints. A dependent Worker consumes predecessor proof only through a newly sealed input that references the predecessor's exact accepted result.
- Keep sibling Task-workspace proof independent. No Worker evaluation can close, invalidate, or stand in for another Worker, and a set of green Worker results cannot be summed into Run Completion.
- Require one fresh final Completion subject after fan-in. Any code or repository mutation uses the exact materialized Candidate identity, version, membership, source baseline, Candidate scope, and Candidate fingerprint. This includes production, tests, documentation, metadata, configuration, dependencies, generated files, and every tracked or untracked repository change. Composition-sensitive tests and contract-selected review run on that Candidate as a whole.
- Permit a typed non-Candidate subject only when the exact Completion-contract revision classifies the Run as `non-repository-output` and current Evidence proves no repository mutation and no started effect. The subject must be one exact Artifact scope or a later separately decided typed non-Candidate Evidence scope. Run-workspace and Task-workspace scopes are prohibited as Completion subjects.
- If any mutation or effect appears after a non-repository subject was selected, invalidate its Completion Evidence and acceptance request. Repository mutation requires Candidate construction; an effect without an eligible Candidate leaves Completion blocked under the v1 contract rather than using Run-workspace state as a bypass.
- Documentation, metadata, research, design, and test-only work is non-behavior only when its accepted change classification proves that no production, runtime, API, schema, dependency, configuration, packaging, security, generated-code, or user-observable behavior changes. If it changes the repository it still requires an exact final Candidate, deterministic checks, Finding disposition, effect reconciliation, and any review selected by risk and contract, but no fictitious Red/Green obligation.
- Treat mixed work clause by clause. A documentation or test change in the same Candidate does not make a production behavior change non-behavior.

### Completion Rules And Matrix

- Register small contract-specific completion evaluators and rules through ADR 0010 `evidence_evaluators`, `evidence_evaluator_versions`, `evidence_rule_sets`, and `evidence_rule_versions`. The initial fixed rules cover strict/test-first behavior, tests-required behavior, approved alternative proof, non-behavior output, Candidate review, Finding disposition, and effect reconciliation.
- Compile each rule in project-owned code against typed contract and Evidence inputs. Changing rule behavior creates a new evaluator version and implementation hash and a new rule version where semantics changed. Reusing a semantic version with changed code cannot preserve current authority.
- Evaluate every Completion obligation to exactly one satisfied or named blocking result. The Completion-family verdict remains one of ADR 0010's closed verdicts. Missing, failed, stale, open-Finding, uncertain-effect, ambiguous, truncated, rejected, and broken conditions retain their exact non-favorable meaning.
- Define the Completion Matrix as a query-only projection with one row per Behavior clause or non-behavior obligation, its selected fixed rule, required proof roles, exact accepted historical causal Evidence, exact current terminal Evidence, applicability, and current blocking diagnosis. It is never accepted, edited, checked off, versioned, or persisted as authority.
- Compute the Matrix in memory from authoritative rows for each query. Do not persist a Matrix cache or allow a Matrix result to be consumed as command authority.

### Finding Scope Snapshot

- Determine the applicable Finding set through one direct, versioned query over `findings` joined to `finding_current_evaluations` by exact Project, originating Run, Completion subject scope, subject fingerprint waterline, Completion-contract revision, applicable Finding rules, and current Finding versions. Never infer an empty set from missing rows, a cached UI list, latest timestamps, or replay.
- Persist one immutable `CompletionFindingSnapshotId` for each Completion observation. Store the normalized query schema/version and parameters, Run, exact Completion subject scope and fingerprint, contract and rule versions, canonical Project-sequence waterline, Writer generation, and one canonical dependency/query fingerprint. Each ordered member references its exact immutable Finding evaluation, evaluation Evidence entry, and accepted Finding decision, and copies the Finding verdict plus `observed_current_version`, canonical current-row hash algorithm, and `observed_current_row_hash` seen during the query.
- Compute the observed current-row hash from a versioned canonical encoding of the current row's primary key, current evaluation, evaluation entry, accepted decision, verdict, input/result fingerprints, evaluator and rule versions, Project sequence, and Writer generation. Snapshot members have no foreign key to `finding_current_evaluations`; copied version and hash values are observations, not identity or authority.
- A zero-member snapshot is valid only when the direct query completed without truncation, ambiguity, missing input, integrity failure, or evaluator failure at the recorded waterline. Every non-zero member remains subject to its exact current Finding meaning; the snapshot cannot close, accept risk, reject, supersede, or otherwise decide a Finding.
- Re-run the same indexed query during Completion decision, user acceptance request, authorization issue, and Run-completion settlement. Compare membership, immutable evaluation/decision pointers, copied observed current version/hash, and the complete query fingerprint. A changed membership, materialized-current version/hash, Finding version, evaluation, decision, verdict, scope fingerprint, query version, rule, or waterline makes the prior snapshot stale and triggers normal ADR 0010 dependency invalidation; no current-row mutation can alter the snapshot.
- Treat the snapshot and members as typed Completion payload and exact Evidence dependencies, not a new Finding ledger, Finding current table, or alternative authority. The authoritative Finding query remains `finding_current_evaluations` under ADR 0010.

### Human Completion Acceptance And Authorization

- Use ADR 0010's `completion` Evidence family and `completion_current_evaluations` as the only current technical-readiness authority. Its `COMPLETION_AUTHORIZED` verdict means Evidence-ready for human review; it is not user acceptance and creates no `CompletionAuthorization` by itself.
- After technical readiness, `SubmitRunCompletionForAcceptance` creates one immutable request bound to the exact current Completion evaluation and entry, accepted Evidence decision, current-row version, Completion Finding snapshot, Completion subject and fingerprint, contracts, Run discipline decision, accepted exceptions, change classifications, Fixed Test sets, plan, policy epoch, evaluator/rule versions, and complete input fingerprint.
- Require one explicit user command for every request: `AcceptRunCompletion`, `RejectRunCompletion`, or `RequestRunCompletionChanges`. Persist one immutable decision with actor, action, reason or requested changes, command receipt, request fingerprint, expected Run and current Completion versions, and decision Project sequence. No Completion contract, discipline policy, model, parent, Worker, or automatic policy may omit or synthesize this decision.
- An exact `reject` or `request-changes` decision creates no authorization. Requesting changes may lead to the existing Run Change-request path, but the user decision itself does not mutate contracts, Findings, Evidence, Candidate, or Run state. A later proposal creates a new acceptance request.
- `IssueCompletionAuthorization` requires an exact user `accept` decision and re-runs every current proof, Finding-snapshot, subject, contract, discipline, exception, change-classification, Fixed-Test-set, rule/evaluator, Artifact, effect, and policy precondition under the fenced Writer. Any mismatch rejects issue and requires a new readiness evaluation and user request/decision.
- When and only when those checks pass, `IssueCompletionAuthorization` creates one immutable `CompletionAuthorization` referencing the exact accepted user decision and request, current Completion-evaluation identity and Evidence-entry identity, Evidence decision and current-row version, Completion Finding snapshot, Behavior-, Test-, and Completion-contract revisions, Run discipline decision and policy version, exceptions, change-classification decisions, Fixed Test sets, Delegation-plan revision, Run policy epoch, Candidate identity/version/fingerprint or permitted typed non-repository subject and fingerprint, evaluator identity/version/implementation hash, rule-set versions, and complete input fingerprint.
- Make the authorization's Completion evaluation carry exact typed dependencies on every Test evaluation, Candidate-review evaluation, Finding and Finding-recheck evaluation, effect evaluation, Artifact-state version, accepted exception, change classification, Fixed Test set, subject version, contract revision, Capability, approved limit, policy epoch, trust basis, and subject fingerprint used. Baseline and Red dependencies are exact accepted historical causal evaluations; final Green, Candidate review where applicable, Findings, effects, Artifact state, rules, evaluators, and subject dependencies must be exact and current at authorization time.
- Treat `CompletionAuthorization` as immutable historical proof, not a mutable certificate status, Run status, Waypoint status, user decision, Candidate user authorization, or Integration authorization. There is no `completion_authorization_status`, mutable validity flag, or second current pointer.
- Require Execution's `AuthorizeRunCompletion` to carry the exact authorization, accepted user Completion-decision identity, expected `completion_current_evaluations.current_version`, Run Entity version, exact Candidate or permitted typed non-repository subject fingerprint, and every contract, discipline, classification, and policy reference. Settlement re-runs the Finding-snapshot query and proves both user acceptance and Evidence readiness are still exact and current before moving the Run. A stale authorization remains history and authorizes nothing.

### Stale Invalidation And Failure Preservation

- Use ADR 0010 typed reverse dependencies and atomic invalidation. A changed Candidate identity, version, membership, source baseline or fingerprint; permitted typed non-repository subject or fingerprint; Behavior, Test, or Completion contract revision; Run discipline decision, policy version, exception, or exception supersession; change classification, authorizing decision, classification supersession, or Fixed Test set; plan, policy epoch or limits; test command or check semantics; Capability; evaluator version or implementation hash; rule version; Artifact state; trust basis; Finding-snapshot query or member; Finding disposition or recheck; effect evaluation; Candidate review; or required Test evaluation invalidates every affected current Completion evaluation in the same settlement. A stale, replaced, or non-accepted user Completion request or decision does not rewrite Evidence authority; it prevents authorization issue or Run completion and requires a new request and decision.
- Advance invalidated Completion authority to the exact applicable ADR 0010 blocked verdict. Use stale for obsolete but intact inputs, missing for absent required Evidence, failed-check for current blocking test or validation failure, open-Finding for current blocking Findings, uncertain-effect for unsettled effects, ambiguous or truncated for those exact Evidence conditions, and broken for integrity or evaluator failure.
- Never clear a favorable current pointer to unexplained null, restore an older readiness result, user decision, or authorization automatically, or reinterpret rejected, ambiguous, broken, truncated, empty, stale, missing, uncertain, cancelled, timed-out, or not-run Evidence as satisfying an obligation.
- A changed input permits new evaluation; it does not prove improvement. Returning an Artifact or evaluator to health requires a new accepted evaluation and never revives the old authorization.

### Commands And Transactions

- Use versioned canonical commands `AcceptBehaviorContractRevision`, `AcceptTestContractRevision`, `AcceptCompletionContractRevision`, `ProposeDisciplineException`, `ApproveDisciplineException`, `RejectDisciplineException`, `RequestDisciplineExceptionChanges`, and `SupersedeDisciplineException`. Each requires expected aggregate and Waypoint versions, exact prior revisions, complete normalized content fingerprint, actor authority, and Writer generation.
- Use ADR 0010 family commands for proof: `RecordTestObservation`, `DecideTestEvaluation`, `RequestTestRerun`, `StartTestProducerAttempt`, `RecordCandidateReviewObservation`, `DecideCandidateReviewEvaluation`, Finding and recheck commands, effect commands, `RecordCompletionObservation`, `DecideCompletionEvaluation`, and `InvalidateCompletionCurrentEvaluation`. No command writes a Proof Chain or Completion Matrix directly.
- `RecordCompletionObservation` captures the exact contracts, Run discipline decision and policy version, exceptions, change classifications and authorizing decisions, Fixed Test sets, Candidate or permitted typed non-repository subject, current Evidence, Completion Finding snapshot, effects, evaluator, rules, Artifact state, trust inputs, and current waterline. It does not record user acceptance or authorize Completion.
- `DecideCompletionEvaluation` evaluates every fixed obligation, writes typed obligation results and dependencies, writes the exact Evidence decision, and compare-and-sets the materialized current row atomically under ADR 0010. `COMPLETION_AUTHORIZED` makes Evidence ready for `SubmitRunCompletionForAcceptance`; it writes no `completion_authorizations` row.
- `SubmitRunCompletionForAcceptance`, `AcceptRunCompletion`, `RejectRunCompletion`, `RequestRunCompletionChanges`, and `IssueCompletionAuthorization` use separate Command IDs and receipts. Exact retries return the first settlement; conflicting command reuse writes `IDEMPOTENCY_CONFLICT` and cannot create a request, decision, authorization, or Run transition.
- `SupersedeDisciplineException` and `SupersedeRunChangeClassification` require the exact predecessor, expected proposal decision where one exists, expected applicability-input fingerprint, successor arm and identity, reason, actor, and Writer generation. Canonical command idempotency settles the append-only relation once; the same transaction reverse-invalidates every current Evidence evaluation depending on the predecessor before the supersession becomes visible.
- Contract, discipline, exception, exception-supersession, change-classification, classification-supersession, and Fixed-Test-set settlement atomically reverse-invalidates affected current Evidence before the canonical change becomes visible. A Finding-current advance queries snapshot members by Finding identity and invalidates every dependent current Completion evaluation whose copied observed version/hash or immutable evaluation/decision pointers no longer match. User Completion decisions never write Evidence; they only permit or deny later authorization issue. A fan-out, stale Finding snapshot, subject mismatch, or compare-and-set failure rejects the whole applicable command.
- Matrix queries and Proof Chain queries are read-only. They allocate no Command ID, receipt, Evidence entry, Project sequence, or status transition.

### Keys And Constraints

- Apply ADR 0006 Project-scoped composite keys, immutable revisions, deferred current-revision references, command settlement, and Writer fencing to every canonical Contract table.
- Key each current contract by `(project_id, contract_id)`, make its Waypoint binding exact, and make `(project_id, contract_id, revision_number)` unique. Contract revision children use non-negative position and stable child identity unique within the revision.
- Require a Test-contract revision to reference one exact Behavior-contract revision. A Test check must have at least one exact Behavior-clause mapping or one exact non-behavior obligation classification, never both. Make normalized command-specification fingerprints integrity values rather than identities.
- Require a Completion-contract revision to reference one exact Behavior- and Test-contract revision. Each obligation uses one closed kind and its required typed child shape. Behavior and Test references must resolve inside those pinned revisions.
- Key discipline policies by stable identity and immutable version; make the identity/version/content-fingerprint tuple unique. Key `project_profile_development_discipline_overrides` by `(project_id, project_profile_id, project_profile_revision_id)`, allowing at most one override child per revision. Give it composite foreign keys to that exact Project-profile revision and selected Development-discipline policy version. Absence means inherit the Application default; removing an override requires a later accepted Project-profile revision without the child.
- Key each Run decision by stable `(project_id, run_discipline_decision_id)`. Store its exact `run_id`, non-negative `decision_sequence`, accepted Delegation-plan revision, source kind, selected policy identity/version/content fingerprint, replacement-permissions fingerprint, command receipt, and Project sequence. Make `(project_id, run_id, decision_sequence)` and `(project_id, run_id, run_discipline_decision_id)` unique for ordering and composite references. Never make `run_id` alone unique; an approved amendment may append a later decision.
- Enforce the Run decision source as a checked union. `application-default` requires exact `application_default_decision_id` and `application_default_decision_sequence` and null Project-profile source columns. `project-override` requires exact `project_profile_id` and `project_profile_revision_id`, null Application-decision source columns, and a composite foreign key to `project_profile_development_discipline_overrides`. Both arms require the same Project-scoped composite foreign key to the selected immutable policy version and equality with its content and replacement-permissions fingerprints.
- Add `run_discipline_decision_id` to `run_policy_epochs` and require its composite foreign key `(project_id, run_id, run_discipline_decision_id)` to resolve to the same Run. Make `(project_id, run_id, run_policy_epoch_id, run_discipline_decision_id)` unique so every Sealed Invocation, Proof Chain, Evidence payload, Completion request, and authorization can use a real composite foreign key to the exact epoch-decision pair it historically consumed. The `runs` current epoch pointer determines the effective decision; there is no independent current-discipline pointer and no uniqueness constraint from decision to Run or epoch.
- Key a discipline exception by `(project_id, discipline_exception_id)`, bind it through a composite foreign key to one exact Run policy epoch and its Run discipline decision, and bind its policy version, plan revision, and Completion-contract revision. Require one or more exact replaced-obligation and alternative-proof rows. Key its optional immutable proposal decision by opaque identity, make the exception and command receipt unique, and constrain the action to `accept`, `reject`, or `request-changes`; an accepted decision can reference only replacement kinds permitted by the selected policy version.
- Key `discipline_exception_supersessions` by `(project_id, discipline_exception_supersession_id)`. Make predecessor exception and command receipt unique; make a populated successor unique so chains cannot merge or branch. Enforce the checked `replacement`/non-null-successor or `none`/null-successor union, same-Project and same-Run composite foreign keys, successor Project sequence after predecessor, no self-link, and acyclic chains. Store actor, required reason, expected applicability-input fingerprint, receipt, and Project sequence only on this append-only record. Current applicability is the exact accepted-decision query anti-joined by predecessor; no mutable exception column participates.
- Key each Run change classification by `(project_id, run_change_classification_id)` and bind at most one immutable proposal decision by proposal fingerprint. Make classification and decision command receipts unique, and constrain decision action to `accept`, `reject`, or `request-changes`. Require exactly one closed classification kind and its typed shape. Key Fixed Test sets by `(project_id, fixed_test_set_id)` and members by non-negative position and exact Test-check identity; a production-only classification requires one Fixed Test set, test-changing requires an exact permitted test scope, and non-behavior prohibits Behavior-clause mappings.
- Key `run_change_classification_supersessions` by `(project_id, run_change_classification_supersession_id)`. Make predecessor classification and command receipt unique; make a populated successor unique; enforce the checked `replacement`/non-null-successor or `none`/null-successor union, same-Project and same-Run composite foreign keys, later successor Project sequence, no self-link, and acyclic linear chains. Store actor, required reason, expected applicability-input fingerprint, receipt, and Project sequence on the relation. Derive current applicability only from exact accept decision plus anti-join absence and equality of every pinned current input; no classification status or supersession action exists.
- Key `test_evaluation_proof_roles` by exact ADR 0010 Test evaluation and proof role, and require its Run, scope, Test contract, check, command specification, and fingerprints to agree. Make each role unique within one clause/check chain, while permitting one evaluation to fill both `green` and `final-green`. An unchanged-rerun role also requires the exact rerun request and producer attempt.
- Key every `completion_evaluation_*` row by its owning Completion evaluation and non-negative position or exact obligation identity. Use real composite foreign keys to the exact Test evaluation, Candidate-review evaluation, Finding and recheck evaluations, effect evaluation, exception, contract child, Evidence scope, and fingerprint. Typed child checks prevent a proof row from changing family or role.
- Key Completion Finding snapshots by `(project_id, completion_finding_snapshot_id)` and make each snapshot belong to one Completion observation, subject scope, fingerprint, query version, Project-sequence waterline, and Writer generation. Key ordered members by snapshot and position and make each Finding unique in the snapshot. Use composite foreign keys only to the immutable Finding, Finding evaluation and its Evidence entry, and accepted Finding decision, proving that the decision selected that exact evaluation, scope, and verdict. Store copied non-negative `observed_current_version`, versioned canonical-hash algorithm, and `observed_current_row_hash` with integrity checks but no foreign key to `finding_current_evaluations`.
- Key each Completion acceptance request by `(project_id, completion_acceptance_request_id)` and make its submit receipt unique. Permit exactly one immutable decision per request with action `accept`, `reject`, or `request-changes`; make its decision receipt unique. An accepted decision must match the request's exact Completion current version and complete input fingerprint.
- Make `completion_authorizations` one-to-one with an exact user `accept` decision and one exact still-current `COMPLETION_AUTHORIZED` Evidence evaluation and accepted Evidence decision. Require its Run, contracts, discipline, exceptions, change classifications, Fixed Test sets, Finding snapshot, subject, evaluator, rules, and input fingerprint to equal both request and evaluation. Every other Evidence verdict or user decision prohibits an authorization row.
- For Candidate subject, require the exact current accepted `CANDIDATE_ACCEPTABLE` evaluation for the same Candidate identity, version, scope, and fingerprint. For `non-repository-output`, require the contract's exact subject arm, exact Artifact or later typed non-Candidate scope, current no-mutation and no-effect proof, and null Candidate columns. Prohibit Run-workspace and Task-workspace subjects. Exactly one subject arm is populated.
- Preserve ADR 0010's current Completion key `(project_id, run_id, evidence_scope_id, completion_contract_revision_id)`. A different Worker, sibling scope, Candidate version, or contract revision cannot overwrite it.

### Direct Queries And Required Indexes

- Query current canonical contracts through their current revision pointers, effective Run discipline through `runs.current_run_policy_epoch_id -> run_policy_epochs.run_discipline_decision_id`, and current Completion authority through ADR 0010's `completion_current_evaluations` primary key. Consumers never infer authority from the greatest discipline decision sequence, replay history, or select the latest timestamp.
- Build the Completion Matrix by joining the exact current Completion row and its accepted evaluation to pinned contract clauses and obligations, typed `completion_evaluation_*` payload rows, and referenced family current rows. Build the Proof Chain from `test_evaluation_proof_roles`, rerun records, typed Completion proof rows, and accepted Evidence decisions.
- Index Behavior clauses by contract revision and stable clause identity; Test checks by contract revision and stable check identity; Test-to-Behavior mappings by clause and check; Completion obligations by revision and stable obligation identity; and Completion obligation mappings by Behavior clause and Test check.
- Index discipline policy versions by identity and descending version; Project-profile overrides by exact profile revision and policy version; Run discipline decisions by Run and descending decision sequence, source kind and source identity, selected policy version, accepted plan, and Project sequence; and policy epochs by Run and discipline decision. Index exceptions by Run, Run discipline decision, policy epoch, Completion-contract revision, obligation, and exact accept decision; index supersessions uniquely by predecessor, populated successor, and command receipt, plus reason and Project sequence. These paths support the applicability anti-join without a latest-row lookup. Index baseline failures by Test contract, Test check, normalized failure signature, and baseline scope fingerprint.
- Index Run change classifications by Run, Worker or role, task, kind, starting fingerprint, policy epoch, exact accept decision, and every applicability-input identity. Index classification supersessions uniquely by predecessor, populated successor, and command receipt, plus reason and Project sequence. Index Fixed Test sets by classification and Test check, and reverse-index members by Test Artifact and command-specification fingerprint.
- Index Test proof roles by Run, Evidence scope, Behavior clause, Test check, role, and descending Project sequence. Index every typed Completion proof table by its referenced Evidence evaluation or Finding and by owning Completion evaluation.
- Index Completion Finding snapshots by Run, exact subject scope and fingerprint, contract, query version, and waterline. Index members by Finding, immutable Finding evaluation and Evidence entry, accepted Finding decision, and copied observed current version/hash; no snapshot index or foreign key targets a mutable current row. Index acceptance requests by Run, Completion evaluation/current version, exact subject fingerprint, and submit sequence; index decisions by request, actor, action, and decision sequence.
- Index immutable authorizations by Run and descending Project sequence, accepted user decision, exact Completion evaluation and Evidence decision, subject scope, Candidate identity/version/fingerprint when present, and contract, discipline, classification, and policy references. The one-to-one user-decision index supplies direct authorization lookup.
- Reuse ADR 0010 reverse dependency and `current_evaluation_entry_id` indexes for invalidation. Do not add duplicate primary/unique indexes, JSON indexes, generic rule-expression indexes, or digest-only authority paths.

### Completion Remains Separate From Integration

- Completion proves that one exact Run output satisfies its current contracts. It does not apply repository changes, authorize a target ref, prove conflict freedom at a later target fingerprint, delete a Run workspace, or imply that a Candidate was integrated.
- Candidate technical Evidence, mandatory user Completion acceptance, Candidate user authorization for Integration, and final Integration approval remain separate exact authorities. `AuthorizeRunCompletion` consumes only Completion acceptance and authorization; none of these decisions substitutes for another.
- Integration continues to require ADR 0010 `INTEGRATION_APPLICABLE` Evidence over the exact current target plus every separate Candidate, Completion, user, policy, and effect authorization. A completed Run may remain unintegrated, and an Integration conflict does not rewrite its historical Completion authorization.

## Consequences

- A Run can explain exactly why it is complete or blocked at each clause without trusting a Worker claim, a green command alone, or an editable matrix.
- Test-first remains strongly enforced for applicable external Project behavior while explicit policy-permitted exceptions and non-behavior rules avoid a false universal product pipeline. SlopStop's own strict repository discipline is unchanged.
- Exact Candidate and dependency binding makes proof stale more often after composition or remediation, but prevents branch-local success from certifying untested combined work.
- Fixed compiled rules require explicit versioned additions for new contract shapes. This is intentionally less flexible than a generic predicate language and keeps authority reviewable.
- Immutable user decisions, authorizations, and query-only projections add relational detail but do not add a second Completion state or weaken ADR 0010's current-evaluation model.
