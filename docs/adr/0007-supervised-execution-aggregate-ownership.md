# ADR 0007: Supervised Execution Aggregate Ownership

- Status: Accepted
- Date: 2026-08-26
- Decision owners: Pedro Mesquita

## Context

Supervised execution needs durable Run, Worker, and steering state without allowing a model, runtime callback, or worker result to become canonical authority. The accepted status families already distinguish Run, Worker, Control request, Waypoint, Action availability, and external Evidence states. The physical persistence layout reserves owner-specific current and transition tables, but it deliberately leaves Execution aggregates to their owner. This decision fixes those aggregate boundaries, exclusivity rules, transition authority, retry identity, model attribution, and the inputs to Action availability before workspace, AgentRuntime, and plan-content designs proceed.

## Decisions

### Aggregate Boundaries

- A `Run` is one supervised attempt to perform one exact Action version on one Waypoint. It owns current execution lifecycle, exact contract and policy references, and links to its Waypoint parent, Workers, Control requests, workspace, Evidence, and recovery records.
- A `Waypoint parent` is the single logical AI supervisor of one Run. It is a singleton child, not a Worker and not another status family. Restart, resume, compaction, runtime session replacement, and future model changes preserve its identity.
- A `Delegation task` is immutable content inside an accepted Delegation plan revision. A `Worker` is one concrete attempt to perform that task. Task identity remains stable while terminal retry creates a new Worker identity.
- A `Control request` is one durable immutable intent targeted at a Run, its Waypoint parent, or one of its Workers. It owns a directly queryable lifecycle, while transport delivery remains in the canonical-to-runtime handoff protocol.
- A `Model attempt` is an append-only attributed record of one admitted provider-dispatch attempt for a Waypoint parent or Worker. Execution creates it only after command and policy admission and durable Recovery Journal `started`, immediately before the adapter boundary. It is not proof by itself that the provider was invoked, is not an aggregate, cannot set status, and gains no authority from model output.

### Run Exclusivity And Lifecycle

- Permit at most one nonterminal Run per Waypoint, independent of Action. A `run_slots` current projection owns that exclusivity without adding Execution state to the Waypoint aggregate.
- Create the slot atomically with the Run and retain it through `draft`, `awaiting-approval`, `ready`, `running`, `pause-requested`, `paused`, `change-requested`, `blocked`, `recovery-required`, `ready-for-validation`, and `cancel-requested`. Release it atomically only when the Run reaches `cancelled`, `failed`, `superseded`, or `completed`.
- Use the primary preparation path `draft -> awaiting-approval -> ready -> running -> ready-for-validation`. Pause follows `running -> pause-requested -> paused -> ready`. Safe idle work may cancel directly; active work follows `cancel-requested -> cancelled | recovery-required`.
- A compatible Change request follows `change-requested -> awaiting-approval` with a new exact approved revision. Materially contradictory intent follows `change-requested -> superseded` and creates a new Run if the user continues.
- Permit `ready-for-validation -> running` only for independently authorized remediation. Permit `ready-for-validation -> completed` only with current Evidence-authority completion authorization. Only `ApplyRunRecoveryReconciliation` may move a Run out of `recovery-required`. It requires one accepted Evidence reconciliation for the exact recovery condition, expected Run and recovery versions, final Model-attempt, Tool-invocation, Process-job, effect, usage, and Workspace-fingerprint classifications, and proof that the targeted uncertainty is closed. It removes only that recovery condition. If another recovery condition remains, the Run stays `recovery-required`; otherwise it reruns the complete lifecycle evaluator over pending pause, cancellation and Change requests, provider/model, Capability, policy, Budget, dependency, Workspace, Evidence, validation, Worker-slot, profile, and policy-epoch inputs, then selects the one legal next state. It never hardcodes `running` or jumps over a remaining blocker.
- Treat `cancelled`, `failed`, `superseded`, and `completed` as terminal. Provider, Capability, Budget, policy, workspace, dependency, or validation problems that may change leave a Run `blocked`; they do not manufacture terminal failure.

### Run State And Versioned Content

- Keep one directly queryable `runs` current row with Waypoint, Action family/version, Run status family/version, Entity version, current Behavior Contract, Test Contract, Completion Contract, Delegation plan revision, `current_run_policy_epoch_id`, Waypoint parent identity, Resume capsule reference, Run-workspace identity and fingerprint waterline, causation, creation sequence, last-transition sequence, and optional terminal sequence. The referenced epoch owns the effective Run discipline-decision reference; `runs` stores no second discipline pointer that could drift from it.
- Do not create generic Run revisions. Behavior Contracts, Test Contracts, Delegation plans, policy epochs, Resume capsules, and Change-request decisions retain separate versioned ownership.
- Pin every Run reference to an exact revision. A newly accepted Project profile, contract, plan, or Capability version never changes an existing Run silently. A compatible amendment changes current pointers through an attributed command and preserves the exact references used by prior dispatches and Model attempts.
- Use the closed v1 Run cause vocabulary `ACTION_SELECTED`, `PREPARATION_COMPLETE`, `APPROVAL_REQUIRED`, `PLAN_APPROVED`, `EXECUTION_STARTED`, `PAUSE_REQUESTED`, `SAFE_CHECKPOINT_REACHED`, `RESUME_APPROVED`, `CHANGE_REQUESTED`, `AMENDMENT_APPROVAL_REQUIRED`, `DEPENDENCY_BLOCKED`, `BUDGET_EXHAUSTED`, `POLICY_BLOCKED`, `CAPABILITY_UNAVAILABLE`, `PROVIDER_UNAVAILABLE`, `WORKSPACE_INVALIDATED`, `RECOVERY_REQUIRED`, `VALIDATION_REQUESTED`, `VALIDATION_FINDINGS_OPEN`, `REMEDIATION_AUTHORIZED`, `COMPLETION_AUTHORIZED`, `CANCEL_REQUESTED`, `USER_CANCELLED`, `RUN_SUPERSEDED`, and `EXECUTION_FAILED`. One cause explains a transition; ordered condition codes explain why current state remains blocked or recovery-required.

### Commands And Preconditions

- Move Run lifecycle only through versioned intent or observation commands: `BeginAction`, `PrepareAutomaticAction`, `SubmitRunPreparation`, `ApproveRunPreparation`, `StartRun`, `RequestRunPause`, `ConfirmRunPaused`, `ResumeRun`, `SubmitChangeRequest`, `ApproveRunAmendment`, `RecordRunBlocked`, `RecordWaypointParentProviderUnavailable`, `RecordWaypointParentModelUnavailable`, `RecoverWaypointParentModel`, `RequireRunRecovery`, `ApplyRunRecoveryReconciliation`, `SubmitRunForValidation`, `AuthorizeRunRemediation`, `AuthorizeRunCompletion`, `RequestRunCancellation`, `ConfirmRunCancelled`, `RecordRunFailure`, and `SupersedeRun`. There is no `SetRunStatus` and no Run `stopped` state.
- Require each mutating command to cover the expected Run Entity version and every applicable Worker or Control request version, Delegation plan revision, policy epoch, Run-workspace identity and fingerprint, Run slot ownership, and exact Evidence or recovery authorization.
- Allow a specific Execution command to update several Execution-owned aggregates atomically only when its versioned contract declares the complete write set. Keep the canonical prohibition on a public generic batch.
- Accept external inputs only as attributed, versioned envelopes. Users supply intent and approval; runtime supplies proposed observations or results; Evidence supplies Finding, remediation, invalidation, and completion authority; Recovery supplies reconciliation; policy supplies one dispatch-bound decision. Execution validates the input and computes the transition. No external owner writes Execution status directly.

### Worker Attempts And Slots

- Add nonterminal `stop-requested` and terminal `stopped` to the Worker status family. A closed normalized `provider-unavailable` or `model-unavailable` observation is not generic provider rejection or failure, Worker failure, cancellation, Run pause, or Run cancellation. `RecordWorkerProviderUnavailable` and `RecordWorkerModelUnavailable` validate the exact observation and create a typed `worker-stop` Control request, moving only the affected queued, running, or paused Worker to `stop-requested` with distinct cause `PROVIDER_UNAVAILABLE` or `MODEL_UNAVAILABLE`. Generic rejection or failure cannot enter this path by free-text or adapter inference.
- `RequestWorkerStop` persists the Worker-targeted Control request and an immutable warning-time snapshot containing expected Worker and slot versions, concrete provider/model and resolution source, reason, current checkpoint, effects then classified completed, effects then classified uncertain, and available Retry, Model change, and Cancel actions. It closes new Model-attempt, Tool-invocation, and Process-job dispatch for that Worker immediately. Cancel submits the existing `RequestRunCancellation` command and a Run-targeted cancellation Control request; task-level redirection or removal uses a Change request and approved replanning, not an undefined Worker cancellation.
- `ConfirmWorkerStopped` requires one immutable Worker stop checkpoint proving zero Model attempts and Tool invocations remain in flight; no Process job, mutation lease, or read claim owned by that Worker remains active; every started effect is terminal and reconciled; and the final Workspace fingerprint and budget waterline are accepted. The checkpoint stores final Evidence-backed classifications separately from the warning-time snapshot, links every refinement and newly discovered effect, and may refine earlier uncertainty to completed, failed, cancelled, or `proven-not-started` without requiring equality to the snapshot. If any effect remains uncertain, keep the Worker `stop-requested`, retain its slot, and move the Run to `recovery-required` rather than manufacturing `stopped`.
- Key `worker_slots` by Project, Run, and Delegation task identity, with a unique current Worker. Create the slot when a Worker is queued and retain it through pause, resume, stop-requested, and safely reconciled interruption. Release it only when the Worker reaches terminal `failed`, `succeeded`, `cancelled`, or `stopped`; stopped release requires the Worker stop checkpoint in the same command settlement.
- Preserve Worker identity for pause, resume, and reconciled interruption. Retry after terminal failure creates a new Worker with `retry_of_worker_id`. `RetryStoppedWorkerModel` requires explicit Retry, the expected terminal availability-stopped Worker and vacant slot, no Run `recovery-required` state, a freshly recomputed Run state that admits Worker dispatch, current provider capability and dispatch authority for the same approved concrete provider/model, a fresh Invocation context record, and a provider-recompiled Sealed Invocation; it atomically creates and slots a new Worker with `retry_of_worker_id` and the same exact Delegation task. `ReplaceStoppedWorkerModel` instead requires one approved Worker-targeted Model-change Control request, the expected terminal stopped Worker and vacant slot, no Run `recovery-required` state, a freshly recomputed Run state that admits Worker dispatch, the request's new approved Run profile revision and policy epoch, selected concrete provider/model, fresh Invocation context record, and provider-recompiled Sealed Invocation. It atomically activates that profile and epoch, creates and slots a new Worker with `replaces_worker_id` pointing to the stopped Worker and the same exact Delegation task, and marks the request `applied`.
- Never replace a stopped Worker automatically, mutate its model, reuse its Invocation context record, or label replacement as fallback. Reject replacement while the old Worker is nonterminal, its effects are uncertain, the task slot is occupied, the profile or epoch is stale, or provider capability cannot represent the new contract.
- Continue to use the accepted Worker commands and status family. A Worker may submit an attributed result, but the Execution owner validates task, plan, policy, Workspace fingerprint, result shape, and current authority before moving it to `succeeded`.

### Waypoint Parent And Model Attribution

- Key `waypoint_parents` by Project and Run, and make `parent_id` unique. Create the Waypoint parent atomically with the Run and preserve it until the Run remains as immutable history.
- Keep only current Resume capsule, runtime session, latest Model attempt, creation, and recovery references on the Waypoint parent row. Derive Waypoint parent availability from Run, Runtime handoff, provider availability, and recovery state rather than adding a duplicate status family.
- After admission and durable Recovery Journal `started`, append one Waypoint-parent or Worker admitted provider-dispatch attempt to `model_attempts` and flush it immediately before crossing the adapter boundary. Attribute exact Run, Waypoint parent or Worker, provider, model, settings, Run policy epoch, prompt version and hash, Invocation context record, Capability versions, limits, and boundary classification. Distinguish `proven-not-started`, `provider-invocation-observed`, and `invocation-uncertain`; provider rejection or failure is observed invocation evidence, not policy rejection. This pre-boundary record gives crash recovery an exact owner for a possible external request, late evidence, usage, and uncertainty. The AgentRuntime decision owns the exact invocation and result schemas.
- `RecordWaypointParentProviderUnavailable` and `RecordWaypointParentModelUnavailable` accept only the matching closed normalized `provider-unavailable` or `model-unavailable` observation, append the typed warning snapshot, derive the Waypoint parent unavailable, close Waypoint-parent and new-Worker dispatch, and add respectively `WAYPOINT_PARENT_PROVIDER_UNAVAILABLE` or `WAYPOINT_PARENT_MODEL_UNAVAILABLE`. They move a dispatchable Run to `blocked` with cause `PROVIDER_UNAVAILABLE` but preserve every existing condition. Generic provider rejection or failure does not invoke either command. Neither command creates a Run `stopped` state.
- The accepted Run policy at the blocking sequence fixes whether each already active Worker may finish its current bounded task or must halt dispatch at its next Worker-safe boundary. Such Workers cannot expand scope or spawn work. Their exact results enter `waypoint_parent_result_queue` and cannot be interpreted, accepted, or dispatched onward until the Waypoint parent recovers.
- `RecoverWaypointParentModel` requires either a successful explicit availability probe for Retry of the same concrete model or an `applied` Waypoint-parent Model-change request, plus a fresh Invocation context record, provider capability proof, reconciled effects, and the expected blocked Run version and condition identity. Any availability probe that crosses an external boundary is itself an attributed Capability effect with its own Command ID, Recovery Journal entry, result, and usage or cost; it cannot be an unrecorded model call. The command removes only the exact `WAYPOINT_PARENT_PROVIDER_UNAVAILABLE` or `WAYPOINT_PARENT_MODEL_UNAVAILABLE` condition proved resolved, then reruns the complete blocker and pending-control evaluator. The Run remains `blocked` when any other condition remains and reaches `running` only when no other blocker, recovery condition, or pending control prevents dispatch. Only then does it restore dispatch and drain queued results in order through later Waypoint-parent invocations; automatic fallback remains prohibited.

### Control Requests

- Store immutable intent and payload plus a directly queryable accepted Control request lifecycle and append-only transition history. Retry after a terminal result creates a new linked Control request. An `uncertain` request preserves identity until conclusive reconciliation; abandonment does not rewrite it as failure.
- Store `run_id` for every request. Enforce target shape with `target_kind`: a Run target has no child target, a `parent` target has the same Run's required Waypoint parent `parent_id`, and a Worker target has the same Run's required `worker_id`. Checks and composite foreign keys prevent cross-Run or cross-Project targets.
- Use `control_request_dispatches` to link domain selection to an exact `runtime_handoff_id`. Delivery attempts and acknowledgements remain in the handoff ledger. Use `control_request_outcomes` only for the attributed domain interpretation that advances Control-request lifecycle.
- Add `worker-stop` and `model-change` as distinct Control-request kinds. Worker stop targets one exact Worker; Model change targets one stopped Worker or the Waypoint parent. `/model` and the graphical picker submit the same typed Model-change Control request and cannot mutate already-started attempts.
- Enforce Run cancellation as a Run-targeted Control request selected through `RequestRunCancellation`. No Worker-targeted cancellation kind is introduced by a model-unavailability warning; Change request remains the only task-level replanning path.
- Use the closed Model-change lifecycle `pending-approval -> approved -> applied`, `pending-approval -> rejected`, `pending-approval -> superseded`, or `approved -> superseded`; `applied`, `rejected`, and `superseded` are terminal. `SubmitModelChange` creates `pending-approval` with exact target, selected provider/model, resolution source, expected Run, target, profile and policy versions, and whether the target is a Waypoint parent or stopped Worker. `ApproveModelChange` validates Capability, credential availability, policy, scope, and current target versions, then records an immutable approved Run profile revision and new policy epoch that are not current until apply. `RejectModelChange` records the attributed reason and changes no profile. `SupersedeModelChange` closes a stale or replaced request; no adapter delivery or provider call is part of this canonical lifecycle.
- `ApplyWaypointParentModelChange` requires the approved request, expected healthy or blocked Waypoint parent and Run versions, a portable boundary with zero in-flight Model attempts and Tool invocations, and no incompatible pending control. It atomically activates the approved profile revision and policy epoch, updates the parent's selected provider/model for future parent invocations, and marks the request `applied`; it never changes an in-flight or historical invocation. Subsequently dispatched Workers without an explicit model override inherit the parent's then-current model at dispatch. Existing Workers and every explicit Worker override remain unchanged. For an unavailable parent, the separate `RecoverWaypointParentModel` command must still remove the exact availability condition and recompute blockers.
- `ReplaceStoppedWorkerModel` is the only apply command for a stopped-Worker Model-change request. It changes only the linked replacement Worker. Rejection, supersession, stale preconditions, another blocker, or unavailable Capability creates no replacement and selects no fallback.

### Physical Tables

Execution adds the following owner tables to `slopstop.db` under the key, transition, and migration rules of ADR 0006:

| Family | Tables |
| --- | --- |
| Run | `runs`, `run_slots`, `run_recovery_settlements`, `run_status_transitions`, `run_status_transition_conditions` |
| Waypoint parent | `waypoint_parents`, `waypoint_parent_result_queue` |
| Worker | `workers`, `worker_slots`, `worker_replacements`, `worker_stop_checkpoints`, `worker_status_transitions`, `worker_status_transition_conditions` |
| Control request | `control_requests`, `control_request_model_changes`, `control_request_status_transitions`, `control_request_status_transition_conditions`, `control_request_dispatches`, `control_request_outcomes` |
| Attribution and policy | `model_attempts`, `run_profile_revisions`, `run_policy_epochs` |

- Store each `run_recovery_settlements` row as an Execution-owned link from the exact `ApplyRunRecoveryReconciliation` receipt and removed recovery condition to the accepted Evidence reconciliation, prior and recomputed Run state, complete blocker-input fingerprint, retained conditions, and resulting transition. It copies no Evidence payload and cannot remove an unrelated condition.
- Store each Model-change request's target union, selected provider/model, resolution source, expected versions, approved `run_profile_revisions` and `run_policy_epochs` references, inheritance/override mode, and applied parent or replacement-Worker reference relationally in `control_request_model_changes`. The approved revision and epoch remain immutable and non-current until the exact apply command settles.
- Give every `run_policy_epochs` row one exact `(project_id, run_id, run_discipline_decision_id)` reference. A later epoch may retain the same discipline decision or select a newly appended decision accepted by Run preparation or amendment; prior epochs and their references remain immutable.
- Keep Delegation plan revisions and tasks, Resume capsules, runtime sessions, Run workspaces, Process jobs, and effect records in their own owner decisions. These Execution tables store exact references without pre-empting those schemas.

### Action Availability

- Compute one versioned live projection for each Project, Waypoint, Action family, and Action version. It is derived and cannot be set by a command or accepted as canonical status.
- Include in its input fingerprint the Project lifecycle, readiness, persistence health, Writer or observer freshness, Waypoint state and Entity version, blocking relationships, Run slot, Action-required contracts, applicable policy preparation, Capability and provider availability, Run-workspace and Budget availability, Evidence gates, recovery state, and every evaluator version.
- Permit a non-authoritative cache keyed by that complete input fingerprint. `BeginAction` and `PrepareAutomaticAction` carry the observed projection version and fingerprint, then re-evaluate availability against current authoritative inputs during command settlement. A stale projection, missing input, or broken evaluator never authorizes Run creation.

## Consequences

- Run, Worker, and Control-request current state remains directly queryable while append-only transitions and attempts preserve exact attribution and history.
- Slot projections make duplicate active Runs and Workers structurally difficult without coupling Execution lifecycle to Waypoint or Delegation-plan aggregates.
- Keeping one logical Waypoint parent across recovery prevents runtime-session or model-call churn from appearing as duplicate supervision.
- Worker stop and linked replacement preserve task history without adding `stopped` to Run lifecycle or mutating a terminal Worker, while durable result queuing lets independent Workers reach the fixed boundary when their Waypoint-parent model is unavailable.
- Exact revision, policy, Workspace, Evidence, and recovery preconditions make commands larger, but prevent stale approvals and model output from silently gaining authority.
- Workspace mechanics, Process jobs, AgentRuntime schemas, prompt and context behavior, plan content, measured limits, and the detailed Execution-to-Evidence handoff remain with their dedicated map tickets.
