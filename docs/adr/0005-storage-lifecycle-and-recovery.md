# ADR 0005: Storage Lifecycle And Recovery

- Status: Accepted
- Date: 2026-08-26
- Decision owners: Pedro Mesquita

## Context

Each Project has separately owned canonical and runtime databases but must remain recoverable as one user-visible body of state. There is no cross-database transaction, storage operations may be interrupted, and missing or broken data must never become a fresh Project silently. The packaged Windows persistence probe proved quiescent `VACUUM INTO` backup and staged restore, rejection of interrupted output, atomic ordinary migration failure, restart idempotence, and application-level refusal of newer, missing, or corrupt schema metadata. The product still needs one logical contract for lifecycle, manifests, activation, recovery, retention, and destructive deletion.

## Decisions

- Keep `Close`, `Archive`, and `Delete SlopStop data` separate. Close ends only the live access session and releases processes, database handles, and the writer lease. Archive is a reversible canonical Project-lifecycle transition that requires quiescence, preserves all state, and permits read, backup, export, restore, delete, and later reactivation. Delete is a physical storage operation, not a lifecycle state.
- Give backup, export, migration, restore, import, runtime reset, and delete one durable `Storage operation` contract. Its journal lives outside every generation it may change and records `requested`, `quiescing`, `staging`, `verifying`, `ready-to-activate`, `activating`, and `completed`, with distinct `blocked`, `failed`, and `recovery-required` outcomes.
- Apply ADR 0013's `project-operation` Effect contract and exact `project-storage` declaration class to every physical Storage operation. Keep that Effect partition, its Project-operation Evidence scope, Recovery Journal, observations, evaluations, decisions, and sole current Effect outcome in `application.db` beside the Storage-operation journal. The Storage operation remains lifecycle authority; Effect Evidence explains the physical side effect and cannot create another Storage status. This partition uses the operation journal's order and revision and never fabricates a Run, Run workspace, Project sequence, Writer generation, cross-database foreign key, or cross-database transaction.
- Before any Storage-operation step copies, transforms, activates, removes, or otherwise touches physical bytes, flush Effect intent and `started`, append the ADR 0013 `started-before-boundary` observation, separately accept current `EFFECT_STARTED_UNSETTLED`, and only then append the exact Storage-operation step referencing that decision/version. Registry, operation, generation, Project snapshot, backup, export, import-source, and deletion-tombstone declarations use ADR 0013's logical keys; `storage_locations` paths never enter the declaration.
- Quiesce before every operation that copies, transforms, activates, or removes Project persistence. Stop admission of new canonical commands and runtime dispatches, finish database transactions, settle or explicitly block active effects, drain durable handoffs, and close both databases. Active work, bounded-wait exhaustion, or any uncertain effect yields `blocked`; no operation forces cancellation or invents a safe boundary.
- Seal every Project snapshot with a manifest containing an opaque snapshot identity, Project and database-lineage identities, source Storage generation, canonical and runtime schema/migration heads, file sizes and SHA-256 hashes, Project sequence, runtime waterline, producing application version, and UTC creation time. Exclude raw credentials and machine-local paths. Never overwrite an existing snapshot path or mutate an input package.
- Call an output a Project backup or export only when both databases and the manifest are present, quiescent, integrity-checked, and mutually consistent. When canonical persistence is verified but runtime persistence cannot be recovered, permit a clearly incomplete Canonical recovery package; it can enter only safe mode for the same Project and becomes normal storage only after repository validation and explicit runtime reset.
- Use staged forward migration only. Create and verify a pre-migration backup, migrate copies of both databases with packaged migration resources, verify integrity, identities, schema heads, migration history, and domain invariants, then activate the complete pair as one new Storage generation. Non-interactive, data-preserving paths may run automatically; paths requiring a decision or accepting possible loss require explicit confirmation. Never downgrade an unsupported-newer schema.
- Restore only into the same Project and database lineages. Verify the package, migrate older supported schemas in staging, preserve the current generation, and activate a newly identified generation only after all checks pass. Import transports the same Project and database lineages to another installation but creates destination-local Repository binding, Workspace, and Storage-generation identities. A duplicate Project identity blocks import, and activation waits for validated Git common-directory and fingerprint evidence.
- Activate a complete generation through one authoritative active-generation change; never activate one database from a normal migration, restore, or import independently. If activation outcome is uncertain, reconcile the operation journal, active-generation record, manifests, and checksums before classifying it completed, safely resumable, reversible, or recovery-required. Never repeat activation blindly or select an older generation automatically.
- Keep Project persistence read-only in Storage safe mode whenever either database is not healthy. Permit only diagnosis, Canonical recovery export, forward migration, restore, rollback, runtime reset, and delete. A healthy canonical database with irrecoverable runtime persistence may undergo explicit runtime reset: quarantine the old runtime data, create new Runtime-database and Storage-generation identities, invalidate incompatible handoffs, and never replay uncertain effects.
- Create fresh defaults only when no prior-state witness exists. Registry records, repository markers, manifests, generation directories, database/WAL/SHM files, local snapshots, deletion tombstones, and unfinished-operation journals all force an explicit missing, corrupt, conflict, or recovery-required result instead of initialization.
- Resume after a crash only from evidence. Before activation, an idempotent owned step may continue or its proven staging output may be discarded. At or after activation, and after the first destructive delete step, cancellation is unavailable until reconciliation proves a safe completion or recovery path. Unknown partial outputs remain quarantined rather than being reused or removed.
- Apply no automatic retention in v1. Protect the active and immediately prior generations. Keep manual snapshots, external exports, and pre-migration or pre-restore backups until explicit deletion; numeric limits and automatic pruning require measured Evidence.
- Delete only after quiescence and explicit confirmation of exact scope. Refuse while Runs, uncertain effects, pending handoffs, unresolved Integration, or managed worktrees with unintegrated changes exist. Offer but never require a final export. One exact delete Effect arm owns one-or-more declared generation members and one deletion tombstone; each generation is an explicit ADR 0013 resource member, never a nullable set or path. Delete Project generations, internal snapshots, Project logs/traces, registry records, Project credential references, and machine-local SlopStop markers, removing registry/markers last. Never delete the Git repository, managed worktrees, tracked `.slopstop` files, external exports, or shared application credentials.
- Keep a deletion tombstone and operation journal outside the Project directory until every requested local artifact is removed. A partial failure remains recovery-required and blocks fresh initialization. Successful completion removes the final Project-linked local witness so later onboarding of the same repository creates a new Project identity unless an external export is explicitly imported.
- Protect portable exports with authenticated encryption and a user-supplied passphrase by default because Project databases may contain prompts, source excerpts, model output, and Evidence. Permit an unencrypted export only after a specific warning and confirmation. Internal backups rely on operating-system storage permissions but follow the same credential/path exclusions.

## Consequences

- Storage operations are slower and require temporary disk space because live databases are never migrated, restored, or imported in place.
- Users retain explicit control over interruption, rollback, runtime reset, destructive deletion, and unencrypted export; the product cannot silently choose data loss to recover availability.
- A valid canonical database remains inspectable when runtime persistence fails, but normal mutations and execution wait for a complete healthy generation.
- Physical directories, tables, indexes, active-generation switching mechanics, and measured numeric limits remain for the physical persistence-layout decision; this ADR fixes logical states, authority, and proof requirements.
