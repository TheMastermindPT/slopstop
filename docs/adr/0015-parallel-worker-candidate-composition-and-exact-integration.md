# ADR 0015: Parallel Worker Candidate Composition And Exact Integration

- Status: Accepted
- Date: 2026-08-26
- Decision owners: Pedro Mesquita

## Context

ADRs 0007 and 0011 authorize a Task DAG and bounded parallel Workers, while ADR 0010 already separates Worker-delta, Candidate-review, Completion, and Integration-applicability Evidence. ADR 0013 requires Integration to own physical apply and its Effect lifecycle. The missing contract is how independent Worker results become one immutable Candidate, how physical resources support fan-out safely, and how an exact approved Candidate reaches one target without treating worktrees, Git operations, or technical Evidence as apply authority.

Before this decision, ADR 0008 bound one Run workspace to one physical resource and required every mutation lease to name a Worker. That could not represent sibling task resources, deterministic composition, Candidate materialization, or an Integration target outside the Run workspace. This decision supersedes those singular-resource and Run-only lease clauses while preserving the separation between ADR 0006 Application Workspace identity and Execution's Run workspace.

## Decisions

### Owners And Authority

- Keep one logical `RunWorkspaceId` per Run as the immutable Repository binding, baseline, and coordination aggregate. Execution owns its physical resource collection, Task-input snapshots, Worker lifecycle, immutable Worker results, composition operations, Candidate materialization, validation-copy provisioning, and cleanup orchestration.
- Let Evidence own resource fingerprints, Worker deltas, Composition evaluations, Candidate deltas and fingerprints, Candidate technical review, Integration applicability, Effects, Recovery, and Artifact state. Accepting exact `COMPOSITION_COMPLETE` Evidence may publish the immutable Candidate in that Evidence transaction; it cannot authorize user review or physical apply.
- Give the Application coordinator's Candidate user-review component sole authority for Candidate user decisions. Give Integration sole authority for Integration targets, target-specific approval requests and decisions, attempt lifecycle, and physical working-tree apply.
- Adapters may provision worktrees, compose immutable Artifact manifests, materialize trees, inspect targets, and perform an admitted apply. They return attributed observations and never select Worker results, resolve conflicts, approve Candidates, decide applicability, or move canonical owner state.
- A path, worktree, branch, ref, patch hash, content digest, or materialized tree is never a domain identity. Hashes and fingerprints verify immutable records and observed bytes only.

### Run Resource Graph And Repository Coordination

- Give every physical Run resource one opaque `RunWorkspaceResourceId`. Use the closed kinds `coordination`, `task`, `composition`, `candidate-materialization`, and `candidate-validation`. Each has exactly one typed principal: Run, Worker, Composition, Candidate materialization, or Candidate validation copy.
- Keep the resource lifecycle `provisioning -> ready -> active -> quiescing -> retained -> cleanup-requested -> removed`, with `ready | retained -> active`, and permit `cleanup-requested -> retained` only through an explicit cancellation before cleanup Effect `started`. `missing`, `conflicting`, `broken`, and `recovery-required` are explicit non-clean states. `removed` is terminal; recreation receives a new resource identity.
- Derive one canonical `RepositoryResourceKey` from Repository binding, Git common directory, and worktree administrative identity, never from a path alone. Coordinate worktree bytes separately from declared shared keys such as Git common-directory administration, refs, hooks, caches, services, and credential references.
- Replace Run-only mutation leases with `RepositoryMutationLeaseId` and a checked owner union. A Run-resource arm names one exact resource and Worker or Execution operation principal. An Integration-target arm names one exact Integration attempt, target, Repository resource key, and target fingerprint. At most one active lease exists for one canonical resource key, independent of owner arm.
- Treat `RepositoryResourceKey` as lease coordination, not a new ADR 0013 Effect-resource vocabulary. Every effectful lease user must also declare the matching ADR 0013 `run-workspace-resource` or `integration-target-resource` key and every other shared resource it can touch.
- Parallel worktree file mutation is allowed only on distinct task resource keys. Permit at most one active mutating Effect per canonical resource key even when the same lease owner planned several effects. Shared Git common-directory reads may coexist; provisioning, removal, ref mutation, hook mutation, or another incompatible shared access serializes through ADR 0013 resource-key access. No undeclared shared access is treated as independent.
- Provisioning, materialization, validation-copy creation, and cleanup follow ADR 0013's intent/start/pre-boundary-decision/owner-record/physical-boundary protocol. A failed, interrupted, or uncertain operation does not produce `ready`, `retained`, or `removed` resource authority.
- `RequestRunResourceProvisioning` creates the typed resource and inert provisioning operation. After the Effect pre-boundary decision, `StartRunResourceProvisioning` appends the owner start before adapter work; `RecordRunResourceProvisioningOutcome` records attributed terminal observations; `SettleRunResourceProvisioning` alone consumes current Effect and fingerprint Evidence to reach `ready` or an exact non-clean state. Candidate materialization and validation-copy requests add their specialized immutable Candidate source rows but use this same provisioning protocol.
- `ActivateRunResource` moves `ready | retained -> active` only while atomically creating the exact Worker, Process-job, Composition, materialization, validation, or read-claim binding that uses it. `QuiesceRunResource` closes new dispatch and moves `active -> quiescing`; `RetainRunResource` requires no active claim, job, lease, attempt, or unresolved Effect and moves `quiescing -> retained`. No generic status command exists.

### Task Inputs And DAG Continuity

- Give each immutable input tree one opaque `TaskInputSnapshotId`. Store exact Run, accepted plan and policy epoch, source kind, source baseline, tree-manifest Artifact, fingerprint, canonicalization version, and creation command. The closed source kinds are `run-baseline`, `predecessor-candidate`, `worker-result`, and `task-input-composition`. `predecessor-candidate` is available only to the exact successor Run created by `BeginCandidateChangeRun` and binds the reviewed predecessor Candidate, change request, manifest, and fingerprint as that Run's immutable starting baseline.
- Bind every accepted Delegation task to exactly one snapshot before its Worker can be created. Root siblings in one fan-out group use the same snapshot identity. One-predecessor tasks use a snapshot sealed from that exact accepted Worker result. Multi-predecessor tasks use a snapshot sealed only from accepted `COMPOSITION_COMPLETE` Evidence over every required predecessor result.
- A Task-input composition fixes a predecessor-closed set, one accepted Worker result per required `DelegationTaskId`, the plan's topological order, stable task-identity tie-break, exact compositor identity/version/implementation hash, baseline, input manifests, conflict policy, limits, and expected output schema. Its complete result manifest and fingerprint become the downstream snapshot; missing or non-favorable input never becomes an empty snapshot.
- Normalize every snapshot's exact accepted ancestor-result closure into `task_input_snapshot_ancestor_results`, keyed by snapshot and ancestor task with the exact `WorkerResultId`, source snapshot, and topological position. `run-baseline` and `predecessor-candidate` start a new DAG with no ancestor rows. A `worker-result` snapshot contains that source result plus its source snapshot's closure; a `task-input-composition` snapshot contains exactly its selected member results plus their closures. Sealing the snapshot creates the complete set atomically; no consumer chooses between alternative source tables.
- Require each dependent Worker result's input fingerprint to equal its bound snapshot. During Candidate fan-in, reconstruct the exact selected ancestor closure for each member and require its ordered `WorkerResultId` membership and source Task-input snapshot or Composition identities to equal the lineage sealed into that member's input snapshot; require that exact ancestor projection, not the whole linear accumulator, to equal the member's input snapshot fingerprint. Fingerprint equality never substitutes for lineage identity. Incomparable sibling changes already present in the accumulator are permitted only when their normalized effective paths and declared resources are disjoint; any overlap conflicts. This admits forks such as `A -> B` and `A -> C` while preserving exact base continuity for both branches.
- Retry or replacement creates a new Worker and task resource but reuses the exact snapshot unless an approved plan revision creates a different task or input authority. It never replaces a selected result inside an existing Composition or Candidate.
- Use `SealTaskInputSnapshot` for one direct source, `BeginTaskInputComposition` for multiple predecessors, and the bounded `BindFanOutTaskInputs` transaction for the complete sibling set. These commands are not a generic batch and cannot add tasks or edges to the accepted plan.

### Immutable Worker Results

- Add nonterminal Worker state `result-pending`. `SubmitWorkerResult` closes new dispatch, creates one attributed `WorkerResultProposalId`, stores it as the Worker's exact current proposal with the resulting Worker version, and moves `running -> result-pending`; it does not claim success.
- `AcceptWorkerResult` requires that exact current proposal, Worker version, task, input snapshot, task resource, input and result fingerprints, current accepted complete Worker-delta evaluation, immutable result-tree manifest, Artifact states, tests, change classifications, terminal Effects, usage, policy epoch, and producer provenance. It atomically creates one `WorkerResultId` bound to the proposal, moves `result-pending -> succeeded`, releases the slot, and queues the result for the Waypoint parent.
- `ResumeWorkerAfterResultRejection` may move `result-pending -> running` only with the exact current proposal and accepted `WORKER_DELTA_OUT_OF_SCOPE`, `WORKER_DELTA_EXTERNAL_CHANGE`, `WORKER_DELTA_STALE`, `WORKER_DELTA_MISSING`, `WORKER_DELTA_CONFLICTING`, `WORKER_DELTA_BROKEN`, `WORKER_DELTA_TRUNCATED`, or `WORKER_DELTA_REJECTED` Evidence, current plan/epoch, remaining budget, a fresh Sealed Invocation, and safe resource/effect state. It supersedes that proposal as current without deleting it. `ConfirmRunCancelled` may instead move a safe `result-pending` Worker to terminal `cancelled`, preserve and close its proposal history, and release its slot in the same settlement; unresolved effects keep the Run out of terminal cancellation. Terminal retry creates a new Worker and can never gain the earlier Worker's result identity.
- A Worker result references, rather than copies, the exact Worker delta, accepted observation/evaluation/decision, changed-path rows, result-tree manifest, validations, Effects, Artifacts, and usage. Make at most one accepted Worker result per Worker. Candidate selection fixes at most one Worker result per Delegation task.

### Composition And Candidate Publication

- Give every deterministic composition operation one opaque `CompositionId` and exactly one typed purpose: `task-input` or `candidate-generation`. A Candidate purpose also has one opaque `CandidateGenerationId`; a failed or incomplete generation is never a Candidate with zero members.
- Use one Evidence family `composition` with the closed verdicts `COMPOSITION_COMPLETE`, `COMPOSITION_CANCELLED`, `COMPOSITION_CONFLICTING`, `COMPOSITION_MISSING_INPUT`, `COMPOSITION_STALE`, `COMPOSITION_TRUNCATED`, `COMPOSITION_UNCERTAIN`, `COMPOSITION_REJECTED`, and `COMPOSITION_BROKEN`. Key current authority by exact Run-workspace Evidence scope and `CompositionId`.
- Fix every Composition member before physical work: exact task, Worker, Worker result, Worker delta evaluation, source snapshot, result manifest, delta Artifacts, topological position, and stable tie-break. Candidate generation also fixes the exact required output-task frontier derived from the current accepted plan and Completion obligations. Membership is the complete predecessor closure of that frontier, contains exactly one selected accepted result for every required frontier and ancestor task, and contains at most one result per accepted task; an arbitrary non-empty predecessor-closed subset is not publishable.
- Treat overlapping normalized effective paths from incomparable tasks as a structural conflict even when a tool could choose an order. For dependent tasks, require exact prefix/input continuity. A successful byte composition does not claim absence of semantic conflict; only whole-Candidate validation can provide technical acceptability.
- Use a versioned deterministic compositor over immutable Artifact manifests. Canonical Candidate construction never reads live Worker resources, invokes `git merge`, changes a branch/ref/index, or treats a materialized checkout as authority. Physical staging may create immutable candidate file Artifacts under a journalled Composition operation, but publication uses only its terminal verified manifest.
- Use the Composition operation lifecycle `planned -> provisioning -> composing -> awaiting-evaluation -> complete`, with nonterminal `cancel-requested` and `recovery-required`, plus terminal `cancelled`, `conflicting`, `incomplete`, `stale`, `failed`, and `broken`. Only the owner command `SettleComposition` consumes exact accepted current Composition Evidence to move its evidence-dependent lifecycle. Map `COMPOSITION_COMPLETE -> complete`, `COMPOSITION_CANCELLED -> cancelled`, `COMPOSITION_CONFLICTING -> conflicting`, `COMPOSITION_MISSING_INPUT | COMPOSITION_TRUNCATED -> incomplete`, `COMPOSITION_STALE -> stale`, `COMPOSITION_REJECTED -> failed`, and `COMPOSITION_BROKEN -> broken`. `COMPOSITION_UNCERTAIN` moves or keeps the operation in `recovery-required` until superseded by conclusive current Evidence.
- `BeginTaskInputComposition` or `BeginCandidateGeneration` fixes membership and creates `planned` without physical work. `RequestCompositionProvisioning` moves `planned -> provisioning` and uses the resource-provisioning protocol for every required staging resource. After those resources are exactly `ready`, `ActivateRunResource` binds each one to this exact Composition and moves it to `active`. Only after every required resource is `active` and the Effect pre-boundary decision is current may `StartCompositionAttempt` append the owner start and move `provisioning -> composing`; `RecordCompositionAttemptOutcome` appends attributed terminal facts and moves to `awaiting-evaluation`. Evidence then records and decides the Composition observation, and `COMPOSITION_COMPLETE` additionally requires current terminal `EFFECT_COMPLETED_AS_DECLARED` decisions for every declared Composition Effect. `SettleComposition` consumes that exact current decision and never performs, repeats, or repairs physical work.
- `RequestCompositionCancellation` closes new provisioning or physical dispatch and moves any unpublished `planned | provisioning | composing | awaiting-evaluation` Composition to `cancel-requested`. Before Effect `started`, exact no-effect proof permits `COMPOSITION_CANCELLED`; after start, every Composition Effect must first reach a conclusive terminal decision. Partial, uncertain, missing, or broken Effect authority moves settlement to `recovery-required`, never `cancelled`. `SettleComposition` alone consumes `COMPOSITION_CANCELLED` to reach terminal `cancelled`. `ConfirmRunCancelled` requires every Composition to be terminal or to have an explicit unresolved recovery condition that keeps the Run in `recovery-required`.
- For Candidate purpose only, accepting `COMPOSITION_COMPLETE` atomically creates one immutable `CandidateDeltaId`, next non-negative Candidate version, exact ordered Worker-result membership, normalized create/update/rename/delete manifest with expected source state and Artifact references, source baseline, compositor contract, provenance manifest, `CandidateFingerprintId`, and Candidate Evidence scope. It creates no Candidate-review evaluation or user decision.
- Cancellation and Candidate publication serialize under the Writer. Cancellation accepted first prohibits publication. Publication accepted first preserves the Candidate, but a subsequently accepted cancellation reverse-invalidates every still-current Integration-applicability evaluation for that Run and makes pending Integration requests or approvals stale; the cancelled Run cannot obtain new Completion or Integration authority. Export or salvage remain separate decisions.

### Conflicts And Resolver Work

- Store each conflict as immutable typed Evidence with kind `textual`, `structural`, `policy`, or `materialization`, exact members, paths or rules, conflict fingerprint, and complete/truncated state. A conflict creates Attention and no Candidate.
- Resolution is new scoped work through ADR 0011 amendment authority. A Resolver requires a new task, accepted plan revision, policy epoch, Task-input snapshot, Worker, budget, Effect declaration, and Sealed Invocation. It never edits an old Composition, conflict, Worker result, or Candidate.
- A replacement Composition references the predecessor generation, selected Resolver result, and every retained original result. It creates new Evidence and, on success, a new Candidate version.
- Count identical conflict fingerprints over one root conflict lineage against a cumulative Run limit fixed by the initial approved policy. A later epoch may reduce remaining authority but cannot reset consumed attempts. Exhaustion keeps the Run blocked with `CANDIDATE_CONFLICT_REPEATED` and exact Attention.

### Candidate Materialization And Fresh Review

- `RequestCandidateMaterialization` allocates one read-only Candidate resource in `provisioning` from the immutable Candidate file manifest and available Artifact-state versions. The same transaction creates one immutable `CandidateMaterializationReviewRequirementId` fixing the Candidate, materialization, Candidate Evidence scope and fingerprint, accepted plan and policy epoch, review contract and rules, required whole-Candidate producer kinds, and approved limits. The common resource-provisioning commands reconstruct it, verify every byte and the complete Candidate fingerprint, and permit `ready` only after favorable settlement. A mismatch is `CANDIDATE_MATERIALIZATION_MISMATCH` or `CANDIDATE_BROKEN`; never repair the Candidate in place.
- Validation receives a separate `CandidateValidationCopyId` and resource rebuilt from the same Candidate. The copy limits blast radius but grants no repository mutation permission. Capture complete pre/post fingerprints; any tracked, relevant untracked, Git, or undeclared cache mutation makes that producer attempt contaminated or scope-violating even when its process exits zero.
- Keep ADR 0010 Candidate-review verdicts as the sole technical acceptability authority. Every Candidate-review observation and evaluation references the exact immutable materialization review requirement created before its producer checks. `CANDIDATE_ACCEPTABLE` requires a closed Candidate generation, exact materialization, fresh independent whole-Candidate validation, current Findings, terminal Effects, current rules/evaluator, and unchanged Candidate fingerprint. Worker-local green Evidence never substitutes.

### Candidate User Review

- Give each Candidate one Candidate user-review aggregate with current request, current decision, state, and Entity version. Use states `pending`, `accepted`, `rejected`, and `changes-requested` backed by immutable `CandidateUserReviewRequestId` and `CandidateUserDecisionId` records. This canonical user authority is distinct in name and ownership from ADR 0010's technical `candidate-review` Evidence family.
- `SubmitCandidateForReview` requires current accepted `CANDIDATE_ACCEPTABLE` Evidence and exact Candidate generation, manifest, fingerprint, Finding snapshot, Completion-contract revision, and review Artifact set. It binds that exact technical evaluation decision/version and creates or replaces the current pending request by compare-and-set; prior requests and decisions remain immutable.
- `AcceptCandidate`, `RejectCandidate`, and `RequestCandidateChanges` append one typed user decision against the exact current request and its technical Candidate-review decision/version. Acceptance rechecks that technical decision as current at command time, is target-neutral, and is neither Completion acceptance nor Integration approval. Reject and request-changes grant no apply authority.
- `RequestCandidateChanges` also creates one immutable `CandidateChangeRequestId`. It does not mutate the Candidate, reopen or redirect a Run, create a task, or amend a plan. When the originating Run is nonterminal and amendment-compatible, new work requires a separately submitted and approved Run amendment. When that Run is terminal, `BeginCandidateChangeRun` may create one new draft Run under normal Run-slot authority only while compare-and-set proves that exact request and `request-changes` decision remain the current Candidate user-review tuple. It records cause `CANDIDATE_CHANGES_REQUESTED`, an immutable link to the predecessor Run, Candidate, user decision, and change request, and an exact `predecessor-candidate` Run baseline reconstructed only from that Candidate manifest and fingerprint. A terminal Run never re-enters `amendment-requested`. The resulting Candidate version receives independent technical and user review.
- A later Candidate user-review request against the same Candidate invalidates the prior current user acceptance. The request transaction reverse-invalidates every still-current Integration-applicability evaluation depending on the earlier review version or user decision to the exact stale or not-authorized verdict. A later technical Candidate-review invalidation preserves the immutable user decision as history but likewise invalidates dependent Integration applicability. Integration requires the technical Candidate-review decision bound to the user acceptance to be the exact current `CANDIDATE_ACCEPTABLE` decision; any replacement evaluation, even another acceptable one, requires a new user-review request and decision. No Candidate version inherits a sibling or predecessor version's user decision.

### Exact Integration Approval And Apply

- Give Integration one stable `IntegrationTargetId` for an exact Repository binding and working-tree target. ADR 0010's `integration-target-fingerprint` Evidence family owns immutable target fingerprints and their current accepted evaluation; each includes tracked files, relevant untracked files, index state, ref/HEAD identity, conflict state, and canonicalization version. A new fingerprint does not change target identity.
- Use only v1 apply mode `working-tree-only`. It may change the explicitly approved working-tree paths but never stages the index, creates a commit, moves or merges a ref, pushes, resets, cleans, stashes, or resolves an existing conflict. There is no default or automatic Git operation.
- A dirty target can be eligible only when the exact dirty manifest and non-overlap proof are visible in the approval request and policy permits it. A conflicted target is never applicable in v1. An overlapping dirty path, missing target input, ambiguous untracked state, or changed index/ref is explicit non-favorable Evidence.
- `RequestIntegrationApplicabilityEvaluation` creates ADR 0019's immutable Integration applicability request and one inert read-only capture for the exact Candidate, current technical and user review, Completion authorization, originating Run lifecycle, target, working-tree-only mode, expected paths, dirty-target policy, proposed apply declaration and exact Effect/resource-key set, and direct approved limits. The in-process observer crosses no process, credential, remote, cost, mutation, lease, or Effect boundary. It records complete tracked, relevant untracked, index, ref/HEAD, conflict, dirty-manifest, canonicalization, and before/after consistency facts or the exact unsupported, missing, ambiguous, truncated, uncertain, or broken result. Evidence records and decides that target observation from source kind `applicability-request`, then evaluates applicability against the same immutable request.
- `SubmitIntegrationForApproval` requires current `INTEGRATION_APPLICABLE` Evidence for the exact non-superseded Integration applicability request, exact accepted Candidate user decision, Completion authorization, originating Run lifecycle version with no pending or accepted cancellation, Candidate and target fingerprints, working-tree-only mode, declared Effect/resource keys, expected changed paths, policy, limits, canonical approval-manifest fingerprint, and proof that no application proof already exists for this Candidate version, target, and mode. Any changed request input requires another applicability request and evaluation before submission.
- `ApproveIntegration` or `RejectIntegration` appends one immutable target-specific decision. One approval authorizes at most one `IntegrationAttemptId`. A target, Candidate, Completion, policy, Effect declaration, or approval-manifest change requires a new applicability evaluation, request, and approval.
- `PrepareIntegrationAttempt` rechecks that no application proof exists for this Candidate version, target, and mode, then atomically creates one inert attempt in `preparing` and grants its Integration-target Repository mutation lease. `RecordIntegrationPreparationOutcome` records only the Integration-owned attributed capture envelope under that lease. Evidence then uses `RecordIntegrationTargetObservation` and `DecideIntegrationTargetEvaluation` to append and accept the exact target fingerprint. `SettleIntegrationPreparation` consumes the current accepted Integration-target fingerprint decision/version regardless of verdict and repeats every authority, proof-absence, target, and Run cancellation/lifecycle check under the Writer fence. Only `TARGET_FINGERPRINT_CAPTURED` referencing the same exact fingerprint identity approved by the request through complete canonical equality may move `preparing -> prepared` while retaining the lease. Missing, ambiguous, truncated, rejected, broken, stale, dirty-unapproved, conflicting, already-applied, or reapplication-forbidden settlement records the matching terminal no-effect result and releases it. A crash after lease grant leaves a directly queryable `preparing` attempt plus lease and no Effect start; startup reconciliation settles that same preparation or retains a broken blocker, never starts apply implicitly.
- Only a `prepared` attempt with its active lease may enter ADR 0013 Effect intent. Follow ADR 0013 exactly for each apply Effect: flush intent and `started`, then record and accept `EFFECT_STARTED_UNSETTLED`. `RecordIntegrationPreApplyObservation` next records an Integration-owned final target-capture envelope under the still-active lease; Evidence records and decides it through the Integration-target fingerprint family. `StartIntegrationApply` requires that exact current `TARGET_FINGERPRINT_CAPTURED` decision to reuse the approved fingerprint identity, rechecks every authority and proof-absence condition, appends the Integration apply-start, moves `prepared -> applying`, and only then crosses the adapter boundary. A failed post-Effect recheck appends no apply-start and moves to `awaiting-reconciliation`, where conclusive `EFFECT_NOT_STARTED` or broken Evidence decides the result. The adapter applies the immutable Candidate file manifest and Artifacts, never a Candidate materialization resource. Every create, update, rename, or delete must use a platform-specific conditional mutation primitive that holds the relevant OS file/directory exclusion while it verifies the complete expected source kind, path, byte Artifact, file identity, symlink target, and absence/presence condition and performs that one mutation. A platform or filesystem that cannot provide this indivisible compare-and-mutate contract is unsupported for exact Integration and crosses no physical boundary. A mismatch stops before that operation; if an earlier operation already crossed, the attempt is partial or uncertain rather than conflict-free. `RecordIntegrationApplyOutcome` records the attributed physical observations and moves `applying -> awaiting-reconciliation`; lost continuity records an uncertain observation rather than replaying apply.
- Use Integration-attempt states `preparing`, `prepared`, `applying`, `awaiting-reconciliation`, and `recovery-required`, plus terminal `applied`, `not-applied-stale`, `not-applied-conflict`, `not-applied-failed`, `not-applied-already-applied`, `not-applied-reapplication-forbidden`, and `cancelled-no-effect`. `SettleIntegrationPreparation` owns `preparing -> prepared` or an exact pre-Effect terminal no-effect transition. Map stale approval, authority, or target identity to `not-applied-stale`; dirty or changed target content to `not-applied-conflict`; missing, ambiguous, truncated, rejected, broken, or unsupported conditional apply to `not-applied-failed` while retaining the exact diagnostic; and proof races to `not-applied-already-applied` or `not-applied-reapplication-forbidden`. `StartIntegrationApply` owns `prepared -> applying | awaiting-reconciliation`. `RecordIntegrationApplyOutcome` owns `applying -> awaiting-reconciliation`. `FinalizeIntegrationAttempt` may also close `preparing | prepared` when cancellation or authority invalidation occurs before any Effect start. Every not-applied state and `cancelled-no-effect` requires conclusive no-effect Evidence. `started`, partial, or uncertain physical work can reach only `awaiting-reconciliation` or `recovery-required` until current Evidence proves a terminal result.
- `FinalizeIntegrationAttempt` closes `preparing | prepared` in the matching terminal no-effect state only when no target capture remains active and every allocated Effect is absent or has current `EFFECT_NOT_STARTED`; it releases the lease atomically. From `awaiting-reconciliation | recovery-required`, it consumes exact terminal Effect decisions and target observations. Conclusive Evidence moves to the matching terminal state; unresolved or broken Evidence moves or keeps the attempt in `recovery-required`. `applied` requires an immutable application proof over before target fingerprint, Candidate identity/fingerprint/operation manifest, expected result fingerprint, observed result fingerprint, mode, changed paths, terminal Effect decisions, and lease release. Creating that proof atomically reverse-invalidates any current `INTEGRATION_APPLICABLE` row for the same Candidate and target. Current `INTEGRATION_ALREADY_APPLIED` instead references the existing exact application proof when the target still matches its observed result; a later target drift yields `INTEGRATION_REAPPLICATION_FORBIDDEN` for this Candidate version and target. Neither verdict starts a new approval request, attempt, lease, or Effect, and equal bytes alone are insufficient.
- A failed or uncertain apply never rewrites Completion, technical Candidate-review Evidence, Candidate user review, Integration approval, or Effect Evidence. Retry requires conclusive current safety, a new applicability evaluation when any input changed, a new approval request and decision, new attempt and Effect identities, and no automatic replay.

### Retention, Cleanup, And Recovery

- Retain Run resources while a typed live hold requires their physical bytes for a Task-input snapshot, unsettled Worker result, Composition, materialization, validation request/copy, Evidence rerun, export, salvage, or unresolved Effect. A settled Worker result, Candidate, Completion authorization, Candidate user review, or Integration record retains resource identity, fingerprints, manifests, Artifacts, and provenance but becomes a provenance-only reference after current Artifact Evidence proves every required immutable byte is independently available; provenance-only references do not block physical cleanup. Integration never reads a live source resource.
- `RequestRunResourceCleanup` captures exact terminal resources, final fingerprints, query schema/version, dependency-query fingerprint, and zero byte-requiring-hold result, then moves those resources to `cleanup-requested`. That state is a Writer-fenced cleanup reservation: every command that could create a new byte-requiring hold must reject or first invoke `CancelRunResourceCleanup`. Cancellation may return the resource to `retained` directly only before any cleanup Effect intent exists. After intent, it must use ADR 0013 `RequestEffectCancellation` and may release a prepared cleanup lease or return to `retained` only after every allocated Effect has exact current `EFFECT_NOT_STARTED`; an unresolved Effect keeps cleanup and its lease blocked. `PrepareRunResourceCleanup` re-runs the same indexed query and atomically acquires the exact resource lease before the Application coordinator may record Effect intent against that lease. A crash with a prepared lease and no Effect `started` is directly reconcilable and performs no cleanup implicitly.
- After the accepted pre-boundary Effect decision, `StartRunResourceCleanup` appends the owner start before byte or Git-administration removal; after that start no new hold or cancellation may be admitted until terminal settlement. `RecordRunResourceCleanupOutcome` captures attributed physical observations, and `SettleRunResourceCleanup` alone consumes current Effect and resource Evidence to reach `removed` or `recovery-required` with the exact partial, uncertain, or broken condition.
- Cleanup removes managed bytes and Git administration only. It preserves identities, manifests, Artifacts required by retention, Evidence, decisions, and history. Partial or uncertain cleanup enters `recovery-required`; it never becomes `removed`.
- Startup reconciliation covers nonterminal resources, Composition operations, Candidate materializations, validation copies, repository leases, and Integration attempts before any conflicting dispatch or apply. Missing or broken state emits its exact diagnostic and never degrades to absent, clean, or safely removed.

### Keys And Constraints

- Key every identity by `(project_id, opaque_id)` and every aggregate transition by owner, non-negative sequence, command receipt, Project sequence, and resulting Entity version. Hashes and fingerprints are not unique identities.
- Make `(project_id, run_id)` unique for the logical Run workspace, but permit many resources. Give each resource a closed principal-kind discriminator and exactly one kind-matching principal child; creation transactions and opening integrity checks reject a root with zero or multiple children. Give immutable lease grants candidate key `(project_id, repository_resource_key, repository_mutation_lease_id)`. Key `repository_active_mutation_leases` by `(project_id, repository_resource_key)` and use that full candidate key as its foreign key to one grant with exactly one Run-resource or Integration-target owner child. The Run-resource owner child carries the exact resource's canonical Repository resource key; a composite foreign key over Project, resource, resource key, lease, and owner principal proves it equals the grant key. Conclusive release deletes that active projection in the same settlement that appends the immutable release; no projection can point at a grant for another key and no second grant can occupy the key first.
- Key task-input bindings by exact accepted `(project_id, run_id, run_policy_epoch_id, delegation_task_id)`. Bind one snapshot; prove task membership in the selected plan and predecessor closure. A Worker composite foreign key requires the same task, epoch, and snapshot.
- Require every Task-input snapshot to have exactly one typed source child matching its `run-baseline`, `predecessor-candidate`, `worker-result`, or `task-input-composition` discriminator. Composite foreign keys prove an ordinary source belongs to the same Run, plan/epoch lineage, baseline, and selected predecessor closure. The `predecessor-candidate` arm instead proves the snapshot belongs to the unique successor Run and `CANDIDATE_CHANGES_REQUESTED` link created from that exact terminal predecessor, Candidate, `request-changes` decision, manifest, and fingerprint; no unrelated Run may adopt it.
- Key Worker-result proposals by Worker and proposal sequence, and keep the current proposal identity plus Worker version on the Worker aggregate while it is `result-pending`. Key Worker results one-to-one by Worker and bind the exact current proposal through a composite foreign key over Project, Worker, proposal, Worker version, task, manifest, and fingerprints. Bind the exact task resource and final fingerprint. Candidate membership makes `(project_id, candidate_delta_id, delegation_task_id)` unique and references exactly one Worker result through a composite foreign key proving that result belongs to the same Project, Run, and `delegation_task_id`. Store closed `member_source_kind` on `candidate_delta_members`; composite foreign keys carrying its literal value make exactly one matching source child possible, and the creation transaction plus opening checks require that child to exist. `current-epoch-result` requires the result's producing plan/epoch to equal the Candidate generation's current accepted plan/epoch, while `accepted-result-carried` requires the exact carried classification from the amendment proposal selected by that current epoch. A result from an older epoch can never pass through the direct arm. Retries cannot occupy another task's slot or create duplicate task contribution.
- Require every Composition to have exactly one typed `task_input_compositions` or `candidate_generations` child matching its purpose discriminator. Give the Composition candidate key carrying its Project, Run, accepted plan, policy epoch, and purpose. Key Composition members by Composition and position, make task unique, and use composite foreign keys carrying that full current lineage to bind the accepted Delegation task and Worker. Give each member a closed `current-epoch-result | accepted-result-carried` source discriminator with exactly one typed child. The direct arm binds the exact Worker result and current accepted Worker-delta decision from the same plan and epoch; the carried arm binds the exact older result and delta through the current epoch's accepted carried-result classification. Key `composition_member_ancestor_bindings` by dependent member and ancestor task. One composite foreign key selects the exact ancestor Composition member and `WorkerResultId`; another targets the single normalized `task_input_snapshot_ancestor_results` relation for that dependent member's `TaskInputSnapshotId`, ancestor task, result, source snapshot, and position. Require the complete ancestor closure and its positions to equal accepted topological order, then separately require its deterministic projection fingerprint to equal the dependent input fingerprint rather than the whole prior accumulator. Candidate generation and Candidate delta are one-to-one only after accepted `COMPOSITION_COMPLETE`.
- Key Composition current evaluation by `(project_id, run_workspace_evidence_scope_id, composition_id)`. A current row references one exact accepted evaluation decision and complete observation; rejected or pending observations never become complete authority.
- Key each Candidate materialization review requirement by Project plus opaque identity and make its Candidate-materialization pair unique. Its complete candidate key binds Candidate, materialization, Candidate Evidence scope/fingerprint, accepted plan and policy epoch, review contract/rules, required producer kinds, and limits. Language checks, validation-copy requests, Candidate-review observations, evaluations, decisions, and current rows carry this requirement identity through composite foreign keys; none can invent a later requirement or point to a sibling materialization.
- Key Candidate user review by Candidate delta and store current request/decision/state/version with deferred composite foreign keys to immutable records. Every user command compare-and-sets that tuple. Each request binds the exact technical Candidate-review evaluation decision/version checked as current at submission. Each decision uses a composite foreign key over Project, Candidate, request, and that same technical decision/version, then rechecks it as current; a decision cannot silently switch the request from T1 to T2. Make `(project_id, candidate_user_review_request_id)` unique in `candidate_user_decisions`, so one request can receive only one action. `pending` requires a current request and null decision; `accepted`, `rejected`, and `changes-requested` each require one decision for that exact current request whose action respectively equals `accept`, `reject`, or `request-changes`. Later technical invalidation never makes the immutable user-decision row internally invalid, but Integration applicability requires its bound technical decision to remain the exact current `CANDIDATE_ACCEPTABLE` decision. Bind each immutable `candidate_change_request` to the immutable request and `request-changes` decision; its creation transaction separately compare-and-sets the current aggregate tuple without giving history a foreign key to mutable current state. Make `(project_id, candidate_user_decision_id)` unique in `candidate_change_requests`. Make change-request identity and successor Run independently unique in `candidate_change_runs`, and use composite foreign keys to prove the request, decision, Candidate, predecessor terminal Run, successor draft Run, Project, Waypoint, and `CANDIDATE_CHANGES_REQUESTED` cause all agree.
- Key Integration targets by Repository binding and normalized target identity without making target fingerprints unique. Key each applicability request, read-only capture, approval request, and decision by opaque identity. One active capture belongs to one applicability request; one decision settles each approval request and one attempt consumes each accepted approval. The applicability request owns its exact ADR 0019 policy, resolved values, optional headroom decision, proposed apply declaration, Effect/resource keys, and request fingerprint. Key its current projection by Candidate/version, target, and mode. A replacement with no nonterminal attempt appends one immutable applicability-request supersession, supersedes any pending or accepted approval request, invalidates old applicable Evidence, and compare-and-sets the projection in one transaction; an accepted approval decision remains immutable history but grants no start. A nonterminal attempt prohibits replacement. Composite foreign keys bind its target observation and applicability evaluation to the same Candidate, target, reviews, Completion authorization, Run lifecycle, request, limits, and captured fingerprint. Bind preparation settlement, attempts, and Effects to the exact current accepted Integration-target fingerprint evaluation/decision/version, Candidate scope/fingerprint, Candidate user decision, Completion authorization, applicability request and decision/current version, target fingerprint, mode, policy, limits, and resource keys.
- Key application proofs one-to-one by terminal applied attempt and unique by exact Candidate identity/version, Integration target, and mode, regardless of later target drift. Submission, preparation, and start each prove absence of that tuple before any Effect may start. Proof creation atomically reverse-invalidates earlier applicable authority. `INTEGRATION_ALREADY_APPLIED` must reference that proof and matching observed target result; later drift cannot authorize reapplication of the same Candidate version, so a new Candidate version is required and matching content hashes alone are insufficient.
- Key each retention hold by opaque identity, exact resource, hold kind, byte-requiring or provenance-only mode, owner version, creation receipt, and optional release receipt. Require exactly one kind-matching typed owner child. Every typed child carries the held resource and references the owner's immutable dependency or consumption row for that same resource through a composite foreign key; a consumer of resource A cannot place its hold on resource B. Any consumer that may need physical bytes starts with a `byte-requiring` hold. Converting it to provenance-only atomically releases that hold and creates one linked replacement hold referencing the exact current Artifact-state versions and owner Evidence that prove every required byte independently available; direct provenance-only creation for a byte consumer is forbidden. Key cleanup resources by request and stable position. Owner-transition checks require each resource to remain terminal/retained with the same final fingerprint, no indexed byte-requiring hold, a live cleanup reservation, and no later hold-admission command before physical cleanup starts.

### Issue 61 Closure

| Ticket requirement | Explicit answer |
| --- | --- |
| Immutable composition | Exact predecessor-closed Worker results, snapshots, Artifact manifests, order, compositor, conflicts, and fingerprints create one Candidate only after accepted Composition Evidence. |
| Parallel mutation | Each Worker has a distinct task resource and shared accesses are coordinated by typed resource keys; no live worktree enters Candidate authority. |
| Review Evidence | Candidate materialization and a separate fingerprint-checked validation copy support fresh whole-Candidate Evidence. |
| User approvals | Candidate user acceptance, Completion acceptance, and target-specific Integration approval are separate immutable authorities. |
| Target checks | Applicability and first apply bind one complete target fingerprint including dirty/index/ref/conflict state; pre-apply change requires re-evaluation and reapproval, while post-proof drift forbids reapplying that Candidate version. |
| Mutation lease | One repository lease union coordinates both Run resources and Integration targets without fabricating a Run workspace for apply. |
| Exact Integration | V1 applies only the approved Candidate manifest to working-tree paths; no automatic staging, commit, ref, merge, push, reset, clean, or stash exists. |
| Recovery | Attempt and Effect identities are consumed at start; partial or uncertain apply enters recovery and is never replayed automatically. |
| Post-application proof | One terminal proof per Candidate version, target, and mode binds before, Candidate, expected, observed, Effect, and lease-release authority; later drift cannot reapply that version. |
| Retention | Indexed byte-requiring holds preserve physical resources through active validation, export, salvage, and recovery; settled Candidate, Completion, and Integration provenance survives independently available Artifacts, and cleanup is explicit and journalled. |

## Consequences

### Positive

- Parallel Workers gain real isolation without making branches, worktrees, or merge tools authoritative.
- Dependent and multi-predecessor tasks retain exact input continuity and provenance.
- Candidate review proves the final combination, while Integration remains an explicit target-specific action with conservative recovery.
- Dirty targets, conflicts, crashes, cancellation, and cleanup all fail visibly rather than degrading to clean or applied.

### Costs

- Resource, Composition, Candidate-review, and Integration lifecycles add several identities and exact references.
- Immutable Artifact manifests and retention holds consume storage until explicit cleanup.
- V1 deliberately excludes automatic commits, refs, merges, pushes, staging, stashing, and conflict resolution.

### Rejected Alternatives

- Do not share one mutable Run checkout across sibling Workers.
- Do not compose from live worktrees or use `git merge` as Candidate authority.
- Do not let Candidate technical review, Candidate user acceptance, Completion acceptance, Integration applicability, or Integration approval substitute for another.
- Do not apply from a materialization resource or accept equal bytes as exact Integration provenance.
- Do not auto-retry uncertain apply, auto-resolve conflicts, or clean resources by age.
