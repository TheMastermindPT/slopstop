# SlopStop Domain Context

Use these terms consistently in code, schemas, tests, and UI copy.

| Term | Meaning |
| --- | --- |
| Project | One saved Git repository and its local SlopStop state; visualized as a galaxy. |
| Project lifecycle | The independent active or archived axis of one Project; archiving preserves identity and history and never means close, delete, ready, or healthy. |
| Project backup | A sealed, checksum-verified snapshot of both quiescent Project databases and their identity/schema manifest; it contains no raw credentials. |
| Project restore | A staged, verified activation of a Project backup for the same Project and database lineages that preserves the previously active generation. |
| Project export | A portable Project backup stored outside application data for reinstall or machine transfer; it excludes machine-local paths and raw credentials. |
| Project snapshot | One immutable backup or export with its own opaque identity, sealed manifest, and checksums over an exact Storage generation. |
| Application registry | Reconstructible installation-local location and active-generation data used to find and operate Storage; it is never canonical Project truth. |
| Canonical database | The Project's `slopstop.db`, which owns directly queryable current state, immutable Accepted revisions, command settlement, and Canonical events without requiring event replay. |
| Runtime database | The separately owned `mastra.db`, whose private runtime state cannot decide canonical Project truth. |
| Database lineage | The opaque identity of one canonical or runtime database history, preserved by same-Project restore and replaced only by a contract that explicitly permits it. |
| Canonical recovery package | An explicitly incomplete package containing verified canonical Project truth when runtime persistence is unavailable; it opens only in safe mode and requires explicit runtime reset before normal use. |
| Persistence health | The independent healthy, migration-required, recovery-required, missing, corrupt, identity-conflict, unsupported-newer, unavailable, or broken state of one canonical or runtime database. |
| Storage generation | One activated physical pairing of canonical and runtime Project persistence; restore, import, or runtime reset creates a new generation without redefining Project identity. |
| Storage operation | One durable backup, export, migration, restore, import, runtime-reset, or delete attempt whose journal and ADR 0013 `storage-operation` Effect partition remain together in `application.db`, outside every Storage generation it may alter. |
| Storage safe mode | The read-only Project mode entered when either database is not healthy; only diagnosis and explicit storage-recovery operations remain available. |
| Prior-state witness | Any registry record, marker, manifest, generation, database sidecar, local snapshot, or unfinished-operation journal proving that missing files must enter recovery instead of fresh initialization. |
| Deletion tombstone | The external operation witness retained while destructive Project-data deletion is incomplete; it blocks fresh initialization until deletion either completes or is recovered. |
| Feature | A durable objective container with its own Frame record, goals, constraints, revisions, and Waypoint star system. |
| Waypoint | A durable project objective represented as a planet; never an agent session or temporary worker task. |
| Application coordinator | Deterministic software that owns canonical project state, scheduling, policy, budgets, and recovery. |
| Waypoint parent | The single logical AI supervisor of one Run, preserving identity across safe restart, resume, compaction, runtime session replacement, and model changes. |
| Worker | One bounded, attributed, non-nesting attempt to perform an exact Delegation task. |
| Turn Machine | The Execution-owned internal sequence controller for one Waypoint parent or Worker; it is reconstructed from durable records, is not a domain aggregate, and never replaces Worker state authority. |
| Run | One supervised attempt to perform an exact Action version on one Waypoint. |
| Run slot | The current exclusive claim that permits at most one nonterminal Run for a Waypoint without adding execution state to the Waypoint aggregate. |
| Action | A reusable capability such as Frame, Research, Implement, or Validate; not a mandatory pipeline stage. |
| Action availability | A versioned live projection of whether one Action is available, blocked, unavailable, or broken for one Waypoint; it is recalculated from authoritative inputs and never set directly. |
| Behavior Contract | One immutable accepted revision of the user-visible outcomes, examples, non-goals, limits, and failure behavior expected from an exact Waypoint Action. |
| Test Contract | One immutable accepted revision of the checks, oracles, commands, and Evidence required to prove exact Behavior Contract and Completion Contract clauses. |
| Comprehension checkpoint | The pre-approval completeness condition recorded in one sealed Run approval proposal, proving that its exact currently owned Waypoint and Behavior Contract revisions expose the consequential, ambiguous, disputed, limit, and failure expectations; it is not a separate revision aggregate. |
| Delegation plan | The just-in-time worker roles, tasks, tools, budgets, dependencies, models, and risks proposed for a Run and accepted only through generic Run approval. |
| Delegation plan proposal | One immutable non-authoritative proposal containing provisional task nodes and dependency edges; rejection or supersession creates no Delegation task identity or Task DAG. |
| Delegation plan revision | One immutable accepted version created atomically with its Delegation task identities and the only authoritative Task DAG for a Run; ready, blocked, fan-out, and fan-in are derived from it and current facts. |
| Delegation task | One immutable task node created only inside an accepted Delegation plan revision; changed content requires a new task identity, while Worker retries preserve the task identity and create new Worker identities. |
| Run approval proposal | One immutable sealed pre-decision record for initial Run preparation or a compatible Run amendment, containing exact currently owned authority references, a Delegation plan proposal, a complete resolved Run profile selection, conditions, and a canonical manifest hash. |
| Run approval view | The one user-visible projection of a sealed Run approval proposal, including its complete manifest and predecessor diff; it is sealed before the approval decision and has no authority by itself. |
| Run profile proposal | One immutable non-authoritative complete resolved Run-profile selection, including inherited values and their exact sources, sealed before approval. |
| Run profile revision | One immutable accepted Run-profile version created only from the exact resolved profile proposal selected by an approval; the current revision is reached through the current Run policy epoch, never a separate Run pointer. |
| Approval Dependency Graph | A rebuildable reverse invalidation and explanation index over exact approved references; it never accepts a plan, decides applicability, or authorizes dispatch. |
| Task input snapshot | One immutable sealed input for a Delegation task, bound to the common sibling baseline, one accepted predecessor result, or a deterministic materialization of all required predecessor results. |
| Worker result | One immutable accepted output of an exact Worker attempt, binding its Task input snapshot, result manifest, Worker delta, Evidence, Artifacts, effects, and usage without making a live worktree authoritative. |
| Composition | One deterministic operation that combines an exact predecessor-closed selection of Worker results into a downstream Task input or Candidate manifest; conflict or incomplete input creates no output authority. |
| Resolver Worker | A new Worker for a new Resolver Delegation task approved through a Run amendment request, accepted plan revision, and Run policy epoch after an input-composition conflict; it is never an implicit retry. |
| Control request | One durable typed intent whose kind fixes its target: Run pause, resume, cancellation, and Run amendment requests target the Run; Worker stop and Worker model change target one Worker; Waypoint-parent model change targets that parent. |
| Run amendment request | One Run-targeted Control request asking for a compatible replacement of current Run authority; incompatible intent is not an amendment and must use the separate Run-supersession authority. |
| Run amendment proposal | One immutable compatible Run approval proposal whose sealed children classify every prior task, Worker, result, and started effect; every corrected proposal owns a newly allocated complete child set and hash even when values repeat, and approval accepts those exact rows without moving or duplicating them under the epoch. |
| Side question | One bounded read-only question about an active Run whose answer has no execution authority; any later steering or amendment is submitted independently as its own typed intent. |
| Model attempt | One durable append-only attributed admitted provider-dispatch attempt for an exact Waypoint parent or Worker, created after command and policy admission, durable Recovery Journal `started`, and ADR 0013's accepted pre-boundary `EFFECT_STARTED_UNSETTLED` decision, immediately before the adapter boundary; it references that decision/version and distinguishes `proven-not-started`, `provider-invocation-observed`, and `invocation-uncertain` without owning execution state. |
| Sealed invocation | One immutable provider-neutral candidate containing the exact proposed identity, task, policy epoch, workspace, Invocation context record, visible tools, provider, model, budget, and completion inputs; command or policy admission may reject it before any Model attempt exists. |
| Attributed observation | One normalized immutable report with a closed versioned kind, emitted by a provider, runtime, or tool adapter and recorded by Execution against an exact invocation; it reports what was observed and owns no state transition. |
| Model availability observation | One attributed `provider-unavailable` or `model-unavailable` observation for an admitted dispatch; it is distinct from generic provider rejection or failure and may propose, but never perform, recovery behavior. |
| Model change | One Control request proposing an exact provider/model for future Waypoint-parent invocations or a linked replacement of one stopped Worker; it attaches to a Run amendment proposal, and only generic Run amendment approval may create its profile revision and policy epoch. |
| Context record | One Conversation-owned immutable record linked to an exact response message, describing what that direct response used and excluded; its `responseMessageId` contract is never reused as Execution invocation state. |
| Invocation context record | One Execution-owned immutable record of the exact purpose, prompt sources, and deterministic compiled context prepared for one Waypoint parent or Worker provider candidate; a model-based compaction uses the specialized `context-compaction` purpose and produces an artifact only for a later record. It is separate from every Conversation Context record. |
| Tool invocation | One durable attributed attempt to handle an exact model-visible tool proposal through ordered observations; an effectful invocation receives its effect-start observation only after ADR 0013's accepted pre-boundary `EFFECT_STARTED_UNSETTLED` decision, and its terminal transport observation is not semantic or effect success. |
| Effect | One stable attributed identity for one immutable declared attempt to cross a local, process, repository, credential, or external-service boundary; it has exactly one closed Effect subject and keeps intent/dispatch history separate from its Evidence-owned current outcome. |
| Effect subject | The closed discriminated union `run-worker`, `project-operation`, or `integration`; each arm requires only its exact owner, operation, scope, workspace, and before-state fields, and a fourth or generic owner arm is invalid. |
| Run/Worker effect | A `run-worker` Effect bound to one exact Run and one `run`, `waypoint-parent`, or `worker` target, plus exactly one `run-workspace` or explicit `no-workspace` binding and its matching Evidence scope; the `no-workspace` arm uses the Run's scope only to partition Effect and Recovery authority and declares no repository input, resource, or fingerprint dependency. It has no Project-operation or Integration identity. |
| Project operation effect | A `project-operation` Effect bound to one exact `artifact-removal` or `storage-operation` owner operation and Project-operation Evidence scope; it has operation-specific before state and no Run, Worker, Waypoint parent, Delegation task, or Run-workspace identity. |
| Integration effect | An `integration` Effect bound to one exact Integration attempt, Candidate version/scope/fingerprint, Integration target, Repository resource, and target fingerprint; it has no Run, Worker, Waypoint parent, Delegation task, or Run-workspace identity. |
| Effect declaration | The immutable relational declaration of one Effect's exact subject arm, authorized effect classes and scopes, typed resource keys, before fingerprints, command fingerprint, policy and Capability versions, approval, budget authority, lease/read claim or explicit none, remote idempotency contract, cancellation contract, observer versions, and terminal-proof requirements. |
| Effect resource key | One canonical typed conflict identity for a declared real-world resource and access kind. ADR 0013 alone owns the closed `EffectResourceKeyKind` vocabulary, canonical encodings, and class-specific requirements; this glossary does not copy or extend them. |
| Effect observation | One immutable attributed typed account appended by `RecordEffectObservation` together with its Recovery Journal reconciliation fact; it selects no verdict and moves no current pointer. |
| Effect reconciliation decision | A `DecideEffectReconciliation` record that accepts or rejects an exact Effect evaluation and atomically advances Effect current authority only when accepted. Its mandatory first accepted use after `started` records current `EFFECT_STARTED_UNSETTLED` before any owner-specific boundary record or physical crossing; terminal decisions happen later. Run Recovery authority may be written only for a matching Run/Worker effect. |
| Effect current outcome | The accepted Effect-family evaluation presently authoritative for one exact Effect and Evidence scope under ADR 0010; it is not a process status, command receipt, risk decision, or separate current pointer. |
| Effect dossier | A read-only projection joining one Effect declaration, Recovery Journal facts, attributed observations, Evidence history, current Effect evaluation, applicable Run Recovery evaluation, and applicable Artifact/Storage/Integration owner state; it owns no command or state. |
| Typed reconciler | An effect-class-specific adapter that observes an exact declared real-world target and emits attributed typed observations without selecting an outcome, authorizing retry, or changing any subject-owner state. |
| Worker stop | The terminal outcome for one Worker after model unavailability or an explicit stop request closes its dispatch and reaches a Worker-safe boundary; replacement uses a new linked Worker identity. |
| Run policy epoch | One immutable approved authority basis for Run dispatches that references exact independently owned revisions, the accepted Run-profile revision, fingerprints, approvals, Evidence, capabilities, budgets, task authorizations, and any sealed amendment-classification set; later restriction applies live, while added power requires another approved epoch. |
| Development discipline policy | One stable, versioned definition of strict TDD, test-first preferred, tests required, or exploration obligations and the exact replacements its policy permits; it does not itself prove Completion. |
| Application development-discipline default decision | One append-only installation-local selection of an exact Development discipline policy version; a directly queryable current pointer chooses the fallback used by later Run resolutions. |
| Run discipline decision | One immutable ordered resolution for an exact Run and accepted plan, sourced by either an Application development-discipline default decision or one exact Project-profile override; the applicable Run policy epoch selects it, and an amendment may add a later decision without rewriting history. |
| Discipline exception | One immutable one-Run proposal to replace exact default proof obligations, including Red or Green only when the selected Development discipline policy permits that replacement; applicability requires its exact accept decision and no append-only supersession, and it never changes SlopStop's own repository rules. |
| Run change classification | One immutable proposal to classify an exact change as behavior implementation, production-only remediation, test-changing remediation, or non-behavior work; current applicability requires its exact accept decision, unchanged pinned inputs, and no append-only supersession. |
| Fixed test set | The immutable Test checks, command specifications, semantics, artifacts, and hashes that an authorized production-only change must preserve. |
| Evidence family | One bounded proof domain with one typed subject and scope model and closed observation, evaluation, decision, and verdict meanings; a verdict has no meaning outside its family. |
| Trust basis | The immutable source classification, assessing authority, policy or rule version, and optional prior decision that determine whether one Evidence entry may be used for its declared scope; it is separate from the entry's domain verdict. |
| Evidence envelope | The narrow structural metadata shared by every Evidence entry: stable identity and version, attributed producer, typed subject and scope, exact fingerprints and artifact references, time, trust basis, and integrity; it contains no verdict. |
| Evidence observation | One immutable family-owned account of what an attributed producer reported for an exact subject, scope, and input. |
| Evidence evaluation | One immutable family-owned interpretation of exact observations, dependencies, fingerprints, evaluator identity, evaluator version and implementation hash, rule versions, and limits. |
| Evidence decision | One immutable family-owned acceptance, rejection, invalidation, supersession, or other authoritative interpretation of an exact evaluation. |
| Evidence current evaluation | The accepted family evaluation presently authoritative for one exact subject and `EvidenceScopeId`; a scope-keyed materialized pointer advances atomically with its append-only evaluation and decision history. |
| Evidence result-limit policy | One immutable versioned set of bounded counting dimensions and family-applicability rules used by an exact Evidence producer or evaluator; its identity and fingerprint remain historical even after a later policy is promoted. |
| Approved Evidence limit owner | The one direct immutable Delegation-plan, Run-policy-epoch, Effect-declaration, Integration-applicability-request, or Integration-approval authority that fixes the complete limits for an exact Evidence result. |
| Evidence result-limit usage | One immutable account of the applicable ceilings, retained amounts, known observed amounts, omissions, elapsed evaluator time, and complete, exhausted, or timed-out outcome for an exact Evidence observation or evaluation. |
| Convergence proof profile | One immutable versioned definition of the required typed proof roles, cardinalities, freshness rules, canonical ordering, privacy contract, and bundle-level limits for an exact class of Convergence request; it does not alter any referenced Evidence-family limit or authority. |
| Convergence proof request | One inert immutable request selecting an exact Convergence proof profile and typed proof subjects; it grants no upstream command, transition, lease, Effect, limit override, or release authority. |
| Convergence proof bundle | One stable opaque identity under a Convergence proof request with append-only immutable versions containing closed typed Execution and Evidence references, exact observed current-authority tuples, canonical positions, causal edges, counts, and fingerprints; it copies no upstream authority. |
| Convergence proof bundle validity | One bounded validation proving whether an exact bundle version matches every required immutable record and exact current authority at one held read waterline; inspection results authorize nothing after release, while a favorable consuming command must settle its own decision before releasing the same waterline. |
| Finding proposal | One immutable attributed technical claim identified by `FindingProposalId` before canonical admission; current accepted Evidence may settle it exactly once by creating or attaching a Finding, dismissing proved absence/non-applicability, or naming a changed successor proposal, while conflict or non-conclusive Evidence leaves it visibly unsettled. |
| Finding | One stable canonical Project-scoped material claim identified by `FindingId`; its current class and disposition come only from its immutable Finding decision ledger and atomic current decision pointer, never from a validator or Validation Episode. |
| Finding decision | One immutable typed decision that admits, classifies, routes, authorizes remediation, records a fix or explicit no-fix result, accepts risk, defers, marks false positive or out of scope, closes, reopens, or supersedes one Finding under exact Evidence, actor, policy, scope, and command authority. |
| Validation Episode | A rebuildable read model for one immutable Validation request, grouping attributed validator work, commands, Evidence, Findings, decisions, remediation, and rechecks; it has no table-owned status, repository mutation, or Finding authority. |
| Remediation handoff | One immutable bounded authorization containing the exact Finding authority snapshot, Evidence, clauses, scope, permissions, tests, artifacts, starting fingerprint, output contract, independence rule, and reserved limits given to a remediation Worker. |
| Finding recheck episode | One fresh independent producer attempt and accepted technical Evidence evaluation against the same material `FindingId` and a current relevant fingerprint; it may support a later Finding decision but never changes disposition directly. |
| Finding authority snapshot | One immutable direct-query result with separate ordered members for exact Finding roots/current decisions and relevant unsettled or blocking proposals, plus technical Evidence, rules, scopes, and versions; consumers rerun its scoped query against current authority and never reference a mutable projection row. |
| Materially new Finding | A problem whose stable rule, normalized claim, typed subject, semantic scope, applicability, or expected impact differs materially from an existing Finding; it receives a new correlated `FindingId` even when discovered during recheck. |
| Evidence artifact | One bounded local output with opaque durable identity, immutable integrity expectations, truncation-at-production state, and discriminated provenance as Evidence-produced, Language-produced operation output/callback/mutation result, or imported-source; a separate Evidence-owned Artifact state version records current availability, integrity, and retention. |
| Artifact source record | One immutable logical account of the original source, revision, stable relative identifier, timestamp, producer, and declared digest for an imported, historical, or research Artifact; importer identity and trust remain separate attributed facts. |
| Artifact state version | One immutable accepted evaluation of an exact Artifact's availability, integrity, and retention state; evaluations consuming its bytes depend on that exact version, while removal never deletes provenance or history. |
| Artifact retention profile | One immutable user-selectable set of Artifact byte, identity, age, purpose, reservation, and free-space rules with an exact fingerprint and stated calibration confidence. |
| Artifact retention purpose | The immutable reason bytes are retained as generated output, a durable record, or imported source; it is separate from Artifact provenance. |
| Artifact capacity reservation | One durable pre-production allocation of maximum logical bytes, physical bytes, and Artifact identities that remains counted until terminal settlement or reconciliation. |
| Artifact byte hold | One typed live dependency proving that an exact Artifact's physical bytes remain required; provenance-only references and ordinary reads are not byte holds. |
| Artifact hold-free age | The uninterrupted time since an Artifact first became available with no byte hold or since its final byte hold was released; a later hold discards the earlier interval. |
| Artifact retention proposal | One sealed, non-authoritative request to decide retention for an exact Artifact against current state, purpose, profile, usage, age, and zero-hold proof. |
| Evidence evaluator version | One immutable implementation of a stable evaluator identity, fixed by version and implementation hash; a changed implementation invalidates evaluations that depended on the earlier version. |
| Evidence producer attempt | One durable Evidence capture-attempt identity recorded before an explicit rerun, Validation, or Finding-recheck producer starts; it references but never replaces the request and Execution Worker, Process-job, Model-attempt, Tool-invocation, or Recovery-Journal lifecycle. |
| Evidence scope | One stable typed identity from the closed kinds `run-workspace`, `task-workspace`, `candidate`, `integration-target`, `artifact`, or `project-operation`; the last binds one exact Effect Project operation and never invents a Run workspace. |
| Evidence scope fingerprint | One immutable typed state identity bound to an exact Run-workspace, Task-workspace, Candidate, Integration-target, or Artifact scope; Project-operation before state instead uses its exact typed Artifact-state or Storage-generation dependencies and has no generic fingerprint arm. |
| Task workspace | The Evidence scope for one immutable Delegation task and Worker attempt over one exact Run workspace, sealed input snapshot, accepted start fingerprint, result fingerprint, and attributed producer; it is not another checkout or Execution aggregate. |
| Candidate scope | The Evidence scope for one immutable Candidate delta, its source baseline and Candidate fingerprints, and its exact selected Worker results and deltas; Task-workspace green Evidence is not Completion Evidence for the combination. |
| Candidate evaluation | One technical Evidence verdict for an exact Candidate: acceptable, changes required, blocked, stale, uncertain, or broken; user approval, rejection, and Candidate change requests are separate canonical actions. |
| Candidate materialization | One rebuildable read-only physical tree reconstructed and fingerprint-checked from an immutable Candidate manifest; it is neither Candidate identity nor Integration input authority. |
| Candidate user review | One target-neutral user decision to accept, reject, or request changes against an exact Candidate version and technical-review decision; Integration may use acceptance only while that same technical decision remains current. It is neither Completion acceptance nor Integration approval. |
| Candidate change request | One user action against an exact closed Candidate delta asking for another Candidate version; it is not a Run amendment request and cannot steer active execution. |
| Evidence gate | The check that accepted, current evidence is sufficient before implementation side effects begin. |
| Behavior contract | The accepted revisioned statement of a Waypoint's observable intent, expressed as stable clauses with public seams, relevant limits, and failure behavior. |
| Test contract | The accepted revisioned verification design for one exact Behavior contract, owning stable Test checks, approved commands, expected semantics, clause coverage, and proof phases but no test results. |
| Completion contract | The accepted revisioned acceptance design that binds exact Behavior and Test contracts to fixed typed proof obligations before a Run may complete. |
| Completion subject | The exact output Evidence evaluates for Completion: a final Candidate for every repository mutation, or an explicitly contracted typed non-repository output with current no-mutation and no-effect proof. |
| Test-first Proof Chain | A typed view linking exact accepted historical baseline and Red Evidence to current final Green, rerun, review, and exception proof for one contract clause and scope; it is not another ledger. |
| Completion Matrix | A query-only clause projection of Completion obligations, accepted causal Evidence, current terminal Evidence, applicability, and blockers; it has no editable or canonical state. |
| Completion Finding snapshot | One immutable direct-query result over exact current Finding aggregate authority, relevant unsettled or blocking proposals, and supporting technical Evidence for one Completion scope; separate member sets reference immutable Finding and Evidence records while copying observed versions and hashes, and consumers rerun the scoped query rather than treating unrelated Project sequence changes as invalidation. |
| Completion acceptance | One immutable user decision to accept, reject, or request changes against exact current Completion Evidence, contracts, and output fingerprint. |
| Completion authorization | One immutable Evidence-owned proof that an exact Run output has both current contract proof and an exact accepted Completion decision; Execution must recheck both before completing the Run. |
| Board | The canonical append-only index of ordered references to one Waypoint's conversation messages and approved typed events; it owns neither source content nor presentation. |
| Board entry | One immutable, Project-ordered reference to a Waypoint conversation message or approved typed event, with structural provenance and optional supersession but no copied source content. |
| Board position | A monotonic Project-scoped ordering value assigned by the canonical writer when it accepts a Board entry; it is separate from Board-entry identity and source time. |
| Board admission policy | The versioned canonical policy that decides which typed event references enter a Waypoint Board and which of those also appear in the Project activity feed. |
| Board read position | The monotonic highest contiguous Board position confirmed as presented in one scope; the Project feed and each Waypoint keep independent positions. |
| Typed command | A validated request that may change canonical state through the coordinator. |
| Command receipt | The durable applied, unchanged, or rejected settlement of the first distinct Typed-command fingerprint under one Project and command identity. |
| Canonical event | An append-only fact emitted only by an applied command for audit and integration; current Project state never depends on replaying it. |
| Accepted revision | An immutable, explicitly accepted version of canonical aggregate content to which directly queryable current state may point. |
| Writer generation | A durable fencing identity acquired under the operating-system writer lease and checked by every canonical command settlement. |
| Runtime handoff | A versioned immutable request crossing from canonical outbox to the runtime inbox through at-least-once delivery, stable reservation, and evidence-backed reconciliation. |
| Workspace protocol | The application-facing identity and transport boundary for Conversation, Frame, and Memory projections; it owns no Execution checkout, lease, process, or effect state. |
| Run workspace | One separate Execution-owned logical binding to an exact mode, Repository binding, baseline, physical-resource collection, and fingerprint waterline; it never reuses Workspace-protocol identity. |
| Run-workspace resource | One physical checkout, managed worktree, composition area, Candidate materialization, or validation copy within a Run workspace, identified by Repository and Git administration rather than path alone. |
| Read claim | A short-lived Process-job claim permitting observation of one Run-workspace resource at one accepted fingerprint. |
| Repository resource key | One canonical coordination identity for an exact Run-workspace resource or Integration target; a path alone is never sufficient. |
| Repository mutation lease | The durable exclusive grant allowing one exact Worker or Execution operation to mutate a Run-workspace resource, or one Integration attempt to mutate its exact target; it never expires or releases solely because time passed or a process stopped. |
| Compound code anchor | A Git-, text-, symbol-, syntax-, and optional LSP-backed code reference registered against one exact typed Evidence scope and captured scope fingerprint; historical inspection never changes its separate current-location authority. |
| Verified memory | A durable claim accepted through evidence and policy, with provenance, scope, confidence, and invalidation rules. |
| Memory Topic | A stable project-local organizer for related Verified Memories; it has navigational metadata but no trust state, and each memory has one primary topic. |
| Memory Revision | An immutable version of a Verified Memory's claim, applicability scope, limitations, verification policy, and Evidence dependencies. A semantic edit or re-verification creates a new revision; once accepted, a revision may become stale but never returns to accepted. |
| Mandatory Memory Evidence dependency | An authoritative binding from one Memory Revision to one exact accepted Evidence evaluation and decision; trusted use requires that exact authority to remain current. |
| Informational Memory Evidence reference | A provenance or navigation link from one Memory Revision to Evidence that never controls trusted-retrieval eligibility or staleness. |
| Memory invalidation event | One ordered, privacy-bounded Canonical event emitted atomically when current Evidence authority is replaced; Memory consumes it asynchronously without gaining Evidence authority. |
| Effective Memory trust | The read-time accepted, stale, or broken result for one Memory Revision after direct validation of its complete mandatory Evidence dependency set; it may expose stale before the materialized Memory transition catches up. |
| Evidence current-authority slot | One stable opaque identity for an ADR 0010 family-and-scope current row; accepted evaluations replace its versioned authority without replacing the slot identity. |
| Memory Proposal | An untrusted structured candidate produced by an attributed worker with approved `memory-propose` capability; it links claim, topic, scope, evidence, invalidation dependencies, and limitations but cannot enter trusted retrieval until user acceptance. |
| Memory Retrieval | A typed, bounded, and audited query authorized by an approved plan; trusted retrieval returns only accepted revisions whose complete mandatory Evidence dependency set remains exact current authority, while stale revisions require explicit inspection or re-verification. |
| Capability catalogue | The provenance-aware inventory of skills, tools, prompts, analyzers, servers, and extensions that may become available. |
| Recovery journal | Evidence-owned append-only write-ahead facts for one Effect's intent, start, dispatch, terminal, fingerprint, cancellation, and reconciliation observations; the facts preserve history but do not decide the current outcome. |
| Run recovery reconciliation | One accepted Evidence-backed reconciliation that removes only the resolved recovery condition, then recomputes Run state and every remaining blocker before dispatch, retry, or model replacement may continue. |
| Uncertain side effect | An operation known to have started but lacking durable proof of completion; it cannot be replayed automatically. |
| Run-workspace fingerprint | A Git, diff, and untracked-file identity binding Evidence to one exact physical resource state inside a logical Run workspace. |
| Worker delta | One stable identity per Worker for changes between its sealed input and results; explicit reruns append command-bound observations and never rewrite or replace the identity. |
| Candidate fingerprint | The immutable content identity of one exact materialized Candidate version; it verifies Candidate state but never replaces Candidate identity. |
| Candidate delta | One closed immutable manifest of explicitly selected Worker results and changes with its own identity and fingerprint, ready for separate materialization, final review, and possible Integration. |
| Integration target | One stable Integration-owned Repository and working-tree destination whose Evidence-owned current tracked, untracked, index, ref, and conflict fingerprint changes applicability but not target identity. |
| Integration applicability request | One immutable target-specific request for a strictly local read-only target capture and technical applicability evaluation before Integration approval; it grants no mutation lease, Effect, process, remote access, or apply authority. |
| Integration approval | One immutable target-specific user decision over an exact Candidate, Completion authorization, target fingerprint, apply mode, effects, and expected changed paths; it authorizes at most one Integration attempt. |
| Integration attempt | One Integration-owned admitted attempt to apply an exact approved Candidate manifest to an exact approved target under the Effect protocol; uncertainty is retained and never replayed automatically. |
| Integration application proof | The one immutable terminal proof for an exact Candidate version, Integration target, and apply mode, binding target before state, Candidate manifest, expected and observed result, Effect decisions, changed paths, and lease release; later target drift never permits that Candidate version to be reapplied. |
| Declared effect set | One immutable `DeclaredEffectSet` using ADR 0013's sole closed class and `EffectResourceKeyKind` vocabularies; consumers reference that owner and never copy, narrow, or extend its lists. |
| Process job | One coordinator-owned operating-system process attempt with a bounded invocation, output, lifecycle, effect declaration, and durable attribution; its `starting` transition follows the accepted pre-boundary `EFFECT_STARTED_UNSETTLED` decision and precedes spawn. |
| Safe checkpoint | An Execution record referencing Evidence proof that dispatch is closed, zero Model attempts and Tool invocations remain in flight, no active mutation or unresolved effect remains, and the final Workspace fingerprint is accepted. |
| Resume capsule | Persisted context sufficient to continue an interrupted run without guessing or repeating uncertain effects. |
| Resume checkpoint | A Safe checkpoint plus the exact Resume capsule, policy, Capability, budget, approval, and availability inputs needed to continue a Run. |
| Language Intelligence Service | The provider-neutral producer of workspace-isolated language-process synchronization, bounded semantic operations, attributed Language observations, and mutation proposals; it owns no Evidence verdict or repository write authority. |
| Language process set | One Execution-owned language-server lifecycle bound to an exact typed Run-workspace resource, accepted Capability contract, toolchain, and configuration; restarts create new process generations without rewriting completed observations. |
| Language ready waterline | One immutable synchronization proof over an exact Language process generation, Run-workspace resource fingerprint, document set and versions, configuration, toolchain, and Capability; no Language operation dispatches without a current matching waterline. |
| Language check | One stable consumer requirement for current Language Evidence in an exact Evidence scope and typed Run resource; retries create new fenced request generations inside the same check. |
| Language operation request | One immutable Execution-admitted `diagnostics`, `inspect-symbol`, or `find-references` request with exact arguments, dependency closure, source state, Capability, completion strategy, limits, cancellation generation, and result schema. |
| Language observation | One immutable Language-Intelligence-owned attributed terminal fact for one exact operation attempt, including ordered chunks, completion proof, members, omissions, dependency seal, and process provenance; it is input to, not authority for, Evidence. |
| Language mutation callback observation | One immutable Language-Intelligence-owned fact that an admitted Language operation received an exact mutation callback before adapter response; it preserves the callback even when no terminal Language observation follows. |
| Language mutation proposal | One immutable attributed ordered edit set with an exact callback observation, preimage or destination-absence proof, result Artifacts where applicable, scope, and fingerprints; it grants no Tool, Effect, Candidate, lease, approval, or write authority. |
| Debug observation | Registered and redacted runtime evidence from a future DAP session; supporting evidence, never red-green proof. |

## Status Families

Waypoint, Run, Worker, Control request, Run-workspace resource, Process job, Language process set, Language operation attempt, Composition, Candidate user review, Finding, Integration, Memory Revision trust, onboarding readiness, Project lifecycle, Storage operation, and persistence health statuses are separate fixed models. Logical Run-workspace health is a derived projection over its Run and resource states, not another mutable status authority. Action availability is a separate derived projection. Each Evidence family has its own versioned observation, evaluation, decision, and verdict vocabulary; there is no universal Evidence verdict. Do not reuse one family's state to stand in for another.

## Graphs

- The project graph stores durable intent, decisions, relationships, evidence, and status.
- An execution graph represents one attempt with tools, workers, retries, and approvals.
- A conversation graph stores model turns, forks, summaries, and tool results.

These graphs link to one another but never share one canonical state model.
