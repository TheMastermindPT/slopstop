# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

SlopStop is delivered as a Windows-first, cross-platform Electron desktop application. Its interface uses web technology, while operating-system and repository capabilities remain behind strict process boundaries.

## Stack

Electron, React, TypeScript, CSS Modules, pnpm workspaces, and a separate TypeScript harness utility process.

## Users

The first user is one developer working locally across Git repositories. They need to supervise several bounded agent sessions while understanding what each session is doing, why work is blocked, and which evidence supports its claims.

## Product Purpose

SlopStop combines continuity and verified memory, visible multi-agent coordination, and non-linear project control. It lets work branch, pause, reopen, and evolve without forcing every task through one fixed pipeline.

Success means the developer can steer concurrent Waypoint work, inspect durable evidence and decisions, recover safely after interruption, and trust that failed or unknown checks never appear clean.

## Positioning

SlopStop treats project intent, execution attempts, and model conversations as separate graphs. A deterministic application coordinator owns canonical project truth while resumable AI parents supervise bounded, non-nesting workers.

## Operating Context

- Local Git repositories are the implementation workspaces and historical evidence source.
- One project is active at a time; many projects may be saved.
- Projects, Features, Waypoints, and their typed relationships have visual and plain-text projections. The primary workspace uses a spatial relationship map with semantic zoom; its final visual identity remains deliberately open.
- The initial actions are Frame, Research, Implement, and Validate, but they are capabilities rather than mandatory stages.
- The user approves delegation plans, permissions, workspace mode, model changes, and integration actions.

## Workspace Interaction

- One Project is active at a time. One activity rail exposes Projects, Attention, Files, and Runs above separately placed Diagnostics and Settings; each destination replaces one sidebar rather than adding a permanent Project dock.
- Opening or changing the active Project opens Attention and frames every part of the map that requires human action without automatically selecting one item. Attention contains only decisions, approvals, permissions, conflicts, failures, blockers, and recovery, ordered first by impact and then by age; healthy activity remains in Runs.
- Semantic zoom moves from Project-level Feature regions to Feature-level Waypoints and typed relationships. The map is for orientation and selection, not the complete work surface.
- The center keeps deterministic `Map` and `Conversation` destinations and may open source previews, pinned source files, Run overviews, and Change reviews alongside them. Neither permanent destination requires browser-like backtracking to recover.
- Files presents the active Project hierarchy for inspection, not built-in editing. Opening source never sends it to a model; source, selections, and code anchors enter a Prompt packet only through explicit, removable attachments. Unsupported, binary, oversized, and unreadable files remain visible with an exact reason and external-editor action.
- Selecting a Run opens a first-class overview of its plan, Workers, progress, budget, Evidence, and Changes. In-progress Worker changes are visible as provisional read-only diffs; approval, Candidate change-request, and Integration actions appear only for a closed Candidate delta reached from its Run or Attention item.
- Logs, Process-job output, and detailed diagnostics use a collapsible lower panel scoped by default to the selected Run or Worker, with explicit Project and application alternatives. Critical failures always surface in Attention and never remain hidden only in logs.
- The right panel follows the selected Waypoint, file, diff, or Run. When open it keeps a compact summary visible, opens on `Details`, exposes only relevant contextual pages such as `Details`, `Evidence`, and `Changes`, and is resizable or collapsible on wide windows and an overlay on narrow windows. `Conversation` starts with it collapsed and opens it only for selected contextual details.
- Conversation is a full central workspace for direct model dialogue, never a Project activity feed. Project and Waypoint conversations preserve separate visible scopes and provenance; operational Run, Worker, and Board events remain in their owning surfaces instead of being automatically projected into chat. Choosing a Waypoint supplies bounded, inspectable context rather than the entire Board or repository. Model output may explain or create a reviewed proposal; it never changes canonical state directly.
- Board is a durable append-only index over one Project-wide order. Each entry belongs to one Waypoint and references either that Waypoint's conversation graph or an approved typed Execution event without copying source content; the primary Project conversation never enters Board.
- The Project activity feed is a policy-selected projection of approved typed-event entries from Waypoint Boards, never of their conversation messages, and is not another conversation or event store. Canonical state owns stable pagination, independent Project-feed and Waypoint unread positions, linear correction links, and explicit source-resolution failures, while Frame owns presentation.
- For a new Project, Conversation supports Frame from initial understanding through an approved plan. Before technical implementation detail, the model exposes its understanding of the intended end-state in clear language; the user reviews that overall summary first, then the user stories, observable outcomes, examples, and non-goals where misunderstanding may remain. Corrections revise the Decision Canvas, and only explicit acceptance creates canonical map content.
- While Frame remains unresolved, Conversation stays primary and may open an optional, visibly provisional preview of Decision Canvas decisions and relationships. That preview has no canonical authority; the Project map is created only from an explicitly accepted revision.
- Frame proves understanding adaptively. Consequential, ambiguous, corrected, disputed, surprising, limit, and failure behavior receives a bounded set of concrete prediction questions; the user may request the same proof, while clear low-risk work keeps a quick path. Multi-step walkthroughs are optional, structured expectation cards are an alternate projection rather than the primary conversation, and final approval exposes expectation-to-decision-to-plan gaps before canonical map creation.
- Model conversations may branch freely from exact messages, including nested branches that remain open without merge ceremonies. Before branch content influences a revision, the model proposes an inspectable include/exclude selection and the user may correct it; a branch never gains Project-work status or becomes a Waypoint automatically.
- Each Project has one primary Project conversation, and each Waypoint has its own separate scoped conversation. Both may branch under the same reviewed-influence rule; selecting a Waypoint can open its conversation without changing Project state, and returning to the primary conversation is deterministic.
- Before a model attempt, Conversation shows a compact inspectable and correctable Context proposal; routine messages do not require repeated full approval, but scope expansion, source, and sensitive content do. Each response exposes an immutable Context record of what was included and excluded, while token, hash, and provider-delivery details remain in a separate technical view.
- The Project menu opens a central Memory library for browse, search, filtering, proposal review, accepted and stale inspection, provenance, Evidence, history, and re-verification. Context records may link directly to referenced accepted or stale memories with deterministic return. Memory Proposals remain non-blocking and appear only in the library, never interrupting Conversation or creating Attention items; accepted Frame decisions remain canonical revisions and are never duplicated automatically as Verified Memory.
- During Frame, the Decision Canvas follows Conversation continuously. At natural conversational boundaries, coherent groups of proposed decisions receive a lightweight explicit Decision checkpoint and become Accepted revisions; final approval separately validates the complete end-state, plan, coverage, Feature, Waypoints, and relationships before generating the canonical Project map.
- The user corrects end-state, story, Canvas, and plan content through natural Conversation or comments attached to exact text in a provisional revision. The model produces an inspectable attributed diff; corrections never silently rewrite Accepted revisions or Canonical state.
- Full end-state and plan review opens a temporary central `Review` surface containing separate summary, user-story prose, annotations, proposed diffs, Decision checkpoints, technical plan, and final traceability sections. Conversation remains a permanent clean surface with deterministic return; wide windows may optionally split both views, but split is never the default.
- A persistent Conversation scope breadcrumb names the Project or Waypoint conversation and current branch. It opens a temporary searchable tree of scoped conversations and nested branches; the navigator closes after selection, preserving Conversation width, while Map and contextual links may deep-link to an exact conversation with deterministic return.
- Review expresses each end-state expectation first as one short plain-language user story and adds a Future Walkthrough narrative only for ambiguity, multi-step journeys, surprising consequences, or relevant limits and failures.
- Final Frame acceptance opens the generated canonical Project map immediately, frames newly created or changed Features, Waypoints, and relationships, and exposes the Accepted revision that produced them. Conversation and Review remain directly recoverable, while later correction creates a new revision instead of rewriting accepted history.
- Settings opens a short menu for Application, Project, and Models pages. Model credentials and catalogue, Project defaults, Run or role overrides, and the model actually used remain separate visible scopes rather than one misleading global selector.
- Automatic relationship-driven layout remains the v1 contract. Personal position pins are an accepted direction for later rich map control; they are local presentation preferences and can never change canonical relationships or priority.
- The visual treatment uses a carbon and graphite material language: matte near-black surfaces, machined edges, restrained neutral light, and scarce state color. Space, constellation, and game-progression imagery must not replace the real non-linear relationship semantics.
- The same rail destinations, selection, page content, actions, map relationships, and attention states require keyboard-accessible and plain-text projections. Small windows may temporarily prioritize the right panel as an overlay but must provide deterministic return to the center, `Map`, and `Conversation`.

## Capabilities and Constraints

- Project state, boards, revisions, evidence, memory, approvals, and recovery records are local-first.
- Electron renderer code receives no unrestricted Node access.
- The harness runs in one supervised utility process per desktop application.
- Mastra is the first agent runtime behind a project-owned adapter and is added only when its first behavior is implemented.
- The project-owned AgentRuntime is an Execution boundary. An internal Turn Machine sequences each Waypoint parent or Worker independently. Execution may prepare an immutable Sealed invocation with exact policy epoch, task, workspace, Invocation context record, visible tools, provider, model, budget, and completion inputs. Command or policy rejection creates no Model attempt. After command and policy admission, Execution durably records Recovery Journal `started`, appends the pre-boundary Effect observation, and separately accepts current `EFFECT_STARTED_UNSETTLED`. It then creates one Model attempt referencing that decision/version immediately before crossing the adapter boundary. That pre-boundary owner record distinguishes `proven-not-started`, `provider-invocation-observed`, and `invocation-uncertain`, so crash recovery can attribute a possible external request even when no provider response was recorded.
- Conversation Context records remain Conversation-owned and response-message-bound. Each separate Execution-owned Invocation context record persists the exact Waypoint-parent or Worker prompt sources, inclusion or exclusion reasons, trust and scope, token contribution, provider delivery mode, typed retrieval, recent-turn slice, compaction inputs and output, transformations, artifact hashes, and deterministic output hash used by one Sealed invocation.
- Deterministic compaction is a recorded local transformation. Any model-based compaction is instead a normal admitted `context-compaction` Sealed invocation with its own Invocation context record, Command ID, Recovery Journal, Model attempt, usage, and budget accounting. Its output is an attributed artifact eligible only for a later context record; compaction never hides or recursively triggers an unreported model call.
- Provider, optional runtime, and tool adapters emit normalized attributed observations that Execution records against exact invocations. Adapter sessions, retries, callbacks, and storage own no execution state or canonical authority. The Worker aggregate remains the durable authority for Worker state, and only validated Execution commands may move it.
- Provider observations use a closed normalized vocabulary. `provider-unavailable` and `model-unavailable` remain distinct from generic provider rejection and generic provider failure; only the explicit availability observations enter the model-recovery path, and no adapter observation changes Run or Worker state directly.
- Canonical and Mastra persistence use separate local libSQL databases with Drizzle-owned canonical migrations.
- Canonical persistence uses Project-scoped composite keys, directly queryable current aggregates, immutable Accepted revisions, append-only settlement history, and family-owned status transitions. The installation registry selects and operates versioned Storage generations but never becomes Project truth.
- Backup, export, forward migration, restore, import, runtime reset, and deletion use durable staged operations. A Project backup verifies both databases and one sealed identity/schema/checksum manifest; migration, restore, and import replace active storage only with a complete verified generation.
- A persistence fault opens the Project in read-only safe mode and never creates fresh defaults while any prior-state witness exists. Missing, corrupt, failed, recovery-required, identity-conflict, and unsupported-newer remain distinct.
- Close releases only the live session; Archive preserves a reversible canonical lifecycle; Delete SlopStop data removes only confirmed local SlopStop state after quiescence and never deletes the Git repository, tracked files, managed worktrees, or external exports.
- Portable exports use authenticated encryption by default and never contain raw credentials or machine-local paths. Automatic backup or generation retention waits for measured limits; v1 deletion is explicit.
- Test-first preferred is the product default for work SlopStop supervises in external Projects. An append-only Application default decision supplies the fallback, an accepted Project-profile revision may select an override, and each applicable Run policy epoch references one immutable resolved Run discipline decision. An approved amendment may append another ordered Run decision without rewriting decisions retained by historical epochs, invocations, Evidence, or authorizations. An exact user-approved one-Run exception may then replace only the proof obligations allowed by that resolved policy version; a separate append-only supersession relation may replace or terminate that exception without mutating its proposal or decision. SlopStop's own development remains governed independently by `AGENTS.md` and its strict red-green rules.
- Behavior uses a typed baseline, distinct expected Red, Green, final-scope Green, and risk- and Completion-contract-selected review/refactor Proof Chain at an agreed public seam. Tests-required and exact approved alternatives retain fixed obligations; non-behavior work never invents Red/Green proof.
- Behavior, Test, and Completion contracts remain separate accepted revisions pinned by each Run. Evidence evaluates their fixed versioned rules through ADR 0010 current evaluations; the Completion Matrix is only a query projection. Evidence readiness must receive an exact user Accept decision before immutable Completion authorization can exist, and that authorization never becomes duplicate Run, Waypoint, Candidate, or Integration state.
- Every repository mutation phase has one immutable accepted and currently applicable change classification. An append-only supersession relation can replace it with another immutable proposal or terminate it without a successor; neither action mutates the classification or its accept/reject/request-changes decision. Production-only remediation pins a Fixed Test set that cannot change; test-changing remediation names its permitted test scope and invalidates dependent proof; non-behavior classification is rechecked against the final Candidate and cannot hide behavior impact.
- Workers do not nest. Repository reads that become evidence, mutations, commands, analyzers, Git operations, and external effects belong to attributed workers.
- Every complete model-visible tool proposal receives one durable Tool invocation identity. Before any rewrite, Execution validates and persists the proposed effect classification, declared scope, risk class, required approval, Capability, schema, and policy result. Only an accepted proposed validation permits an explicit project-owned rewrite. Execution then persists the proposed and final authorized argument artifacts and hashes, rewrite source and reason, and original and final effect/risk classes, and reruns the complete validation on final arguments. Command fingerprint and effect declaration bind the final arguments, and adapters or providers may never rewrite them invisibly.
- Read-only typed retrieval and effectful tool execution are separate variants. Retrieval is bounded to exact authority, trust, freshness, and Workspace-fingerprint inputs; every model or tool effect carries the exact Command ID and fingerprint, Declared effect set, and Recovery Journal reference required by ADR 0008.
- Parallel Workers keep independent turn sequences. The accepted Delegation plan owns the Task DAG. The Waypoint parent proposes authorized fan-out and interprets completed fan-in, while the deterministic coordinator binds exact Task-input snapshots, isolated mutation resources, accepted Worker results, and immutable Composition authority. Provider or runtime loops may never create, join, accept, compose, or coordinate Workers implicitly.
- Run preparation has one immutable approved authority basis: the Run policy epoch. One sealed pre-decision Run approval proposal and its user-visible view contain exact currently owned Waypoint, contract, Delegation-plan proposal, complete resolved Run-profile selection, workspace, Evidence, budget, condition, and fingerprint inputs. Initial preparation always proposes every resolved profile value, including inherited values and exact sources; amendment either retains the predecessor profile revision or proposes a complete replacement. `ApproveRunPreparation` atomically creates the exact proposed profile revision with its accepted plan, tasks, DAG, and epoch. `ApproveRunAmendment` retains that profile or creates only the sealed replacement while creating the next accepted plan and epoch. The current Run profile is reached only through the current epoch. Ready, blocked, fan-out, and fan-in are derived, while the Approval Dependency Graph is only a rebuildable reverse invalidation and explanation index.
- Manual Actions create a Run only through Begin; automatic Actions may prepare only to the approval boundary. A compatible Run amendment request closes dispatch and requires a sealed Run amendment proposal whose immutable children classify every prior task, Worker, result, and started effect shown to the user. Every corrected proposal owns a newly allocated complete classification set and owner-bound hash even when all values repeat; it never reuses rows from an earlier proposal. The accepted epoch references that exact set without duplicating it. An incompatible submission persists its durable rejected command receipt and idempotency settlement but creates no Run amendment request and changes no Run lifecycle state. Contradictory intent is not an amendment and uses `SupersedeRun` before any continuing new Run. Side questions remain read-only and cannot be promoted directly, composition conflicts create Attention rather than implicit work, and a Resolver Worker requires a new task, accepted plan revision, epoch, and fresh invocation/effect identities.
- A closed `provider-unavailable` or `model-unavailable` observation stops only the affected Worker through a Worker-targeted Control request, closed dispatch, and a Worker-safe checkpoint; generic provider rejection or failure does not. Its warning preserves the warning-time role, concrete model, resolution source, reason, checkpoint, and effect snapshot; the final stop checkpoint separately records reconciled effect classifications, which may refine earlier uncertainty through Evidence without matching the snapshot. Retry, Model change, and Cancel remain available. Cancel submits the existing Run cancellation intent as a Run-targeted Control request; changing or dropping one task uses a Run amendment request and approved replanning, never a hidden Worker-cancellation meaning. A stopped Worker is terminal and releases its task slot only after effects are reconciled. Automatic fallback is prohibited.
- A Model-change Control request creates or attaches to a Run amendment request and proposal. Only `ApproveRunAmendment` creates and activates the exact Run-profile revision and new Run policy epoch. Later target-specific apply commands may update the healthy Waypoint parent or create the linked stopped-Worker replacement under that already-current epoch, but never create or activate policy authority. Existing Workers and explicit Worker overrides remain unchanged; `/model` and the graphical picker submit the same action.
- Waypoint-parent `provider-unavailable` or `model-unavailable` makes the Waypoint parent unavailable, adds only its matching `WAYPOINT_PARENT_PROVIDER_UNAVAILABLE` or `WAYPOINT_PARENT_MODEL_UNAVAILABLE` blocker, and closes new Worker dispatch without creating a Run `stopped` state. Already active Workers may follow the fixed policy to finish their bounded task or reach the next safe boundary; their results queue durably. Recovery removes only the proved availability condition and recomputes all Run blockers; it returns to `running` only when no other blocker or pending control prevents dispatch.
- Each Waypoint has at most one nonterminal Run, each Run has one logical Waypoint parent, and each Delegation task has at most one nonterminal Worker attempt. Runtime and model outputs remain attributed proposals; only typed coordinator commands, independent Evidence authority, and proven recovery records can move canonical execution state.
- The application Workspace protocol for Conversation, Frame, and Memory is separate from each Execution-owned Run workspace. A Run binds one exact logical Run workspace in read-only current-checkout, explicitly leased editable current-checkout, or isolated-worktree mode; identities and persistence are never shared between the two concepts. That logical workspace may own several typed physical resources. Parallel mutation is permitted only for Workers with distinct isolated task resources and compatible declared shared-resource access; one repository mutation lease remains exclusive per canonical resource key. External changes invalidate attribution instead of entering a Worker result or Candidate delta silently.
- The Application coordinator is the sole process and committed-action authority and owns the common Effect identity/declaration mechanism. Every effect has one stable identity and exactly one closed subject: `run-worker`, `project-operation`, or `integration`. Its immutable relational declaration records only that arm's exact owner, operation, scope, workspace and before state, plus the final authorized command, effect classes and scopes, typed shared-resource keys, policy and Capability versions, approval, budget, lease/read claim, idempotency, cancellation, observer versions, and terminal-proof requirements. Execution, the Artifact/Storage operation owner, or Integration retains the selected arm's operation lifecycle and attributed owner observations. Evidence owns the append-only Recovery Journal facts, typed effect observations, evaluations, decisions, and current outcome. Storage-operation Effect records live with the external journal in `application.db`; the other arms live in `slopstop.db`, and no cross-database transaction is assumed.
- Every physical Effect uses one order. Flush intent, flush `started`, append the `started-before-boundary` observation, separately accept current `EFFECT_STARTED_UNSETTLED`, flush the owner-specific boundary record, and only then cross the boundary. Model attempts, effectful Tool-invocation start observations, Process-job `starting` transitions, `ARTIFACT_REMOVAL_STARTED` observations, Storage-operation steps, and Integration apply-start records all reference that accepted decision/version. Artifact removal has one additional gate: `DecideArtifactStateEvaluation` must persist the accepted removal-started decision and atomically advance current Artifact state after its observation and before byte deletion. Later terminal observations and a separate terminal decision replace the current outcome. Every crash window is directly queryable; no missing or undecided pre-boundary record authorizes physical bytes, remote calls, processes, or retries. Durable `started` consumes the Effect identity permanently. An exact project command or Storage-operation request retry returns its original result/record; a later effect retry requires conclusive current Effect Evidence, matching Run Recovery, Artifact/Storage, or Integration authority for its subject arm, explicit authorization, and new identities unless a remote system proves continuation of the same idempotent request.
- Typed file, Git, `local-artifacts`, `project-storage`, process, external-service, and credential reconcilers observe and never decide. ADR 0013 alone owns the closed `DeclaredEffectSet` class and resource-key vocabularies. The Effect Dossier is a query-only projection, and ADR 0010's Effect current evaluation is the only current Effect outcome; Run Recovery appears only for a `run-worker` subject. Missing, broken, truncated, rejected, stale, uncertain, started-undecided, or observed-undecided recovery input never becomes clean, safe, absent, or completed. Compensation is a new effect; abandonment and accepted risk preserve the unresolved outcome and cannot manufacture a safety proof.
- Completed, cancelled, failed, partial, or uncertain work remains retained until explicit Integration, export, discard, or cleanup. Task resources, Candidate materializations, and validation copies remain physically held while a typed live reference from a Task input, unsettled Worker result, Composition, Evidence rerun, export, salvage, or unresolved Effect still requires their bytes. Settled Candidate review, Completion, and Integration references preserve immutable identities, manifests, Artifacts, fingerprints, and provenance but become provenance-only after current Artifact Evidence proves every required byte is independently available; provenance-only references do not block physical cleanup. An accepted Evidence reconciliation exits Run `recovery-required` only through a typed command that removes the resolved recovery condition and recomputes the appropriate state and every remaining blocker before any stopped-Worker retry or replacement. Integration applicability remains Evidence-owned while Integration alone owns target-specific approval, attempt lifecycle, physical working-tree apply, and application proof; applying a Candidate uses the same effect contract without moving Integration lifecycle authority into Execution or Evidence.
- Evidence uses one narrow structural envelope for identity, version, producer, subject, scope, fingerprints, artifacts, time, trust basis, integrity, and owner-partition order/fence. Each family owns a closed verdict vocabulary, typed observations, evaluations, decisions, and an atomic `EvidenceScopeId`-keyed current evaluation over append-only history; every current advance includes its exact accepted evaluation decision. Typed reverse dependencies cover subject, evaluator implementation, rule, Capability, limits, policy, Artifact state, and trust changes so only affected current evaluations are invalidated in the same database transaction; cross-database Storage observations are appended and invalidated before the operation continues rather than pretending to be atomic.
- Explicit Evidence reruns persist their own producer-attempt identity before dispatch and reference, rather than replace, Worker, Process, Model, Tool, and Recovery lifecycles. An accepted request that never starts remains distinct from a started attempt whose result is interrupted or uncertain.
- Language Intelligence runs only through Execution-admitted checks against exact typed Run resources. Each check uses a versioned Capability, synchronized ready waterline, immutable request generation, full source and dependency seal, and one of the closed read operations `diagnostics`, `inspect-symbol`, or `find-references`. Language Intelligence owns attributed raw observations; Evidence alone owns the `language-observation` evaluation, decision, invalidation, and current pointer. Plain push diagnostics, missing document versions, partial chunks, late results, and empty payloads without a proved completion barrier never become clean Evidence.
- A completed Language observation remains bound to its exact dependency closure and can survive a process restart when every semantic input is unchanged; in-flight work cannot. Semantic symbols and definitions are revision-bound hints that never replace Git, content, revision, or syntax authority. Diagnostics may propose independently evaluated Findings but cannot create canonical Findings or prove Red, Green, Completion, Candidate acceptance, or Integration. Every edit emitted by a language server is first a durable callback observation; only a valid normalized edit set becomes an immutable Language mutation proposal. A task-resource write requires separate Execution admission, approval, preimage-or-destination-absence recheck, lease, Tool, and Effect authority; its result must later pass Worker-result, Composition, Candidate, review, and Integration authority rather than requiring a Candidate before the task change exists.
- Finding is the sole canonical stable authority for a material validation problem. Validators first create attributed immutable Finding proposals and Evidence. Current accepted Evidence settles one proposal exactly once by creating or attaching a Finding, dismissing proved absence/non-applicability, or naming a changed successor; conflict or non-conclusive Evidence remains visibly blocking. Validators and fresh rechecks cannot alter Finding disposition. Every current class or state comes from an immutable Finding decision and atomic aggregate advance. A recheck preserves the same identity only for the same material claim; a materially changed rule, claim, subject, scope, applicability, or impact creates a correlated Finding. Blocking/advisory class, remediation, explicit fix/no-fix outcomes, risk acceptance, out-of-scope, closure, reopening, and supersession are typed scoped decisions. Remediation handoffs and rounds are exactly budgeted, exhaustion blocks without erasing history, Validation Episodes are query-only views, and Completion consumes an immutable exact Finding authority snapshot with separate Finding and blocking-proposal members, then reruns its scoped query before favorable use.
- Task-workspace proof stays bound to one sealed Worker input and accepted Worker result. Deterministic Composition selects at most one result per task, proves DAG input continuity, and publishes one immutable Candidate manifest without reading live Worker resources or using a Git merge as authority. Candidate proof technically evaluates a separately materialized and independently validated copy of that exact combination as acceptable, changes-required, blocked, stale, uncertain, or broken. Candidate user acceptance, rejection, and Candidate change requests remain separate canonical authority. Acceptance binds one exact current technical-review decision; replacing that decision requires a new user-review request and decision before Integration can become applicable again.
- Parallel Worker proof remains Task-workspace-local. Every Run with repository mutation is evaluated over one exact final materialized Candidate, including documentation-, metadata-, and test-only repository changes. Only an explicitly classed non-repository output with no mutation or effect may use an exact typed non-Candidate subject. Every relevant contract, Candidate, subject, rule/evaluator, Artifact, Finding, effect, test, discipline, change classification, fixed test set, or user-acceptance input invalidates affected Completion authority rather than restoring an older green result. V1 Integration applies only the exact approved Candidate manifest to the exact approved working-tree target; one Candidate version may produce at most one application proof for that target and mode, and later target drift requires a new Candidate version rather than reapplication. Integration never stages, commits, merges, moves refs, pushes, resets, cleans, stashes, or resolves conflicts automatically.
- Artifacts distinguish Evidence production, typed Language operation/callback/mutation-result production, and attributed import, and have Evidence-owned versioned current availability, integrity, and retention state. Missing, unavailable, removed, or corrupt bytes invalidate dependent current Evidence and never become clean. Removal is an explicit journalled `project-operation` Effect requiring both ADR 0013 Artifact resource keys; its accepted pre-boundary Effect decision precedes the `ARTIFACT_REMOVAL_STARTED` observation and separate accepted Artifact state, so no bytes may be deleted earlier. Every pending removal blocks byte use directly, and identity and provenance are preserved.
- Artifact retention uses immutable user-selected Application and Project profiles. The provisional `0.1.0-local-balanced` profile counts Project logical bytes, installation physical allocation, retained Artifact identities, and active capacity reservations; a volume floor overrides nominal quotas. Attention may create sealed proposals only for eligible generated output, while hard exhaustion blocks new production and never deletes bytes. Active byte-requiring holds always prevent removal, age restarts only after the final hold releases, and only an explicit user decision may authorize ADR 0010/0013 journalled removal.
- A code anchor with stable semantic content at a different path or range, including pure line or column drift, is moved rather than changed. Historical anchor inspection never advances current-location authority. Hashes verify integrity rather than replacing domain identity, and no universal Evidence verdict is permitted.
- Automatic model fallback, silent isolation downgrade, and failure-to-clean degradation are prohibited.
- Run pause and cancellation, Worker stop, model change, adapter replacement, and recovery close their applicable dispatch immediately. A portable pause or stop checkpoint proves zero in-flight Model attempts and Tool invocations as well as no active mutating Process job or unresolved effect; a later compensation can earn safety only through accepted Recovery proof without rewriting the original Effect outcome. Cancellation may request in-flight cancellation, but an unproven outcome remains explicitly uncertain and is never replayed or presented as clean automatically.
- Shared adapter conformance and the exact real-provider portfolio-expansion gate both prove same-model stopped-Worker retry, generic provider rejection, generic provider failure, `provider-unavailable`, `model-unavailable`, timeout, cancellation, and effect recovery before production tool scope expands.
- Live debugger implementation follows the first resilient proof; its safety seam is designed earlier.

## Brand Commitments

The product name is SlopStop. The final visual identity is deliberately open and will be selected through explicit variants. The foundation shell may use a provisional technical-cartography direction, but it must remain cheap to replace.

The current prototype direction is carbon and graphite, centered on a live graph, direct model conversation, explicit commands, contextual supervision, and full diagnostic state. Effects are reserved for focus, attention, active work, and transitions so code and operational reading remain stable. This direction remains a prototype until explicit review selects a Stable Product Identity.

## Product Principles

- Durable application state outranks model conversation state.
- Every side effect is attributable, bounded, and recoverable without touching unrelated user work.
- Evidence and failure states remain explicit; unknown is never presented as clean.
- Rich visual control always has a keyboard-accessible and plain-text equivalent.
- Frameworks remain behind project-owned boundaries so measured requirements can replace them.
- Plans earn trust by proving shared understanding of the intended end-state in plain language before presenting implementation mechanics.

## Accessibility & Inclusion

Every map, Decision Canvas, board, approval, memory, evidence, and supervision interaction requires a keyboard-accessible and plain-text equivalent. Status must use text, shape, icon, and motion in addition to color. Reduced-motion behavior is required.
