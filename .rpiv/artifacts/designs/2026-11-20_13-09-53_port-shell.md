# React port, Shell (PORT-PLAN slice 2)

## Intent

**Outcome.** The window gets the Ragnarok shell: the rune bar with its contents, a labelled rail whose Attention item is the Kenaz rune, and an Attention sidebar that the rail opens. Rule C's automatic opening waits for the Projects page (Q7). The old shell's look and its `legacy-shell` style layer go.

**Source.** `C:/Users/pedro/Documents/ragnarok-hero/PORT-PLAN.md:49`; Pedro, 2026-11-20, "continua com a fatia Shell" (relayed by the coordinator).

**Pedro's rules for this brief (relayed by the coordinator, 2026-11-20).**
1. The first question is the split into slices by risk, with `lane.mjs --paths` shown for each. Only what touches window, IPC, security or data is rigorous; visual and CSS work is fast or normal.
2. Lean contracts: each behavior's intent and one observable example. Tuning CSS to reach an approved look is evidence, never a new behavior.
3. Visual acceptance uses zoom screenshots at 80, 100, 150 and 200%, taken early, before candidate review. Before the zoom floor (`sh-s6-zoom-floor`, Q26) the lowest was 50%.
4. While building, only the affected test rows run; the whole suite runs once at the end.
5. A hand binding only for a pin row that cannot show a red; never for CSS (standing change, 2026-11-19).

**Non-goals.** The Projects list's and the add-repository flow's new look (PORT-PLAN slice 3). Any Attention data source. The Map, Files, Runs, Diagnostics and Settings surfaces. Search. The right panel.

**Constraints.** The renderer imports neither Electron nor Node. No new IPC channel and no preload change are foreseen. The security defaults of `AGENTS.md` stay. The bar stays as high as the native strip and keeps its proportions under zoom (PF-B22, PF-B42, PF-B43).

## Architecture

### What exists today (read at `a8bbf85`)

- `app.tsx:131-132` renders `<TitleBar />` and then `<ProjectsWorkspace strip={…} />`.
- `shell/title-bar.tsx`: the rune and the level-1 heading "Ragnarok"; the whole bar is `app-region: drag` and holds no control. A static drag strip sits behind the page in `apps/desktop/index.html` (PF-B36).
- `projects-workspace.tsx:233-250` is the old shell: `<main>` with a rail `<nav aria-label="Workspace">` holding one Phosphor icon button (Projects), a `<header>` with the harness status and Retry, and an `<aside aria-label="Projects">` with the list.
- The old look lives in `@layer legacy-shell`: `legacy-shell.css` (100 lines, the `--legacy-*` tokens and global rules), `global.css`, and `projects-workspace.module.css` (356 lines, 44 uses of `--legacy-*`). That last file styles the shell frame and also the Projects list, the add-repository flow and the removal view.
- `@phosphor-icons/react` is imported in eight renderer files; only the rail's icon is in the shell.
- Attention has no data: no protocol schema, no IPC channel, no harness read model names it. The only mention in source is a comment in `workspace-view.tsx`.
- Only the Projects destination has a surface. Map, Files, Runs, Diagnostics, Settings and search do not exist.
- Opening a Project shows the Conversation region (C1); there is no Map to enter.

### What the approved look asks (prototype `ragnarok-hero/src.html:25-90`, `components.css:50-248`, `DESIGN.md:266-278, 342, 347`)

- **Top bar, 44px:** the rune over the rail's width, the wordmark, a Project switch (folder, the Project's name, a chevron), centre tabs, and a search field at the end.
- **Rail:** 72px with labels at 1280px and wider, 56px with icons only below; Runa icons at stroke 1.5; the active item is a forged fill with 12px corners and the row lift; Attention is the Kenaz rune with an ember count of actionable items; Diagnostics and Settings sit apart at the bottom.
- **Sidebar, 272px** (248px below 1280px, hidden below 860px): one replaceable sidebar. Attention's has the section name, a count badge, the rune rule, the order line, the items, an empty line and a foot.
- **Rule C** (decisions log, `2026-10-05_conversation-decisions.md:192`): the Attention sidebar opens on Project or Map entry. Explicitly entering Conversation collapses it; typing, sending or reading does not. The rail item, with its actionable-only count, reopens it, and it stays open until closed. A new Project that goes straight to Frame starts with it closed.

### The shape

- **The rule:** the app's own controls never take the page's zoom below 80%. Zoom in from between two steps lands on the next step above, so as many presses of plus as of minus bring the page back to 100%. Reset goes to 100%.
- **Today** (`apps/desktop/src/main/application-menu.ts:10-13`): packaged Windows has a menu with three roles, `zoomIn`, `zoomOut`, `resetZoom`. The `zoomOut` role has no floor of the app's; it stops where Electron stops, far below 80%. Development and every other platform keep Electron's default menu, with the same role.
- **How (amended, then reworked after the intent review):** the app handles the three zoom keys itself, in the main process, before the page sees them (`before-input-event` on the window's `webContents`), and stops the event when it is a zoom key.
  - A plain function maps a key press to zoom in, zoom out, reset or nothing. It reads what the key types (`input.key`) and, for the numpad and for reset by position, which key it is (`input.code`), so it does not depend on the keyboard's layout.
  - Plain functions give the next zoom level: zoom out, zoom in to the next step above, reset. They work in Chromium's zoom levels (`getZoomLevel`, `setZoomLevel`), where a step is half a level, as Electron's roles step. 100% is level 0; 80% is `log(0.8)/log(1.2)`, about -1.224; the top is level 8.5, about 471%, which is on the half-level steps (Pedro, 2026-11-22: "Máximo nos 471%"; before, the top was 500%, level about 8.827, off the steps).
