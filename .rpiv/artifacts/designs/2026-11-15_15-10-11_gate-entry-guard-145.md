# Design: #145 a gate script that is launched through a linked path must still check

Lane: **normal** for slice 1 (Q4 (b), Pedro). `lane.mjs --paths` over its seven paths answers `fast` ("within fast limits"; slices, lines and hub signal unknown); Pedro raised it because this is gate code. The fourth script would be a second slice that `lane.mjs` answers `rigorous` for, only because its file name holds the word "migration" (Q2).

## Intent

- **Outcome:** a repository gate script either runs its check or fails visibly. It never exits 0 without checking because of the path it was launched through.
- **Scope:** the entry guard of the gate scripts under `apps/harness/scripts`, one shared owner for that guard, and the rows that prove it through a real linked folder.
- **Non-goals:**
  - no change to what any gate checks, prints or returns when it runs;
  - no change to `package.json` commands;
  - #139 (mutation survivors in the Effect gate script) and the owner of `canaryFolder` are not handled here;
  - the existing spawn rows in `check-golden-sql.test.mjs` and `check-stryker-ranges.test.mjs` are not moved (Q5).
- **Constraints:**
  - **degrade-distinguishes-broken:** "not the entry" may do nothing; "cannot tell" must fail with its own diagnostic, never report as clean;
  - **shared-vocab-union:** the guard is copied in several sibling scripts, so it gets one owner;
  - real-process rows belong to the integration project (the reclassification rule; #148), included by exact path.

## Architecture

### What is on main (read at `e6b6a76`)

Four scripts carry the same guard, not three. All are under `apps/harness/scripts`:

| Script | Guard line | Run by | Mutated by |
|---|---|---|---|
| `check-effect-diagnostics.mjs` | `:436` | `pnpm check:effect` (in `pnpm check`) | `stryker.effect-gate.config.json`, whole file |
| `check-golden-sql.mjs` | `:58` | `pnpm check:duplicates` (in `check:deep`) | none |
| `check-stryker-ranges.mjs` | `:261` | `pnpm check:mutation-ranges` (in `pnpm check`) | `stryker.stryker-ranges.config.json`, whole file |
| `check-generated-migrations.mjs` | `:97-98` (the same test, written with a local name) | `pnpm db:generate:check` in `apps/harness` only; in no gate command and not in CI | none |

No other script in the repository has this guard (`rg` over `.mjs`, `.js`, `.ts`). `apps/desktop/tests/e2e/package-smoke.mjs` has no guard: it always runs.

The guard compares two spellings of a path: `import.meta.url`, where Node has already followed links, against `process.argv[1]`, where it has not.

### What fails, measured (2026-11-15, Windows 11, Node 24.20; a probe in the scratchpad, not in the repository)

| Launch path | Guard | Same file by identity (`dev:ino`) |
|---|---|---|
| real path, relative path | true | true |
| through a **junction** to the folder | **false: the module loads, does nothing, exits 0** | true |
| drive letter in the other case (`c:`) | true (Node keeps the typed spelling on both sides) | true |
| upper-case path | not reached: Node rejects `.MJS` | - |
| `subst` drive, 8.3 short name | **not measured** (`subst` maps a drive for the whole session; 8.3 names depend on a volume setting) | - |

So the proven fault is the link case (junction on Windows, symlinked folder on POSIX). The fix below does not depend on the spelling at all, so it also covers the two forms that were not measured.

### Options

| | (a) One shared helper, file identity, three answers | (b) Library plus a bin entry that always runs | (c) Real-path comparison in each script |
|---|---|---|---|
| How | `gate-entry.mjs` answers `entry`, `imported` or `unknown`; each script hands it its run | each script loses its guard; four new bin files call the libraries; `package.json` commands and every spawn row point at the bins | each guard compares `realpathSync` results |
| Silent exit 0 possible | only if the same file reported two different `dev:ino` values | no: there is no guard | yes, for any alias form the comparison misses |
| Cannot tell | `GATE_ENTRY_UNKNOWN` on stderr, exit 1 | does not arise | not handled |
| shared-vocab-union | one owner | no guard left to own; four near-equal bins | four copies: against the decision |
| Paths | 7 (slice 1) | about 15: 4 bins, 4 scripts, 2 `package.json`, 4-5 test files | 4 scripts and the rows |
| What moves for others | nothing: script paths, commands, mutation configs stay | commands and spawn rows change; mutation configs stay only if the libraries keep their names | nothing |

**Recommendation: (a).** It gives one owner, changes one line per script, leaves commands and mutation configs alone, and makes "cannot tell" loud.

**Where (a) is weaker than (b), plainly:** (a) still has a branch that does nothing ("imported"), because the tests import these scripts. Its safety rests on file identity being exact: the same file always has the same `dev:ino` (read as bigint, as `check-golden-sql.mjs:23-26` already does). (b) removes the branch altogether and is the stricter reading of the standing decision; it costs twice the paths and changes every command. If Pedro wants no guard at all, (b) is the answer.

### The helper (shape only)

`apps/harness/scripts/gate-entry.mjs`, plain synchronous functions (no I/O beyond two `stat` calls; not an Effect program):

- `gateEntry(moduleUrl, { entry = process.argv[1], stat = statSync })` answers:
  - `"entry"` when `entry` and the module's own file are the same file by `dev:ino`;
  - `"imported"` when the process has no entry path, or the entry path is another file;
  - `{ unknown: reason }` when either file cannot be read (`cannot read <path>: <code>`), and in the three guarded cases below (second revision).
- **Guards added by the second revision (Pedro, after the coordinator's probe).** Each answers unknown, so the process writes `GATE_ENTRY_UNKNOWN` and exits 1. `gateEntry` takes the platform as a port (`platform = process.platform`). The entry path is checked first, then the module's own file:
  - **the entry path is a directory:** `entry path is a directory: <path>`. Probe P1: `node <dir>` or `node .` with a `package.json` `main` naming the script leaves the directory in `process.argv[1]`; the real entry then answered `"imported"` and exited 0 unchecked;
  - **a file with no usable file index:** `no file identity for <path>: ino <value>`, when `ino` is `0n`, `0xFFFFFFFFFFFFFFFFn` or `-1n`, on either file. Probe R2 and R3 (sourced): a filesystem without 64-bit IDs returns 0, and ReFS returns all-ones for IDs outside the 64-bit subset. Both spellings of all-ones are covered because nobody verified which one Node prints. `<value>` is the bigint as text: `0`, `18446744073709551615` or `-1`;
  - **a file with no volume serial, on `win32` only:** `no volume identity for <path>: dev 0`, when `dev` is `0n`, on either file. Probe R1 (reproduced): through `\\wsl.localhost` or `\\wsl$`, Windows Node reports `dev` 0 for every file and `ino` as the Linux inode, so two different files shared one `dev:ino` and an imported script answered `"entry"`.
  - **Why the `dev` rule is not applied off Windows:** on Windows `dev` is the low 32 bits of the volume serial, and libuv writes 0 when it cannot get one, so 0 means "no volume identity". On Linux `dev` is the device number (`makedev(major, minor)`), a real value the kernel reports; small numbers are normal there (the Docker 9p mount in the probe gave 67). Nothing shows that 0 means "unknown" on Linux, so the rule would guard nothing and could refuse a working setup.
  - **What the guards cost, plainly:** a checkout reached through `\\wsl.localhost` with Windows Node can no longer run these gates or import them in tests: every run answers `GATE_ENTRY_UNKNOWN`, exit 1. That is loud, and it is the intended trade.
- **An entry path that is not this module** (measured, Node 24.20): `node -e` and `node --input-type=module` give no `process.argv[1]`, so the answer is `"imported"`. Piped code (`node -`) gives the text `-`, which cannot be read as a file, so the answer is unknown: `GATE_ENTRY_UNKNOWN`, exit 1. Another script, a test runner or Stryker gives an existing other file: `"imported"`.
- **When a real entry could become `"imported"` (corrected by the second revision).** The earlier text here said it never could; the coordinator's probe (P1) showed one way: a directory launch, where `process.argv[1]` is the folder and not the file Node loaded. The directory guard above now turns that into unknown, exit 1. For a launch by file path the earlier reasoning holds: Node loaded the entry from the very path in `process.argv[1]`, so both are one file with one `dev:ino`. If the entry path cannot be read, the answer is unknown and the process exits 1: loud, never a silent 0.
- `runGateEntry(moduleUrl, run, ports)`: on `"entry"` returns `run()`; on `"imported"` does nothing; on unknown writes `GATE_ENTRY_UNKNOWN: <reason>` and a newline to stderr and sets the exit code to 1. It never throws for an expected case.
- Each script replaces its `if (…)` line with `runGateEntry(import.meta.url, () => { … })`; the body of its block is unchanged. `pathToFileURL` and `resolve` leave a script when nothing else there uses them.

**An import with no entry path is "imported", not "unknown":** when `process.argv[1]` is absent (`node -e`, the REPL) no file is the entry, so the answer is certain.

### The linked-folder rows on each platform

- **Windows, no admin rights:** a junction to `apps/harness/scripts`, made with `symlinkSync(target, link, "junction")`. This is what `linkEffect` already does in the Effect gate rows. File symlinks may need rights; they are not used.
- **POSIX CI:** the same call with type `"dir"`.
- **`subst` and 8.3:** not automated (system-wide or volume-dependent). The identity comparison does not read the spelling, and the unit rows cover the decision with an injected `stat`.
- **Cleanup:** the link is removed before the temporary folder, so a recursive remove can never reach the repository's `scripts` folder (the rule `linkEffect` states at `effect-gate-real-compiler.integration.test.mjs`).

### Mutation configs and ranges

- `stryker.effect-gate.config.json` and `stryker.stryker-ranges.config.json` mutate their script as a whole file: no line range, so no anchor moves. `stryker-range-anchors.json` and `stryker.config.json` name no script. `check:mutation-ranges` is unaffected.
- The two mutation Vitest configs are not edited: their test files do not change. The guard line's mutants exist today and stay of the same kind (the block runs only in a child process).
- The helper is in no mutation config (Q3).
- **#139:** unchanged. Its "real canary fails inside the Stryker sandbox" is a copied tree, not an alias, and is not this fault. One thing to prove: under Stryker and Vitest the process entry is another file that exists, so the scripts answer `imported` (proof 5).
- **`canaryFolder`:** still parked for #139. `gate-entry.mjs` is the first shared non-test module under `scripts`; it does not own that path.

## Decisions

- **Q1 (decided (a), Pedro, 2026-11-15): which fix?** (a) one shared helper comparing file identity, with `GATE_ENTRY_UNKNOWN` when it cannot tell; (b) library plus always-run bin entries, no guard, about 15 paths and new commands; (c) real-path comparison in each script. **Recommendation: (a).**
- **Q2 (decided (a), Pedro, 2026-11-15): the fourth script, `check-generated-migrations.mjs`.** It has the same guard but is in no gate command. `lane.mjs` answers `rigorous` for any slice that touches it, because its file name holds "migration"; the change is one line and touches no migration. (a) a second slice after slice 1, in the lane Pedro names (the tool says rigorous; lowering it is Pedro's call, not the designer's); (b) leave it and record it as known. **Recommendation: (a)**: shared-vocab-union asks for every copy, and a silent exit in `db:generate:check` is the same fault.
- **Q3 (decided (a), Pedro, 2026-11-15): mutation for the helper.** (a) no new mutation config; four sabotages in the contract stand in for it; (b) a small dedicated Stryker config and Vitest config (two more files, a heavy run, and the config counts in `check:mutation-ranges` change). **Recommendation: (a).**
- **Q4 (decided (b), Pedro, 2026-11-15): lane of slice 1.** (a) fast, as `lane.mjs` answers; (b) normal, adding one independent candidate review, because this is gate code. **Recommendation: (b)**: a wrong answer here is a gate that passes without checking, and one review is cheap against that.
- **Q5 (decided (a), Pedro, 2026-11-15): the existing spawn rows in the two unit test files** (left out of #148). (a) leave them; (b) move them to integration in this work. **Recommendation: (a)**: no timeout seen, and it would double the paths.
- **Rejected:** an explicit `--run` flag (a launch without it would exit 0 silently: the same fault); comparing `realpathSync.native` strings (equal in the probe, but a string comparison where identity is available).
