# Design: C1-0 S3b — the window updates an older Project

Lane: rigorous (`lane.mjs --paths`, 2026-10-06: files 7 > 5; sensitive word `preload`). Intent review: at most two rounds (user rule).

## Intent

S3a (`110ea90`) made `project.upgrade` a strict protocol-v6 message that the harness answers, but nothing in the desktop sends it. S3b closes the loop for the user: opening an older Project shows "Updating Project…" and then the normal Project view, with no prompt. If the upgrade fails, the Project stays in its safe-mode view and the window says why; if the call itself fails (a rejected IPC call), the window shows the existing connection error, as opening does today.

Authoritative requirements:
- parent S3 design (`.rpiv/artifacts/designs/2026-10-06_13-20-24_upgrade-request-and-window.md`, content hash `b031715c8a7a53ffdde910be0cfb8019dc8885af3645cbc69519145c6827486f`): "S3b — outline", the protocol table, F3, F7 and F10;
- FRD (`.rpiv/artifacts/discover/2026-10-05_20-11-21_project-database-staged-upgrade.md`, content hash `d45f5d9c6f63fdfd7cca2e00d6197299522aa2568bae31e3a1c0155165b21105`): FR7, FR8 and FR11, the UX/Accessibility NFR, and the E2E acceptance criterion;
- S3a as built: `.rpiv/artifacts/evidence/2026-10-06_c1-0-s3a-tdd-evidence.md` (deviations 1–10);
- user decisions: `.rpiv/artifacts/evidence/2026-10-05_conversation-decisions.md` §8.

Non-goals:
- changing activation or switch results, or the bridge's activation and switch mapping;
- visual identity (not decided by the user; the screens use the existing workspace style, and the Figma exploration is not a contract);
- an E2E failure journey (G2);
- Sentry, the C1 gate and S4.

Constraints:
- AGENTS.md process boundaries, strict decode both ways, and renderer isolation;
- `degrade-distinguishes-broken`, with one user-accepted exception (G8);
- `shared-vocab-union`: the window and the bridge read the protocol's `projectUpgradeDiagnostics`, never their own copy;
- no test hook in production code (parent F7);
- squash merges;
- two review rounds.

## Architecture

### Facts (verified at `110ea90`)

**Bridge**
- `createProjectEntryBridge` returns `{ list, register, activate, switchProject, stop }` (`apps/desktop/src/main/project-entry-bridge.ts:120-160`).
- `echoing` (:83-119) answers one transport-loss result for a mismatched or undecodable reply, a lost connection and a stopped bridge.
- `Pending.fail()` takes no argument (:23, :31-35), so a `request.failure` loses its code. `dispatchPendingHarnessEvent` passes only a message (`harness-pending-request.ts:6-22`).
- `dispatchPendingHarnessEvent` is shared with `workspace-bridge.ts:119-123` and `project-storage-bridge.ts:98-102`. Both build diagnostics from that `message`; their tests pin it.
- An undecodable payload reaches a bridge only as a session `protocol-error` (`harness-session.ts:40-43`).
- `session.send` returns `HARNESS_SESSION_MESSAGE_INVALID`, `HARNESS_SESSION_UNAVAILABLE` or `HARNESS_SESSION_SEND_FAILED` (`harness-session.ts:67-86`). The first cannot happen for a factory-built command: the factory decodes against the same schema (`protocol.ts:459-471`).

**Protocol** (`packages/protocol/src/project-upgrade-protocol.ts:19-133`)
- `projectUpgradeDiagnostics` has twelve keys. `connectionLost` is byte-identical to the row `echoing` builds today for activation (retryable true; switch builds retryable false) (`project-entry-bridge.ts:97-106, 145, 152`).
- The protocol test pins the map against the literal design table (S3a deviation 10).

**IPC and preload**
- Channels and `SlopStopApi` are declared in `apps/desktop/src/shared/desktop-api.ts:20-53`.
- The Project IPC handlers are inline in `main.ts:400-409`. The precedent for an extracted, unit-tested registration is `registerWorkspaceIpc` (`workspace-bridge.test.ts:919-947`) and `project-registration-ipc.ts:48-56`.
- The preload decodes both ways (`preload.ts:29-36`).
- API method lists live in `package-smoke-verifier.ts:29-42`, `package-smoke-verifier.test.ts:382-393`, `tests/e2e/shell.test.ts:99-112` and `src/renderer/test-api.ts:19-52`. `canonical-writer-package-smoke-main.test.ts:84-91` is a bridge mock, not an API list.

**Renderer**
- `ProjectsWorkspace.open` (`projects-workspace.tsx:137-164`) activates, or switches when a Project is already active (`switchTo` :106-135). Its catch (:150-157) shows "Project selection could not be confirmed. Refresh the connection before trying again." and clears the view.
- `present` (:80-104) maps `safe-mode` to the view mode `"safe-mode"`.
- The `selecting` ref and `busy` guard against a second open (:41, :48, :138-160, :214, :237). The `ready`/`attempt` effect resets the workspace on a harness restart (:63-76).
- The busy line is mounted with its text (`workspace-view.tsx:74`).
- `app.tsx:113` already renders an always-mounted `role="status"` for the harness, which tests query singly (`app.test.tsx:303,309`; `shell.test.ts:87,158,159`).
- After a switch to a safe-mode target, the coordinator is `inactive` (`active-project-coordinator.ts:457-464, 636-641`).
- Precedents:
  - "Reference:" and "Try again": `removal-view.tsx:76-86`, `outcome-view.tsx:24-26, :70-72`;
  - renderer API fakes: `test-api.ts:11-63`;
  - gated promises: `app.test.tsx:249-286`.

**Seeding**
- An older Project cannot be a registered Project: registered admission reads `repository_bindings` (`registered-project-selection.ts:66`), which does not exist at canonical schema 2.
- A Storage-only Project keeps the legacy opening contract (:113-114) and is listed as `registration: "unbound"` (`registration/project-listing.ts:170-191`). The window opens an unbound safe-mode row (`projects-list.tsx:46-49`) labelled "Open Project without a repository <first 8 chars>" (:15-18, :69).
- `createGenerationTwoProject(root)` (`apps/harness/tests/integration/project-storage-upgrade-fixture.ts:240-275`) builds exactly that Project, id `00000000-0000-4000-8000-000000000010`, with its application database at `root`.
- E2E seeding reaches harness fixtures only by running vitest in a subprocess, gated by an environment variable (`tests/e2e/projects.test.ts:12-40`). The desktop storage root is `<userData>/storage` (`project-storage-bootstrap.ts:25`).

### Bridge: `upgrade`

`upgrade(input: ProjectUpgradeRequest): Promise<ProjectUpgradeResult>`. It never throws, except for the strict input decode.

| Event for a pending `project.upgrade` | Result (rows from `projectUpgradeDiagnostics`) |
|---|---|
| `project.upgrade.result` that decodes strictly and echoes the request | that result, unchanged |
| reply whose `request` differs, or with the wrong `event` | `broken` + `protocolMessageInvalid` |
| session `protocol-error` (also every undecodable reply) | `broken` + `protocolMessageInvalid` |
| command factory throws (for example a non-UUID id), or the message id collides | `broken` + `protocolMessageInvalid` |
| `send` returns `HARNESS_SESSION_MESSAGE_INVALID` (unreachable, see Facts) | `broken` + `protocolMessageInvalid` |
| `request.failure` with code `HARNESS_INTERNAL_FAILURE`, `PROTOCOL_MESSAGE_INVALID` or `PROTOCOL_VERSION_UNSUPPORTED` | `broken` + that code's row (the row's message, not the payload's) |
| session `disconnected`; `send` returns `HARNESS_SESSION_UNAVAILABLE` or `HARNESS_SESSION_SEND_FAILED`; `stop()` while pending; call after `stop()` | `unavailable` + `connectionLost` |

**Additive failure argument.** The change keeps every existing argument:
- `dispatchPendingHarnessEvent`'s handlers keep their `message: string` argument.
- They gain a trailing `failure: PendingFailure`:

  ```ts
  type PendingFailure =
    | { kind: "transport" }
    | { kind: "protocol" }
    | { kind: "harness"; code: HarnessFailureCode };
  ```

- `failAll` passes `transport` on `disconnected` and `protocol` on `protocol-error`; `failRequest` passes `harness` with the payload code.
- `workspace-bridge.ts` and `project-storage-bridge.ts` stay unchanged and keep passing their existing tests.
- In `project-entry-bridge.ts`, `Pending.fail(failure)` receives the failure. `activate`, `switchProject`, `list` and `register` ignore it, so their results are unchanged.

The mapping from `PendingFailure`, and from a bridge-detected fault, to a `ProjectUpgradeResult` is one exported pure function in a new `apps/desktop/src/main/project-upgrade-failure.ts`.

### IPC and preload

- `desktopIpcChannels.upgradeProject = "projects:upgrade"`.
- `SlopStopApi.upgradeProject(request: ProjectUpgradeRequest): Promise<ProjectUpgradeResult>`.
- New `apps/desktop/src/main/project-entry-ipc.ts` exports `registerProjectEntryIpc(projects)`. It owns the four Project handlers (list, activate, switch, upgrade) now inline at `main.ts:400-409`, moved unchanged apart from the new one, which uses `decodeStrict(ProjectUpgradeRequestSchema, value)`. `main.ts` calls it once where the handlers are today.
- The preload follows the activation pattern: strict decode of the request before `invoke`, and of the result after.
- The four API lists gain `upgradeProject`. The bridge mock in `canonical-writer-package-smoke-main.test.ts` gains `upgrade` as test scaffolding.

### Renderer: the update flow

`ProjectsWorkspace` holds the state and `WorkspaceView` the markup. The new panel is `apps/desktop/src/renderer/upgrade-problem.tsx`. The flow logic lives in a new hook, `apps/desktop/src/renderer/use-project-upgrade.ts`.

**Trigger.** The flow starts when `open` presents a `safe-mode` result with `canonicalHealth.status === "migration-required"`. The result can come from an activation or a switch target. A follow-up activation inside the flow never triggers it.

1. **Progress.** One always-mounted, visible `<p id="ws-progress" aria-live="polite">` replaces the conditional busy line in `WorkspaceView`. It is rendered by `ProjectsWorkspace` inside `<main>`, beside the existing `srOnly` live region (`projects-workspace.tsx:250`) and outside the `aria-busy` "Project workspace" section, so it is mounted while the add or remove screen shows and its announcements are not held back by `aria-busy`. It has no `role`, so the existing `role="status"` queries stay unique.
   - Its text is "Opening Project…" during the first activation or switch.
   - It reads "Updating Project…" from the upgrade request until the follow-up activation answers, and does not switch back to "Opening" (G1).
   - It is empty otherwise.
   - `busy` becomes `"opening" | "updating" | undefined`.
   - `selecting` stays held, and the open buttons stay disabled, through the whole flow, including the follow-up activation and every retry.
2. **Success.** If the result is `upgraded` or `not-required`, the window calls `activateProject({ projectId })`.
   - If that activation answers `active`, it is presented, and the Project list refreshes (existing `refresh`), so the row no longer says safe mode.
   - If it is still `safe-mode` `migration-required`, the window shows the safe-mode view and the panel for the protocol row `broken` + `storageBroken`, with no second upgrade (G5).
   - Any other result is presented as `open` presents it today.
3. **Not registered.** `not-registered` shows the existing "This Project is not registered." error.
4. **Failure.** Any other status keeps the safe-mode view (same label and body) and adds the panel:
   - a `role="alert"` container holding exactly three lines:
     - "This Project could not be updated. Your data is intact." (FRD FR7 in the app's English), with `tabIndex={-1}`;
     - the row's `message`;
     - "Reference: <code>";
   - a "Try again" button outside the `role="alert"` container, unless the status is `refused` (F3).

   "Try again" reruns steps 1–5 from the upgrade request: the whole upgrade (FR8), without a new first activation.
5. **Rejected call.** If `upgradeProject` or the follow-up `activateProject` rejects (a preload decode failure or an IPC fault), the flow behaves as `open`'s catch does today. It shows "Project selection could not be confirmed. Refresh the connection before trying again.", clears the view (heading "No Project selected"), empties the progress line, and releases `selecting`. This applies from the first attempt and from "Try again".
6. **Focus.**
   - When the panel appears, focus moves to "Try again", or to the panel's first line ("This Project could not be updated. Your data is intact.") when the status is `refused`.
   - When "Try again" is chosen, the panel is cleared and focus moves to `#ws-heading`.
7. **Lifetime.** The panel is cleared by a new open, by a list refresh, by starting the add or remove flow, and by the `ready`/`attempt` reset.
   - A flow whose epoch changed while a call was pending drops its result: no panel, no follow-up activation, no view change.
   - Like `open` today (`projects-workspace.tsx:158-163`), the flow releases `selecting`, `busy` and the progress text in its `finally` only when its epoch is still current; the `ready`/`attempt` reset already clears them, so a stale flow never releases a newer open's guard.

### Data flow

```text
row click --activateProject--> preload --projects:activate--> bridge --> harness: safe-mode migration-required
#ws-progress "Updating Project…" --upgradeProject--> preload --projects:upgrade--> registerProjectEntryIpc --> bridge.upgrade
  --project.upgrade--> runtime/coordinator/owner (S3a)
  <-- project.upgrade.result | request.failure(code) | protocol-error | disconnect  ==> one ProjectUpgradeResult
upgraded|not-required --> activateProject --> active: present + refresh list | still migration-required: panel storageBroken
other --> safe-mode view + panel (sentence, message, Reference, Try again unless refused)
rejection --> "Project selection could not be confirmed…"
```

## Decisions

- **G1 Busy text** (user): "Opening Project…" first, then "Updating Project…" from the upgrade request until the follow-up activation answers. It does not switch back.
- **G2 E2E covers the success path only** (user). The failure panel, the reference and "Try again" are proven by renderer tests through the preload API, and the failure mapping by bridge tests. The harness proves a real one-time failure and a successful retry (S3a UPG-B27).
  - Rejected: a physical fault in E2E (timing-fragile) and an E2E-only fault hook (breaks F7).
  - Residual risk: no composed proof of a failure result through the real IPC handler.
- **G3 Failure copy** (user): the FRD sentence in English, the protocol `message`, "Reference: <code>", and "Try again" unless `refused`. The safe-mode view stays underneath.
- **G4 Bridge failures are distinct**:
  - a harness `request.failure` keeps its code;
  - malformed replies, protocol errors and desktop-side faults are `broken PROTOCOL_MESSAGE_INVALID`;
  - only a lost or stopped connection is `unavailable` + `connectionLost`;
  - activation and switch mapping is unchanged (non-goal).
- **G5 One automatic upgrade per open; a false success is visible** (user, round 1, reopened). If the harness answers `upgraded` or `not-required` but the follow-up activation is still `migration-required`, the window shows the panel with `broken PROJECT_STORAGE_BROKEN` ("Project Storage upgrade failed.") and "Try again". There is no automatic second upgrade. Residual risk: this reference is chosen by the window, not reported by the harness (FRD "the reference code is the real code"), it cannot be told apart from the harness's own `PROJECT_STORAGE_BROKEN`, and no desktop log line records it.
- **G6 Persistent progress region**: an always-mounted `aria-live="polite"` paragraph `#ws-progress`, with no `role`, so the existing `role="status"` stays unique.
- **G7 The older Project in E2E is Storage-only (unbound)**: a generation-two Project cannot carry a registration (Facts, Seeding).
- **G8 Desktop-side faults share `PROTOCOL_MESSAGE_INVALID`** (user, round 1: accepted residual risk). The shown message "Harness received an invalid protocol message." also covers a malformed reply or a desktop-side fault, with no distinct desktop log line. Rejected: a bridge logger with its own codes (wider scope).
- **G9 IPC handlers extracted** to `registerProjectEntryIpc`, so the new handler has a unit oracle (precedent `registerWorkspaceIpc`).
- Inherited, unchanged: parent F1–F10, S1 D1–D12 and S2 E1–E10.
