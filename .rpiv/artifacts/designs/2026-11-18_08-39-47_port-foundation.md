# React port, Foundation (PORT-PLAN slice 1)

## Intent

**Outcome.** The whole window can use the Ragnarok theme, not only the Conversation region, and the window gets its own dark title bar with the Raidho rune and the native Windows buttons. This is the ground the Shell slice and every later screen stand on.

**Scope (roadmap Phase 3 items 1 and 2; PORT-PLAN slice 1).**
- The theme tokens become global.
- The Raidho mark (ᚱ), the rune rule and the diamond.
- The custom title bar (`DESIGN.md`, "Window chrome": `titleBarOverlay` with native caption buttons), with an Electron security review.

**Already done, so not in scope.** Bundled fonts (Red Hat Text, Cinzel, Cascadia Code), the Runa icon component, the focus ring, the accessibility e2e harness and the per-window CSP owner were built in Conversation C1 S4a. The old `renderer/prototype/` folder is gone. PORT-PLAN still lists the fonts and "the Lucide decision"; both are stale (Runa v2 is decided, `DESIGN.md:362`).

**Non-goals.**
- The Shell (top bar contents, rail, Attention sidebar), the Projects list and every other screen: later PORT-PLAN slices.
- The Rive splash window. Its CSP rule is recorded in ADR 0001 (Amendment 2026-11-18) and it has its own slice.
- The product rename to Ragnarok (executable, `userData`, AppUserModelId): ADR 0001, Amendment 2026-10-10. Only the visible title is asked about here (Q4).
- Notifications, tray and close behavior (same `DESIGN.md` line as the window chrome): later.
- Restyling the old shell. It keeps its look until the slice that replaces it.

**Constraints.**
- Renderer security defaults stay: context isolation and sandbox on, Node integration off, navigation and new windows denied, the strict CSP, ASAR integrity, the fuses (`AGENTS.md`, ADR 0001).
- The renderer imports neither Electron nor Node APIs.
- Accessibility is an acceptance criterion of every slice from here (roadmap Phase 3 item 3; decisions log §33; the 12-point checklist at `ragnarok-hero/access.src.html:381-393`). Each slice maps the checklist.
- Mutation testing runs only on the last slice of the work, unless a slice is critical; then on its changed files, saying why (Pedro, 2026-11-18).
- Each slice deletes the old code it replaces in the same change (Pedro, 2026-10-09, decisions log §22).
- Windows is the product platform (ADR 0001). The title bar is designed and proved on Windows; another platform keeps its native frame and is not tested.

## Architecture

### What is on main (read at `4ea961d`)

**Tokens.**
- The Seixo tokens are declared once, on `.seixo, .seixoTokens`, in `apps/desktop/src/renderer/theme/seixo.module.css:14-70`: 18 colours, 4 radii, 9 spacings, 2 hover fills, 4 shadows, the focus and fault rings, 2 font stacks, 1 transition.
- `.seixo` is the Conversation region root. `.seixoTokens` gives the tokens alone to one element outside the region: the note strip (`workspace-view.tsx:140`).
- `seixo-tokens.test.ts` reads `DESIGN.md` and requires each token "exactly once, equal to DESIGN.md"; it also guards colour literals, the forced-colours rules and selector scoping.
- The old shell is in `@layer legacy-shell`: `global.css` and `legacy-shell.css` on `:root`, and `projects-workspace.module.css`.
  - `global.css` declares ten old properties on `:root`. Only two are used (`--surface`, `--signal`, in `global.css` itself). Three of the unused ones have the names of Seixo tokens with other values: `--ink`, `--ink-muted`, `--line-strong`.
  - `projects-workspace.module.css` uses `--legacy-*` properties only (guarded by `legacy-shell.test.ts`).
- `main.tsx` imports the font files and `global.css`.

**Brand marks.**
- The old shell shows a letter "R" as its rail mark and an `<h1>Ragnarok</h1>` in a 3.5rem header (`projects-workspace.tsx:233-250`). Its one rail icon comes from `@phosphor-icons/react`, a third-party set that `DESIGN.md:373` forbids; it goes with the Shell slice.
- No Raidho mark, rune rule or diamond exists in the renderer. Their prototypes are `ragnarok-hero/components.css:62-63` (rune: 11 by 21, 1.25px non-scaling stroke), `:570-581` (rune rule) and `:582-587` (diamond, tones).

**Window.**
- `createApplicationWindow` (`apps/desktop/src/main/main.ts:272-309`) builds the one window: native frame, `minWidth` 640, `minHeight` 480, `backgroundColor` `#101411`, `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`, `devTools` only when not packaged. It is not covered by a unit test; `main.ts` is the entry.
- No application menu is set, so Electron's default menu is in force.
- `index.html` has `<title>SlopStop</title>`; `package.json` has `productName: "SlopStop"`.
- The CSP owner is `apps/desktop/src/shared/content-security-policy.ts` (one window kind, `main`); the header is installed for the whole default session (`security.ts:9-22`); the built page also carries the `<meta>`.

**Title bar design.**
- `DESIGN.md:353`: native Windows caption buttons through `titleBarOverlay` inside the dark rune title bar, Snap layouts kept (decisions log §33, option A).
- `DESIGN.md:268`: the shell has "a 44px top bar". The title-bar prototypes (`ragnarok-hero/firstuse.css:47-52`, `appicon.css:68-73`, `access.css:257-266`) draw a 36px bar with the rune, the wordmark and a place name. Whether these are one bar or two is not written anywhere (Q2).
- Electron 43.4.0 (Context7, `/electron/electron/v43.4.0`, `docs/tutorial/custom-title-bar.md`): `titleBarStyle: "hidden"` with `titleBarOverlay: { color, symbolColor, height }` keeps the native buttons on Windows and enables the Window Controls Overlay CSS variables (`env(titlebar-area-*)`); `win.setTitleBarOverlay` changes the colours later.

### The shape

**Global tokens (first slice).**
- A new global style sheet, `theme/tokens.css`, declares every token once on `:root`, outside any layer. `main.tsx` imports it.
- `seixo.module.css` stops declaring tokens and keeps the region's rules. `.seixoTokens` is deleted, and the note strip drops that class: it now inherits the tokens from `:root`.
- `global.css` loses its eight unused old properties, which removes the three name clashes. The old shell's two used properties and every `--legacy-*` property stay. The old shell's look does not change.
- Token names stay as they are (`--canvas`, `--frost`, `--radius-pill`, `--space-4`): the Conversation region already uses them, and they are the `DESIGN.md` names.
- Added now, from `DESIGN.md`, because the Foundation uses them: `--font-mark` (Cinzel, for the wordmark), and the two missing shadows of the Shadow Vocabulary, `--shadow-row-lift` and `--shadow-overlay`. Motion tokens beyond `--transition-control` wait for their first user.

**Title bar (later slice; outline only, see Next Slice).**
- Main process: one small pure function gives the window-chrome options from the platform and the high-contrast state. On Windows: `titleBarStyle: "hidden"` and a `titleBarOverlay` whose colours come from the theme; in Windows high contrast it passes no colours, so the system's are used. `main.ts` spreads its answer into the `BrowserWindow` options and changes nothing in `webPreferences`.
- Renderer: a `TitleBar` component at the top of the window: the Raidho mark, the wordmark, a drag region, and a reserved empty area where the native buttons sit (`env(titlebar-area-width)`). It shows application-owned text only.
- No new IPC channel and no preload change: the native buttons need none. That is what makes option A the small one.

**Brand primitives.** The Raidho mark is one SVG component (decorative by default, like `RunaIcon`). The rune rule and the diamond are small presentational components with tones. Where they first appear is Q1.

## Decisions

- **Q1 (open, Pedro): the rune rule and the diamond have no screen to live on until the Shell slice.** The Raidho mark has one: the title bar. (a) Build the mark in the title-bar slice, and move the rune rule and the diamond to the Shell slice, where the Attention title and the status chips use them; (b) build all three now, as PORT-PLAN lists them, proved by component tests only and used by nothing until Shell. **Recommendation: (a).** Under (b) Pedro cannot judge them in place, "never colour alone" (checklist 07) cannot be checked on a part with no state, and the code ships unused. Cost of (a): PORT-PLAN slice 1 is one item shorter and slice 2 one longer.
- **Q2 (open, Pedro, with the ui-ux agent): is the rune title bar the shell's 44px top bar, or a second bar above it?** (a) One bar, 44px: the Foundation gives it the rune, the wordmark, the drag region and the native buttons; the Shell slice later adds the Project switch, the tabs and search to the same bar; (b) two bars: a 36px title bar as in the prototypes, and the 44px top bar under it. **Recommendation: (a).** Two bars spend 80px of height on chrome, and at the minimum window (640 by 480) that is a sixth of the screen.
- **Q3 (open, Pedro): the old shell already shows "Ragnarok" as its heading and an "R" as its mark.** With the title bar, the name would show twice. (a) The title-bar slice removes the old heading text and the "R" mark, and the page keeps exactly one `<h1>`; (b) both stay until the Shell slice. **Recommendation: (a)**: it is the "delete what the slice replaces" rule.
- **Q4 (open, Pedro): the window's title.** Windows shows it on the taskbar and in Alt+Tab; today it is "SlopStop". (a) The title-bar slice sets it to "Ragnarok", and the executable, the data folder and the installer names stay for the rename work; (b) it stays "SlopStop" until the rename. **Recommendation: (a)**: a bar that says RAGNAROK over a taskbar entry that says SlopStop reads as two programs.
- **Q5 (open, Pedro): lanes and slices.** (a) Two slices if Q1 is (a): `pf-s1-global-tokens`, normal lane; `pf-s2-title-bar`, rigorous lane, with the Electron security review as its intent and candidate reviews, and the work's one mutation run (it is the last slice, and the one that touches window creation). With Q1 (b) a third slice, `pf-s3-brand-primitives`, normal lane, goes between them; (b) everything normal lane. **Recommendation: (a).**
- **Settled without a question (constraints, not choices):**
  - Token names are kept.
  - The old shell keeps its look in the first slice. Between the title-bar slice and the Shell slice the new dark bar sits on top of the old shell; two looks meet at one line for that time. This follows from porting slice by slice (Pedro, 2026-10-09) and is said here so it is no surprise.
  - Windows only for the title bar.
- **Rejected:**
  - Custom-drawn caption buttons: decided against (§33, option A). They would also need minimise, maximise and close IPC channels.
  - Keeping tokens scoped and adding `.seixoTokens` to each new screen: every screen would need the class, and one forgotten class gives an unstyled screen.
  - Putting the tokens inside `@layer legacy-shell`: the layer exists so the new look wins over the old; tokens in it would lose to any unlayered rule.

## Verification Notes

- The derived tokens (`--focus-halo`, `--fault-edge`, `--fault-halo`, the two focus rings) are written from other tokens and now resolve on `:root`. An element that overrides `--frost` for itself would not get a matching halo. Nothing does that today; the note strip's test overrides `--canvas`, which no derived token reads except the frost-gap ring.
- `:where(.seixo *:not(svg, svg *)) { all: revert; }` does not reset custom properties, so the region still inherits the tokens.
- Unlayered rules win over `@layer legacy-shell` whatever their specificity. That is why the three name clashes in `global.css` must go in the same slice: left in place they would simply lose, but PF-B2 keeps one owner honest.
- PF-B3 compares computed custom properties, which the browser returns as written; the row normalises case and spaces.
- e2e rows run the built bundles with the development Electron binary (ADR 0001); the packaged application is proved by the launch smoke at `check:deep`.
- (Amendment.) The designer's contract missed that removing a line from a file with Stryker line ranges moves those ranges. The Phase 3 lesson "Stryker ranges re-pointed with anchors in the same slice" applied here and was not carried into this brief; `check:mutation-ranges` caught it.
- The title-bar outline is not a contract: its behaviors have no oracles yet, on purpose, until the probe facts exist.

- High contrast: `nativeTheme` fires `updated` and `shouldUseHighContrastColors` flips, about 4 s after it is switched on and about 5 s after it is switched off. The overlay does not follow by itself (it stayed `#16191c` while the page got forced colours). Called from the `updated` handler, `setTitleBarOverlay` repaints it.
- Second probe (Q11, display scale 1.5):

### The shape, as it will be built

**Main process.**
- `window-chrome.ts` (new) holds the pure parts and the service.
  - Pure: the overlay colours for a high-contrast state; `opaqueSystemColour`, which turns the system's `#RRGGBBAA` into a lower-case six-digit `#rrggbb` (alpha dropped, so the strip is opaque) and answers nothing for any other form; and `applicationWindowOptions`, which builds the whole `BrowserWindow` options object that `main.ts` builds inline today. On `win32` it adds `titleBarStyle: "hidden"` and `titleBarOverlay: { color, symbolColor, height: 44 }`; on another platform it adds nothing, so the native frame stays. `webPreferences`, the minimum size, `show: false` and the background colour (`#101411`, as on main) are value for value the ones on main.
  - Ports (`WindowChromePorts`): `platform`, `packaged`, `highContrast()`, `systemColour(name)` for `window` and `window-text`, `onThemeUpdated(listener)` which answers its own unsubscribe, `createWindow(options)`, and `reportUnreadableColour(name)`.
  - Service `WindowChrome` (`Context.Service`), one operation with no requirements: `open({ width, height, backgroundColor, preload })`. It reads the high-contrast state at that moment, builds the options, creates the window through the `createWindow` port, remembers the window until its `closed` event (registered with `once`), and answers that same window, typed so `main.ts` gets its `BrowserWindow` back without a cast.
  - Layer: on `win32` it acquires exactly one `onThemeUpdated` subscription with `Effect.acquireRelease`; the release calls the unsubscribe. On another platform it subscribes to nothing. On each event the service reads the state again and calls `setTitleBarOverlay` on each window it remembers that is not destroyed. It never asks Electron for "all windows", so a window made elsewhere (the planned splash window) is never touched.
  - **A system colour that is not eight hex digits after `#` (Q12, open, written on (a)):** the service uses the fixed pair black `#000000` and white `#ffffff` for both colours and calls `reportUnreadableColour` with the colour's name; `main.ts` logs one warning with the code `DESKTOP_SYSTEM_COLOUR_UNREADABLE` and the name, never the value. The overlay never receives a string Electron might refuse, so the `updated` handler cannot throw on the colour.
  - A failing `createWindow` stays a defect; `main.ts` and the reopen rule see the same rejection as today.
- `desktop-runtime.ts`: the service joins the one desktop runtime. `DesktopRuntimePorts` gains the chrome ports, the desktop Layer gains the chrome Layer with its release in the owners' scope, and `DesktopServices` gains `windowChrome`. No second runtime, no `Effect.provide` per call.
