## Design notes for review

- **Lock.** `FairPermitLock` (`permit-lock.ts`) keeps `#held`, a FIFO array of waiter `Deferred`s and a `#handing` depth. Its acquire and release are methods keyed by module-private symbols, so no caller can reach the state.
  - Release shifts the head waiter and completes it with `Deferred.doneUnsafe` in one synchronous step (the Q3 invariant).
  - A waiter resumed inside another hand-off (`#handing > 1`) yields once, uninterruptibly, before its body. This is the anti-nesting guard. It defers only the resumption, never the dequeue and completion.
- **Interruption.** A waiter interrupted while queued splices itself out. An interruption after hand-off releases again: this is the R6 defensive branch, `#abandon`'s `else`. The yield is outside `restore`, so it cannot be interrupted, and the branch stays unreachable from the seam.
- **Facade.** The Promise `withPermit` keeps one `runPromise` acquire followed by a synchronous release. The start-deferral pin `sync,tick1,op,tick2,tick3,tick4` is unchanged.
- **`ProjectStorageLocks`.**
  - `make` is now `Effect.sync` and exposes only `forCreate`, `afterCreateDrain` and `forProject`.
  - The facade and each service value build their own `createLockSet()`, a module-private helper.
  - `retainProject` is now synchronous and is released exactly once: by `acquireUseRelease`, or by the facade's single `finally`.
  - No idempotent-release flag was added (R13).
- **Refactor gate (CodeScene).** `project-registration-flow.ts` scored 9.68, both at base and after B6, from the pre-existing `dispatch` (cyclomatic complexity 9). To reach the required 10, the switch was split into `dispatch` and `dispatchProposal`. The behaviour is unchanged and exhaustiveness is still checked by the return type. The result scores 10, and the safeguard says "improved".
- **Mutation scope (R2), for the later run.** The config gains `permit-lock.ts` and `project-registration-flow.ts:204-216` in `mutate`, plus the two new test files in the include. The brief's flow range `:184-196` and writer range `:111-118` were base line numbers. On the candidate, the same code sits at `project-registration-flow.ts:204-216` and `canonical-project-writer.ts:112-119`, so the run commands should use those.
