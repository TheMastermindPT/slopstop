### I1 🟡 A quit during an upgrade can never stop it cooperatively; the desktop stops forwarding its diagnostics first [cascade: masking]

**Where**
`apps/harness/src/active-project-coordinator.ts:670` `apps/harness/src/harness-runtime.ts:96` `apps/harness/src/harness-runtime.ts:102` `apps/harness/src/active-project-coordinator.ts:608` `apps/harness/src/storage/project-storage-upgrade-pipeline.ts:408` `apps/desktop/src/main/harness-supervisor.ts:367`

**Code**
```
        return projectUpgradeResult(request, await dependencies.storage.upgrade(request));
  const canonical = startStop(() => options.canonicalProjectApplication.stop());
          Effect.suspend(() => startStop(() => options.projectStorageApplication.stop())),
  const stopOnce = retryableAttempt(() => enqueue(stop));
    if (!isRunning(pipeline.lifecycle)) return;
      lines.end();
```

**Why**
Constituents Q7+Q13+Q4. The runtime stops the coordinator first (harness-runtime.ts:96), whose stop is queued behind the running upgrade's lifecycle permit (active-project-coordinator.ts:608, :670); the Storage owner, the only source of the cooperative stop signal, stops only afterwards (harness-runtime.ts:102). So the pipeline's assertRunning guards and the skip-discard-when-stopping branch (project-storage-upgrade-pipeline.ts:109, :408) are dead in production, the ADR 0005:47 'owner stop' interruption cannot happen, and the desktop ends the log forwarder (harness-supervisor.ts:116 -> :367) and kills the child after 5 s, so an upgrade still running at quit becomes 'interrupted' and its abandoned/discard-failed lines are lost. Data stays safe (declare-before-disk, discard at next activation).

**Fix**
Decide the intended quit behaviour: either signal cancellation to the Storage owner before awaiting the coordinator permit (and prove the post-switch answer, see Q13), or document that quit-during-upgrade is always an interruption and amend ADR 0005:47; keep the stdout forwarder open until the child exits (Q4).

### I2 🟡 A busy registry during the unfinished-upgrade lookup is silently read as 'no unfinished upgrade' [cascade: contradictory-design]

**Where**
`apps/harness/src/storage/project-storage-upgrade-node-adapter.ts:542` `apps/harness/src/storage/project-storage-upgrade-recovery.ts:117` `apps/harness/src/storage/project-storage-upgrade-recovery.ts:105`

**Code**
```
    return undefined;
  if (upgrade === undefined) return "none";
  const kind = isBusyStorageError({ error: cause }) ? "busy" : "broken";
```

**Why**
Constituents Q11+Q19. The catch in unfinishedUpgradeRows (project-storage-upgrade-node-adapter.ts:539-542) rethrows only client-initialization errors, so a transient SQLITE_BUSY becomes undefined -> 'none' (project-storage-upgrade-recovery.ts:117) with no discard-failed(busy) diagnostic; the following opening sees the target staging row and answers safe mode recovery-required (project-storage-opening.ts:65-71). The same busy one statement later is classified busy (recovery.ts:105), answers retryable unavailable and is diagnosed. Violates the standing decision degrade-distinguishes-broken and the ADR 0005:48 diagnostic rule; one-shot because the next activation retries.

**Fix**
Classify the marker-lookup failure like the discard steps: busy -> ProjectStorageUnavailableError plus discard-failed(busy), anything else -> broken; add a red-first test with a held registry write lock during findUnfinished.

### I3 🟡 Upgrade diagnostic rows are protocol-owned, but activation and the bridge hand-copy the same texts, and the pin drops the busy text

**Where**
`packages/protocol/src/project-upgrade-protocol.ts:78` `apps/harness/src/project-upgrade-outcome.ts:25` `apps/desktop/src/main/project-entry-bridge.ts:104`

**Code**
```

      ? { status: "unavailable", request, diagnostic: rows.storageUnavailable }

```

**Why**
Constituents Q26+Q27+Q28. The upgrade schema pins each message as a literal (project-upgrade-protocol.ts:78) while the activation schema keeps free text (canonical-project-protocol.ts:130). The coordinator (active-project-coordinator.ts:176, :289) and the bridge (project-entry-bridge.ts:104) hand-copy the same texts (shared-vocab-union, AGENTS.md:96), and the pin forces project-upgrade-outcome.ts:25 to drop the pipeline's busy text (project-storage-upgrade-pipeline.ts:434). **Fix**
Make the protocol rows the single owner: activation/switch producers and the bridge read projectUpgradeDiagnostics (or a shared vocabulary module) instead of literals; decide whether the busy 'can be retried' text is a row of its own.
